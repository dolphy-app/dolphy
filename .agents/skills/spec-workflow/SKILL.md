# Спеки фич и ADR

Схема выбрана по обзору `docs/research/spec-workflows.md` (§9): один файл на активную фичу, по завершении — в архив, долговечные решения — в ADR. Слоя «текущее поведение в specs/» нет: текущее состояние описывают `docs/design`, `engine-ts/design` и README пакетов.

Спека фичи **живёт, пока фича в работе**. После закрытия она становится исторической записью и не источником требований. Так старые фичи не влияют на новые.

## 1. Нужна ли спека

Спека **обязательна**, если фича:

- меняет контракт `@spirula-app/engine-contract`, схему RPC (`@spirula-app/engine-rpc`) или схему БД (`engine.db`);
- добавляет пакет `@spirula-app/*`, экран или настройку (см. `AGENTS.md`: настройка — поле контракта, проверка в сервисе, схема RPC, тест адаптеров).

Иначе спека **не нужна**: багфиксы, рефакторинг и правки внутри пакета без изменения контракта идут сразу в код и коммиты. Сомневаетесь — пишите короткую спеку на полстраницы: `Цель`, `Требования`, `Progress`.

## 2. Что где лежит

| Путь                                    | Что                                                                                   |
| --------------------------------------- | ------------------------------------------------------------------------------------- |
| `specs/<feature-name>/SPEC.md`          | активная фича; имя каталога = имя ветки `feature/<feature-name>`                      |
| `specs/archive/ГГГГ-ММ-ДД-<name>/SPEC.md` | завершённая, заменённая или брошенная фича; дата — день закрытия (коммит `git mv`) |
| `docs/adr/NNNN-<название>.md`           | решения, ограничивающие будущее (§6)                                                  |
| `assets/SPEC.template.md`, `assets/ADR.template.md` | шаблоны в каталоге этого скилла (`skill://spec-workflow/assets/...`) |

Каталоги `specs/` и `docs/adr/` создаются вместе с первым документом, заранее пустыми не заводятся. `specs/` не проверяют prettier и eslint.

## 3. Начало фичи

1. Ветка и worktree — по скиллу `git-workflow`.
2. Прочитать контекст (§7): активные спеки из `specs/` и ADR из `docs/adr/`, пересекающиеся по `touches`.
3. Создать `specs/<feature-name>/SPEC.md` из `assets/SPEC.template.md`. Заполнить шапку (`status: draft`, `branch`, `created`, `touches`, `depends-on`), `Цель`, `Не цели`, `Требования`.
4. Согласовать спеку с пользователем до кода, если есть развилка в поведении. Сразу после согласования `status: active`.
5. Коммит: `docs(repo): add spec for <feature-name>`.

Требования — **наблюдаемое поведение**, а не реализация: то, что видит пользователь или вызывающий код, входы, выходы, ошибки. У каждого требования есть проверка (команда, тест, сценарий в приложении). Проверка: если реализацию можно поменять без изменения поведения, в `Требования` этому не место — оно идёт в `Решения`.

## 4. Ход работы

Спеку обновляют в тех же коммитах, что и код, вместе с изменением плана или решения:

- `Progress` — чек-лист гранулярных шагов с датой (`- [x] 2026-09-30 схема RPC`); всегда отражает реальное состояние, при частичной работе шаг делится на «сделано» и «осталось».
- `Surprises & Discoveries` — неожиданности с короткими доказательствами (вывод теста, число).
- `Decision Log` — каждое решение: что, почему, дата. Изменение курса записывается здесь, а не переписывается молча.
- `Требования` меняют только при смене намерения, и это отмечают в `Decision Log`.

Агентам-исполнителям (`task`) в контекст передают путь к `SPEC.md` и номера требований, а не пересказ.

## 5. Закрытие фичи

Всё в той же ветке, отдельными коммитами, до слияния PR. PR сливают только после зелёного pipeline (`git-workflow`), дата слияния заранее неизвестна, поэтому дата в имени архива — день закрытия, то есть день коммита `git mv`. Если pipeline или ревью потребовали правок, пока ветка не слита, архивную спеку этой фичи можно дополнять (`Decision Log`, `Outcomes`) и переименовывать каталог не нужно.

1. **Перенести долговечное.** Всё, что через полгода нужно знать без чтения спеки, — в `docs/design`, README пакета или приложения; общее правило для всех — в `AGENTS.md`.
2. **ADR.** Если решение ограничивает будущие фичи или его отмена потребует менять контракт, схему или пакеты (§6) — оформить ADR и сослаться на него из `Decision Log`.
3. **Итог.** Заполнить `Outcomes`: что сделано, что отличается от плана, что осталось (оставшееся — новая спека или issue, не «TODO» в архиве). Проставить `status: done` и `closed: ГГГГ-ММ-ДД`.
4. **Архив:**
   ```sh
   mkdir -p specs/archive && git mv specs/<name> specs/archive/$(date +%F)-<name>
   ```
   Первой строкой после шапки в `SPEC.md` вставить: `> Исторический документ. Не источник требований.` Поправить ссылки на старый путь: `git grep -n "specs/<name>"`.
5. Коммит: `docs(repo): archive spec <name>`.

Брошенная фича: `status: dropped`, причина в `Outcomes`, тот же перенос в архив с датой отказа. Такие спеки не удаляют: они защищают от повторного обсуждения.

## 6. ADR

Один ADR — одно решение, короткий (до страницы). Нужен, когда решение:

- ограничивает выбор в будущих фичах («настройки только в `engine.db`», выбор формата контракта, схема идентификаторов);
- дорого отменить (контракт, схема, зависимость уровня пакета);
- не помещается в правило `AGENTS.md`.

Мелкие и локальные решения остаются в `Decision Log` спеки.

- Файл `docs/adr/NNNN-<название-kebab-case>.md`, номер следующий по порядку, четыре цифры, **не переиспользуется**. Шаблон — `assets/ADR.template.md`.
- Статусы: `proposed`, `accepted`, `deprecated`, `superseded by ADR-NNNN`. Принятый ADR не редактируется по существу.
- Отмена решения — новый ADR; в старом меняется только `status`.
- ADR не архивируют: журнал решений лежит в одном каталоге.

## 7. Что читать перед фичей

Источники требований, по убыванию приоритета:

1. Спека текущей фичи и спеки из её `depends-on`.
2. `docs/adr/` (по названиям; открывать релевантные).
3. `docs/design`, `engine-ts/design`, README пакетов и приложения.
4. `AGENTS.md`.

Пересечения с другими активными спеками: `git grep -ln "touches:.*<пакет>" -- specs ':!specs/archive'`.

**`specs/archive/` без явной ссылки не читать и не использовать как источник требований.** Архивная спека может описывать поведение, которое уже заменено. Ссылка допустима из `depends-on` или `supersedes`, когда нужна история или обоснование.

## 8. Замена и переработка

Спека закрытой фичи неизменна. Если поведение меняется:

1. Новая спека `specs/<новое-имя>/SPEC.md` со `supersedes: specs/archive/ГГГГ-ММ-ДД-<старое>` (или ADR).
2. В архивной спеке правятся только `status: superseded` и `superseded-by`, больше ничего.

Опечатки и битые ссылки в архиве можно исправлять.

## Чего не делать

- Не писать спеку под мелкую правку и не расписывать реализацию в `Требования`.
- Не оставлять завершённую спеку в `specs/<name>/` и не читать `specs/archive/` без ссылки.
- Не переносить старые фичи в спеки задним числом: история — в `git log` и merge-коммитах.
- Не править архивную спеку по существу; не переиспользовать номера ADR; не заводить `specs/capabilities` (второй источник текущего поведения).
- Не пропускать закрытие: спека в `specs/` после закрытия фичи — это устаревший документ рядом с актуальными.
