# @spirula/desktop

Настольное приложение: Electron + Vue 3 + Vite. Слой бизнес-логики (`@spirula/engine`) живёт в `utilityProcess`, UI видит его как `LearningEngine` из `@spirula/engine-contract`. Проект: `engine-ts/design/engine-ts-electron.md` (§9–§14).

## Архитектура

```
renderer (Vue, sandbox)      preload (CJS, sandbox)     main                         utilityProcess «spirula-engine»
src/**  ─ LearningEngine ─►  window.spirula.{engine,platform} shells + supervisors        electron/host
        ◄─ MessagePort (RpcRequest / RpcResponse / RpcPush) ─ порт выдаёт main ─►     dispatcher + engine
        ◄─ spirula-ext://<id>/view.mjs (элементы ввода ответа) ─ протокол в main         SQLite (engine.db)
                                                                                        ExerciseTypes: каталог + клиент
                                                                                          │ MessageChannelMain (host-link)
                                                                                          ▼
                                                                                      utilityProcess «spirula-ext-host»
                                                                                        electron/ext-host: рантайм расширений
                                                                                        spirula.sql: fork воркера → ELECTRON_RUN_AS_NODE
```

Сборка (`vite build`) даёт `dist/` (renderer) и `dist-electron/{main,preload,host}`. Preload собирается в CJS (`index.cjs`): при `sandbox: true` Electron не грузит ESM-preload. Хост — ESM-бандл со всеми workspace-пакетами; снаружи остаётся только нативный `better-sqlite3` (N-API prebuild, в упаковке — `asarUnpack`). Вход `ext-host.js` (хост расширений) собирается тем же вызовом.

**Расширения.** Плагин Vite `spirula:extensions` собирает `packages/ext-*` (`pnpm -F <пакет> build` → `dist-ext/`) и кладёт каталоги в `<outRoot>/extensions/<id>/` (в упаковке — `extraResources` → `Resources/extensions`, вне asar: `import()` и `fork` воркера SQL читают настоящие файлы). Пользовательские расширения — `<userData>/extensions/<id>/`, побеждают по `id`. Устройство, манифест и API — `docs/design/extensions.md`. CSP допускает скрипты только `'self'` и `spirula-ext:`; протокол `spirula-ext` отдаёт `.js`/`.mjs` из каталогов расширений с CORS (renderer грузится с `file://`).

**Настройки и вклады расширений.** «Настройки → Внешний вид»: плитки тем из расширений (`themes`) рядом со встроенными «Как в системе», «Светлая», «Тёмная». «Настройки → Обучение»: «Правило оценки» — встроенное Pass@N или правило из расширения (`gradePolicies`); сбой правила или пропавшее расширение — оценка по Pass@N. «Настройки → Расширения»: список расширений (поставка, пользовательское, разработка) с их вкладами по четырём точкам и причиной, по которой расширение не загрузилось или перекрыто. Блоки кода в Markdown заданий выводят рендереры содержимого (`markdownRenderers`, например `spirula.math`); при сбое остаётся исходный текст и заметка.

**Изоляция расширений** (`docs/design/extensions.md`, «Права и изоляция»). Расширения не из поставки (пользовательские и из `SPIRULA_DEV_EXTENSIONS`) изолированы, пока пользователь не нажал «Доверять». Код исполняет ограниченный дочерний процесс: хост расширений запускает `process.execPath` с `ELECTRON_RUN_AS_NODE=1` и флагами режима разрешений Node; вход процесса — артефакт сборки `restricted/ext-restricted.mjs` (плагин Vite `spirula:restricted-child`, `electron/ext-host/restricted-child.ts` → `<outRoot>/restricted/`; в упаковке — запись `{ "from": "restricted", "to": "restricted" }` в `extraResources` в `electron-builder.json`, вне asar: режим разрешений сверяет настоящие пути файлов). Интерфейс (элемент ввода ответа и рендерер содержимого) — в `<iframe sandbox="allow-scripts">`, страницу рамки отдаёт протокол `spirula-ext` (`/__spirula/frame.html`); CSP окна содержит `frame-src spirula-ext:`. «Настройки → Расширения» у расширений не из поставки показывает заявленные разрешения, метку «Изолировано»/«Доверено» и переключатели «Включено» и «Доверять (без изоляции)» (состояние — в `engine.db`; для кода действует сразу, интерфейс, темы и рендереры — после «Перезагрузить окно»). Расширения из поставки не переключаются.

## UI

Интерфейс — Feature-Sliced Design (`app` → `pages` → `widgets` → `features` → `entities` → `shared`; `features` и `entities` заводятся, когда код нужен нескольким экранам: выбранный курс читают план дня и «Курсы», данные курсов — переключатель и «Курсы»). Алиас `@` → `src`. Компоненты — Vuetify 4, тема «индиго + бирюзовый» (светлая и тёмная). Renderer грузится через `file://`, поэтому роутер — на hash-истории. CSP разрешает шрифты (`font-src 'self' data:`) — без этого не грузятся иконки MDI.

**Локализация** — `vue-i18n` (Composition API), языки `ru` и `en`. Сообщения лежат в слайсе (`pages/<слайс>/i18n/{ru,en,index}.ts`), общие — в `shared/i18n`, оболочка — в `app/i18n`; `app/i18n/messages.ts` собирает каталог, `app/i18n/vue-i18n.d.ts` типизирует ключи по каталогу `ru` (опечатка в `t('…')` — ошибка `vue-tsc`, `en: typeof ru` не даёт разойтись наборам ключей). Русские формы — четыре варианта `ноль | один | несколько | много` (`russianPluralRule`), английские — три. Языки и тема выбираются в «Настройках → Внешний вид»; `system` берёт язык системы (неподдерживаемый — английский). Встроенные строки Vuetify берутся из того же каталога (адаптер `createVueI18nAdapter`). Не переводятся данные движка: названия курсов, уроков и упражнений, `feedback` раннера, тексты ошибок движка.

**Хранение настроек** — в `engine.db` (SQLite), не в файлах и не в `localStorage`: опции планировщика (только отличия от умолчаний), предпочтения, сохранённые фильтры и сессии, тема и язык интерфейса. Устройства не синхронизируют настройки друг с другом.

Прежние настройки в JSON (`dataDir/settings`: `user_preferences.json`, `filters/`, `study_sessions/`) при первом запуске переносятся в БД одной транзакцией (`importLegacySettings`, вызывается из `electron/host/boot.ts`). Отметка `legacy_settings_imported` в таблице `setting` делает перенос одноразовым; записи, уже лежащие в БД, не перезаписываются; битый файл — предупреждение в лог без частичного переноса, перенос повторится после исправления. Файлы остаются на месте и больше не читаются.

Layout берётся из `assets/wireframes-screens.pdf`, палитра — своя. Экраны реализуются по важности; данные — только из контракта `LearningEngine`, поэтому элементы wireframes без данных в движке (серия дней, время, «Reschedule», ИИ-действия) не рисуются.

**Визуальная система.** Цвета — только токены темы Vuetify (`app/providers/vuetify.ts`): акцентный градиент плана дня — токены `hero-start`/`hero-end`, а не hex в компоненте; у карточек нет `variant="outlined"` (он красит рамку в `currentColor` — белую в тёмной теме и почти чёрную в светлой): рамка мягкая, из глобального `VCard`. Заголовки страниц — `PageHeader` (`headline-large`), заголовки секций внутри страницы — `title-large`; отступы у `h1–h6` сброшены глобально (`app/styles/global.css`). Статус несёт значок и нейтральный текст (цвет только у значка): цветной 12-пиксельный текст статуса давал контраст 2.4–3.0:1. У `v-btn` нельзя использовать `block` во flex-колонке (`flex: 1 0 auto` растягивает кнопку): вместо него `w-100`. Настройки — вкладки сверху (`v-tabs`), а не второе боковое меню: контенту хватает ширины при узком окне. «Внешний вид»: тема — радио-группа плиток с образцом (`ThemeTile`: нативные `input type="radio"` — стрелки, `aria-checked` и focus без своего кода; образец рисуется из цветов самой темы, «Как в системе» — диагональ светлой и тёмной), язык — строка «название и описание слева, список справа», как в остальных настройках. Проверено в настоящем Electron: axe без нарушений на «Курсах» и «Внешнем виде», контраст текста ≥ 5.7:1 (светлая) и ≥ 6.3:1 (тёмная), окно 760 px без обрезанных элементов.

**Граф знаний** (`pages/graph`). Уроки выбранных курсов (`getGraph({rootIds: курсы, depth: 1, kinds: ['lesson'], limit: 2000})`) склеиваются с прогрессом (`getProgress({scope: {courseId}})`) в вид-модель (`lib/view.ts`: `buildGraphView`, `applyProgress`). Курс — контейнер-заголовок, узлы — уроки, упражнения не рисуются; рёбра `superseded` скрыты. Раскладка — `@dagrejs/dagre` слева направо (`lib/layout.ts`) **только по рёбрам `dependency`**: `encompassed` поверх пунктиром с подписью веса (переключатель «Показать охват») в ранжирование не идёт. Уроки без зависимостей лежат сеткой под связной частью. Раскладка считается в Web Worker (`lib/layout.worker.ts`, `model/use-layout.ts`): на графе в сотни уроков она занимает сотни миллисекунд и не должна блокировать интерфейс; она зависит только от структуры, поэтому событие `progress` обновляет статусы, оценки и счётчики (`model/graph.ts`) без повторной загрузки графа и без новой раскладки, а `library-reloaded` и `state-rebuilt` перестраивают структуру. Рендер, pan/zoom и `onlyRenderVisibleElements` — `@vue-flow/core`; узлы — Vue-компоненты, тема Vue Flow переопределена токенами Vuetify (`--v-theme-*`). Vue Flow совместим с CSP «запретить всё» (он не создаёт `<style>`, `eval` и воркеров, а стили узлов ставит атрибутами `style`, которые разрешает `style-src 'unsafe-inline'`), поэтому CSP не ослаблена; встроенную английскую подсказку клавиатурной доступности Vue Flow отключает `disable-keyboard-a11y`, вместо неё у узла `role="button"`, `aria-label` из vue-i18n, roving tabindex (в граф входит один Tab) и переход стрелками к ближайшему уроку. Курс берётся из `useCourseScope`, `?course=` выбирает курс при переходе и убирается из адреса. «Учить» ведёт в `session` с `?course=` урока: сессия строится по курсу, отдельного урока в её параметрах нет.

## Курсы и параллельное обучение

Несколько курсов изучаются параллельно и не смешиваются: выбранный курс сужает план дня, повторения и учебную сессию до себя. Курс не «включается» и не «завершается» — прогресс каждого хранится отдельно и не теряется при переключении.

- **Область (scope) — параметр запроса.** `plan.getDay` и `practice.getDue` принимают `courseIds` (пусто или нет поля — все курсы, неизвестный курс — `NOT_FOUND`); вне области упражнения не попадают ни в повторения, ни в новое, ни в закрепление основ. Переключение курса **ничего не пишет в журнал**, поэтому не влияет на другие устройства; для этого не годится blacklist — он журнальный и синхронизируется. Семантика — в `engine-ts/design/engine-ts-api.md` §4.1.
- **Выбранный курс** хранится в настройках движка (`UiSettingsDto.activeCourseId`, `engine.db`) и переживает перезапуск. Пропавший из библиотеки курс сбрасывается на «все курсы» (с записью в настройки), но только если в библиотеке есть курсы: пустая (сломанная) библиотека сохранённый выбор не стирает. `createCourseScope` создаётся в `app/main.ts` до монтирования и раздаётся через `provide`/`useCourseScope`.
- **План дня.** Под заголовком дата и «Всего в плане: N» (дата и план обновляются после полуночи), ниже переключатель курса («Все курсы» и по чипу на курс, с переносом строки; при одном курсе не показывается). Экран — одна колонка: акцентная карточка первого упражнения, затем список «Ближайших» (до пяти, «и ещё N»); у повторений в списке — значок и «запомнено» в процентах (цвет только у значка: цветной 12-пиксельный чип не проходит контраст; для упражнений вне очереди повторений процента нет). Отдельного списка «К повторению» нет: план уже содержит повторения. «Начать сессию» передаёт курс плана в `?course=`, поэтому сессия строится по тому же (`seed`, курс), что виден на экране. Пока курс в фокусе, повторения остальных курсов не подмешиваются, а показаны контурными чипами («Git · 3»): клик переключает на этот курс. Пустой план — одна карточка; в ней те же чипы, а если ждать нечего — кнопка «К курсам». Списки без действий не участвуют в Tab (`tabindex="-1"`), ссылки бокового меню — обычные остановки Tab. В светлой теме `medium-emphasis` — 0.7 (0.6 давало 4.29:1 у подзаголовков). Окно имеет минимальный размер 900×600 (`createWindowOptions`): при меньшей ширине боковое меню оставляет странице меньше 660px.
- **Экран «Курсы»** (образец — Vault из `assets/wireframes-screens.pdf`: карточки в сетке, поиск, списки состояния и сортировки). Колонки сетки считаются по ширине содержимого (`auto-fill, minmax(20rem, 1fr)`), а не окна. Карточка: плитка с инициалом (цвета темы по кругу), название, число уроков и попыток, описание, прогресс — доля освоенных уроков (одна метрика; статус «пройден» — все уроки освоены, поэтому «Освоен» при неполном прогрессе невозможен), состояние и число повторений. Единственная заливная кнопка на экране — у курса в фокусе («План курса») или, пока фокуса нет, у рекомендованного (`recommendCourse`: больше всего повторений → начатый последним → первый неначатый); у остальных «Учить» приглушена. Курс в фокусе выделен рамкой `primary`, вверху «Показывать все курсы» снимает фокус. Карточка «Add New Source» и потоковая загрузка не рисуются (нет данных в движке).
- **Dev-курсы:** `pnpm dev:seed` кладёт в библиотеку SQL-курс `sql_kb`, проверяемый курс `sql_analytics` и `git_kb`, `http_kb`, `js_kb` из `dev-library/`; `pnpm dev:reset` сбрасывает прогресс всех курсов (настройки, включая выбранный курс, остаются).
- **Курсы из git.** «Добавить из Git» на экране «Курсы» (`pages/courses/ui/AddRepositoryDialog.vue`, модель — `model/add-repository.ts`) принимает URL публичного `http(s)`-репозитория и необязательную ветку или тег; индикатор идёт по событиям `repository-progress`, «Отмена» вызывает `repositories.cancel` (id операции берётся из первого события, отмена до него откладывается). «Настройки → Библиотека → Репозитории» (`pages/settings/ui/RepositoriesCard.vue`) показывает URL, ветку, коммит, дату, число курсов и состояние, даёт «Обновить» («Уже актуально», если коммит на сервере совпал) и «Удалить» (прогресс в журнале сохраняется). Общие хелперы — `entities/repository` (проверка URL и ветки, разбор ошибок по `code` и `details.reason`, редьюсер прогресса). Движок (`repositories.*`, `@spirula/engine-git`) держит на диске снимок коммита без `.git` в `<userData>/library/repositories/<id>/`, реестр — в таблице `repository` в `engine.db`; контракт — `engine-ts/design/engine-ts-api.md` §3.1. Приложение ходит в сеть только по действию ученика, автообновления нет.

## Dev-данные

Каталог `userData` dev-запуска — `~/Library/Application Support/@spirula/desktop` (macOS), `$XDG_CONFIG_HOME` или `~/.config/@spirula/desktop` (Linux), `%APPDATA%\@spirula\desktop` (Windows; пути Linux и Windows заданы по документации Electron и не проверялись). Библиотека лежит в `library/`, журнал и настройки — в `data/engine.db`. Другой каталог задаёт `--user-data <каталог>`, например для упакованного приложения (`Spirula`).

- `pnpm dev:seed` — курсы: `sql_kb` (образцовый, фикстура движка), `sql_analytics` и `git_kb`, `http_kb`, `js_kb` из `dev-library/`. `sql_analytics` («SQL: аналитика данных») — «настоящий» курс: 18 уроков, 72 упражнения на двух учебных базах (сотрудники/отделы и магазин), плотный граф `encompassed`, материал к каждому уроку; ответ пишется как `SELECT` и проверяется раннером на фикстуре с эталонным CSV (свои `fixtures/`, `checks/`, `solutions/` лежат внутри каталога курса, `engine-cli validate <каталог> --run-checks` прогоняет эталонные решения). `git_kb`, `http_kb`, `js_kb` — по 3 урока × 3 упражнения с самооценкой, на русском (раннера для Git/HTTP/JS нет). Повторный запуск перезаписывает эти файлы, чужие курсы не трогает. Приложение подхватит курсы при запуске или по «Настройки → Библиотека → Перечитать». Проверка библиотеки: `pnpm -F @spirula/engine engine-cli validate <каталог>`.
- `pnpm dev:reset` — удаляет строки `log_entry`, `log_conflict`, `imported_segment`, `study_session`; `setting`, `saved_filter` и `meta` (id устройства) остаются. Правка БД в обход движка: журнал append-only и синхронизируется, поэтому команда только для dev-данных. Приложение должно быть закрыто: на macOS и Linux скрипт отказывается работать, если `SingletonLock` указывает на живой процесс (на Windows этой проверки нет).

## Смоук

Код смоука (шелл в main, мост в preload, сценарии в renderer, лог раннера в хосте) существует **только в смоук-сборке**: `SPIRULA_SMOKE_BUILD=1 vite build` выставляет через `define` константу `__SPIRULA_SMOKE_BUILD__` в `true` и пишет в `dist-smoke/`. В обычной сборке константа `false`, код за ней вырезается, а все имена смоука собраны в `shared/smoke.ts` и недостижимы: релизный `dist/` и `dist-electron/` не содержат ни `smoke` (без учёта регистра), ни id упражнения сценариев. Это проверяет `test/release-bundle.test.ts`: он сам собирает релизный вариант `vite build` во временный каталог (`SPIRULA_BUILD_OUT`) и ищет маркеры, а для смоук-варианта проверяет, что те же маркеры находятся (детектор не слепой). Сборка в упакованный `.app` идёт только из `dist-smoke/`, штатный `pnpm build` его не касается.

Режим включается `SPIRULA_SMOKE=1` в окружении (и только в смоук-сборке). Запуск — со скрытым окном, временным `userData` и копией библиотеки `sql-course` (`packages/engine/test/fixtures/libraries/sql-course/lib_kb`). Renderer выполняет сценарии через настоящий путь renderer → preload → main → хост → движок и сообщает итог main, тот печатает `SPIRULA_SMOKE_RESULT …` (в том числе `packaged`) и выходит с кодом 0 или 1:

1. `basic` — `library.getInfo`, `recordAttempt`, повторный `recordAttempt` (`duplicate: true`), событие `progress`;
2. `sql` — `beginAttempt` / `submitAnswer` (неверный и верный SQL) / `completeAttempt`; проверку выполняет расширение `spirula.sql` в хосте расширений (воркер раннера порождён из `utilityProcess`);
3. `choice` — то же для расширения `spirula.choice` (`view` содержит варианты, неверный и верный ответ);
4. `renderer` — скрипты элементов ввода (`spirula.sql`, `spirula.choice`) грузятся в renderer по `spirula-ext://` под CSP и CORS `file://` и определяют свои теги (`ensureAnswerElement`);
5. `isolated` — упражнение «враждебного» расширения (`e2e/fixtures/hostile-extension`, копируется в `<userData>/extensions`): проверка идёт в ограниченном процессе, чтение `/etc/hosts`, запись, запуск процесса и поток запрещены, переменная `HOME` не видна. Сценарий и процессный тест `restricted.test.ts` — стражи на случай, если после обновления Electron режим разрешений перестанет применяться;
6. `crash` — убийство хоста, перезапуск супервизором, переподключение клиента, повтор идемпотентного вызова, `duplicate: true` после рестарта (журнал на диске), `progress` после переподключения.

- `pnpm smoke` — смоук-сборка и запуск неупакованного приложения (`electron dist-smoke/dist-electron/main/index.js`).
- `pnpm smoke:packaged` — та же сборка, упакованная `electron-builder --dir` без подписи (`CSC_IDENTITY_AUTO_DISCOVERY=false`) во временный каталог вне репозитория; запускается бинарник `.app`: хосты грузятся из `app.asar`, расширения — из `Resources/extensions` (вне asar), `better-sqlite3` — из `app.asar.unpacked`, воркер раннера SQL стартует с `ELECTRON_RUN_AS_NODE`. Скрипт сверяет `packaged` в отчёте, наличие `app.asar` и `app.asar.unpacked` и после выхода ждёт до 5 с, затем убивает и считает ошибкой любые оставшиеся процессы из каталога упакованного приложения. Проверено на macOS arm64; пути бинарника для Linux и Windows заданы по раскладке electron-builder и не проверялись.
- `--verbose` печатает stderr хоста и main и вывод сборки.

## E2E

`e2e/` — сценарии от лица ученика: настоящий Electron, клики и чтение экрана (Playwright `_electron` под vitest, `vitest.e2e.config.ts`); в корневой `pnpm test` не входят. `pnpm -F @spirula/desktop e2e` сам собирает релизный бандл в `dist-e2e` (`SPIRULA_BUILD_OUT`, `dist` запущенного `pnpm dev` не трогается; `SPIRULA_E2E_SKIP_BUILD=1` переиспользует сборку) и гоняет каждый тест на временном `userData` с теми же курсами, что кладёт `dev:seed`. Приложение запускается с `--user-data-dir` и `--lang=ru` (селекторы — по русским строкам интерфейса), поэтому не конфликтует с dev-запуском. Окна показываются на экране.

- «Проходят дни»: приложение закрывается, `shiftJournalBack` сдвигает `at`/`recorded_at` всех записей `log_entry` временной БД в прошлое, приложение открывается снова — движок видит забывание, план дня заполняется повторениями. Так курс проходится целиком за один прогон.
- Журнал и настройки проверяются прямым чтением `engine.db` (`better-sqlite3`, read-only): число и оценки попыток, `source`, непрерывный `seq`, `ui.activeCourseId`.
- Сценарии: каталог курсов; «Учить» и фокус курса; Git до «Пройден 3 из 3» (оценки «5», с повторами через дни); один проход урока не открывает следующий; оценки «1» возвращаются в план через сутки; SQL и `spirula.choice` — неверный ответ не пишется в журнал, верный пишется с `source=runner`, «Сдаться» даёт оценку 1; пользовательское расширение `acme.echo` (`e2e/fixtures/echo-extension`) грузится с диска через `spirula-ext://`; пользовательская копия `spirula.choice` побеждает расширение из поставки.
- Вклады расширений: темы (`themes.e2e.test.ts`, фикстура `theme-extension`: выбор применяется сразу и переживает перезапуск); Markdown (`markdown.e2e.test.ts`: `math` выводится формулой, неизвестный язык остаётся кодом, сбой рендерера из `bad-markdown-extension` оставляет исходник); правило оценки (`grade-policy.e2e.test.ts`, `policy-extension`: Pass@N по умолчанию, выбранное правило ставит 5 и сохраняется в БД, возврат к встроенному, расширение убрали — предупреждение и оценка по Pass@N).
- Изоляция расширений: `isolation-code.e2e.test.ts` (враждебное расширение без разрешений — чтение, запись, процессы и потоки запрещены, приложение живо; объявленные `process.spawn` и `library.read` работают; «Доверять» снимает ограничения без перезапуска приложения), `isolation-ui.e2e.test.ts` (элемент в `iframe sandbox="allow-scripts"`, ввод, Ctrl+Enter, Tab, тема, рендерер содержимого в рамке, после «Доверять» — без iframe), `extension-settings.e2e.test.ts` (разрешения и метки, переключатели «Включено»/«Доверять», отключение, доверие переживает перезапуск).
- Курсы из Git: `git-courses.e2e.test.ts` (локальный `serveGitRepo` из `@spirula/testkit`, нужен системный `git`): «Добавить из Git» → карточка без перезапуска, снимок без `.git` и строка в `repository` с коммитом, перезапуск, «Обновить» («Уже актуально» и новый коммит), «Удалить»; ошибки адреса, сети, каталога без курсов и занятого id оставляют библиотеку как была; курс в корне репозитория.

## Режим разработчика

`SPIRULA_DEV_EXTENSIONS=<каталог>` в окружении процесса приложения (работает и для `pnpm dev`, и для упакованной сборки) добавляет каталог корнем расширений с происхождением `dev`. Он читается последним и побеждает пользовательский и поставляемый корни при совпадении id; обычно это выходной каталог `spirula-ext build --watch` (`<проект>/dist-ext`, внутри `<id>/extension.json`). Расширения, не прошедшие проверку, видны в «Настройки → Расширения» как `invalid`.

Main наблюдает за каталогом (`fs.watch` с `recursive`). Правка любого файла (кроме имён, начинающихся с `.`, и `node_modules`) перезапускает оба хоста — движок и расширений — и перезагружает все окна (`reloadIgnoringCache`; скрипты `spirula-ext://` отдаются с `Cache-Control: no-cache`). Серия изменений (сборка пишет много файлов) объединяется задержкой 300 мс в один перезапуск. Перезапуск по правке не считается падением: счётчики супервизоров и backoff не меняются, `onFatal` не вызывается. Сессия в окне после перезагрузки начинается заново.

Ограничение: если каталога нет при запуске, в лог пишется предупреждение и наблюдение не включается; каталог, созданный позже, не наблюдается — приложение нужно перезапустить.

Расширение из `SPIRULA_DEV_EXTENSIONS` изолировано так же, как пользовательское, и получает объявленные в манифесте разрешения автоматически. Чтобы на время разработки снять ограничения, включите для него «Доверять» в «Настройки → Расширения» и перезагрузите окно.

## Безопасность

`sandbox: true`, `contextIsolation: true`, `nodeIntegration: false`; навигация запрещена, `window.open` отклоняется; CSP — «запретить всё», скрипты `'self'` и `spirula-ext:`, рамки — `frame-src spirula-ext:` (в dev добавляется websocket для HMR); протокол `spirula-ext` отдаёт только `.js`/`.mjs` из каталога расширения (выход за каталог — 404); расширения не из поставки изолированы: код — в ограниченном процессе (режим разрешений Node — «ремень безопасности», а не граница безопасности), интерфейс — в `iframe sandbox="allow-scripts"`; доверенные расширения и расширения из поставки не ограничены (`docs/design/extensions.md`, «Права и изоляция», «Пределы»); `ipcMain` принимает только от верхнего фрейма; мост не отдаёт `ipcRenderer`; аргументы RPC валидируются zod на хосте.
