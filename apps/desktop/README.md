# @dolphy/desktop

Desktop application: Electron + Vue 3 + Vite. The business-logic layer (`@dolphy-app/engine`) lives in a `utilityProcess`; the UI sees it as `LearningEngine` from `@dolphy-app/engine-contract`. Design: `engine-ts/design/engine-ts-electron.md` (§9–§14).

The build (`vite build`) produces `dist/` (renderer) and `dist-electron/{main,preload,host}`. Preload is built as CJS (`index.cjs`): with `sandbox: true` Electron does not load an ESM preload. The host is an ESM bundle with all workspace packages; only the native `better-sqlite3` stays external (N-API prebuild, `asarUnpack` when packaged). The `ext-host.js` entry (extension host) is built by the same invocation.

**Extensions.** The Vite plugin `dolphy:extensions` builds `packages/ext-*` (`pnpm -F <package> build` → `dist-ext/`) and puts the directories into `<outRoot>/extensions/<id>/` (when packaged — `extraResources` → `Resources/extensions`, outside asar: `import()` and the SQL worker `fork` read real files). User extensions live in `<userData>/extensions/<id>/` and win by `id`. Structure, manifest and API: `docs/design/extensions.md`. CSP allows scripts only from `'self'` and `dolphy-ext:`; the `dolphy-ext` protocol serves `.js`/`.mjs` scripts and the assets `css`, `svg`, `png`, `webp`, `jpg`, `jpeg`, `woff2` (lowercase extension, per-type size ceiling, no symbolic links out of the extension directory or to an asset) from extension directories with the right `Content-Type`, `nosniff` and CORS (the renderer is loaded from `file://`); `extension.json`, `README.md`, `.json`, `.md`, `.txt` and dot-paths are 404. An isolated frame gets a CSP built for its extension: scripts, style sheets, images and fonts only from `dolphy-ext://<its id>`.

**Extension settings and contributions.** "Settings → Appearance": theme tiles from extensions (`themes`) next to the built-in "As in the system", "Light", "Dark". "Settings → Learning": "Grading rule" — the built-in Pass@N or a rule from an extension (`gradePolicies`); a rule failure or a missing extension falls back to Pass@N grading. "Settings → Extensions": a list of extensions (bundled, user, development) with their contributions across eight points and the reason an extension failed to load or is overridden. Code blocks in task Markdown are rendered by content renderers (`markdownRenderers`, e.g. `dolphy.math`); on failure the source text and a note remain.

**Live application of extensions** (`docs/design/extensions.md`, "Live application"). Contributions in the window are a reactive store (`shared/api/engine/contributions.ts`, `createContributionsStore`): read at startup and after every `contributions-changed`; `ContributionsDto.generation` discards a stale response, and after an engine host restart (`connectEngine().onReconnect`) the counter starts over. The store is provided via `CONTRIBUTIONS_KEY` and read reactively (`useContributions()`): Vuetify themes are registered and removed on the fly (`bindExtensionThemes`, `shared/lib/theme-registry.ts`; if the selected theme disappears, "As in the system" applies and the stored value is unchanged), `MarkdownView` re-renders blocks, grading rule parameters are reactive, `AnswerElement` and `IsolatedFrame` are keyed by revision only for `dev` extensions. A trusted extension module is loaded from the `?v=<revision>` URL (`shared/lib/extension-url.ts`). A custom element already defined in the window cannot be replaced: `ensureAnswerElement`/`staleAnswerElements` (`shared/lib/answer-element.ts`) detect this single case, and "Settings → Extensions" shows the banner "The update will apply after the window is reloaded" (`pages/settings/model/reload-required.ts`).

**Extension isolation** (`docs/design/extensions.md`, "Permissions and isolation"). Non-bundled extensions (user ones and those from `DOLPHY_DEV_EXTENSIONS`) are isolated until the user clicks "Trust". Code runs in a restricted child process: the extension host launches `process.execPath` with `ELECTRON_RUN_AS_NODE=1` and the Node permission-mode flags; the process entry is the build artifact `restricted/ext-restricted.mjs` (Vite plugin `dolphy:restricted-child`, `electron/ext-host/restricted-child.ts` → `<outRoot>/restricted/`; when packaged — the entry `{ "from": "restricted", "to": "restricted" }` in `extraResources` in `electron-builder.json`, outside asar: permission mode checks real file paths). The UI (the answer input element and the content renderer) lives in `<iframe sandbox="allow-scripts">`; the frame page is served by the `dolphy-ext` protocol (`/__dolphy/frame.html`); the window CSP contains `frame-src dolphy-ext:`. For non-bundled extensions, "Settings → Extensions" shows the declared permissions, the "Isolated"/"Trusted" label, and the "Enabled" and "Trust (no isolation)" toggles (the state is stored in `engine.db`; it takes effect immediately for code, and for UI, themes and renderers after "Reload window"). Bundled extensions cannot be toggled.

**Extension catalog and installation** (`docs/design/extensions.md`, "Installation and catalog"). "Settings → Extensions" has two tabs, "Installed" and "Catalog" (`pages/settings/ui/InstalledExtensions.vue`, `CatalogExtensions.vue`, dialog `InstallDialog.vue`; models `pages/settings/model/{catalog,install,extensions}.ts`). Catalog: search, quick filter groups ("Learning", "Appearance and interface", "For developers") with counts, a collapsible "More filters" block (contribution kinds and tags; open while any of them is selected; the chips are the shared `FilterChip.vue` toggle button with `aria-pressed`, the counts are part of the accessible name of the group and tag chips), a card with tags, permissions and contributions (a contribution chip shows the title from `titles`, the id is a tooltip and screen-reader text; exercise types and renderer languages stay monospace ids, learning events are localized; a lone theme titled like its extension is not repeated), "Install" → dialog → the result "Installed. The extension is already working." (no reload); on "Installed" — the banner "Updates available: N", "Update"/"Update all", the checkbox "Check for updates at startup", "Delete" (extensions with `user` origin), a revocation warning. The installer lives in the engine process: `electron/host/installer.ts` (`createDesktopInstaller`: global `fetch`, `<userData>/extensions`; `DEFAULT_EXTENSION_CATALOG_URL` is `https://dolphy-app.github.io/dolphy-extensions/index.json`); the window makes no network calls and the CSP is unchanged. Installation, deletion, "Enabled", "Trust" and editing in developer mode are applied on the fly (see "Live application of extensions" above): there is no `window.dolphy.extensions.apply` bridge and no host restart. The background update check at startup runs at most once every 24 hours.

**Extension data, settings and events** (`docs/design/extensions.md`, "Data, settings and events", ADR 0007). An enabled extension with a `settings` point has a "Settings" button in "Settings → Extensions → Installed": a dialog (`pages/settings/ui/ExtensionSettingsDialog.vue`, fields in `ExtensionSettingField.vue`, model `pages/settings/model/extension-settings.ts`) renders a form from the definitions (switch, string, number, list); the value goes to the engine immediately on change, an engine rejection (bounds, length, option) is shown under the field and announced by the screen reader, "Reset" restores defaults, and a running extension sees the change without a reload. The "Data" block in the card (`ExtensionData.vue`, model `model/extension-data.ts`) shows the space used (keys and size) and "Clear data" with confirmation; the delete dialog has the checkbox "Delete extension data" (by default the data stays). The "Learning events" permission (`learning.events`) and the `settings` and `events` points are visible in the install dialog, the catalog card and the installed list. The window reports the end of a session to the engine once (`practice.finishSession`, `pages/session/model/session.ts`).

**Extension commands and panels** (`docs/design/extensions.md`, "Commands", "Panels", ADR 0008). The command palette (`widgets/command-palette`, `features/extension-commands`) is mounted in `App.vue`, so it opens with Ctrl/⌘+K on any page, including a session, and with the "Open command palette" button on the "Settings → Keyboard shortcuts" page (there is no button in the side menu). Search is case-insensitive over the title, category and extension id; the field is a `combobox`, the list is a `listbox` (`aria-activedescendant`), Escape returns focus. The command list comes from reactive contributions (`contributions-changed`), and the selected row is held by the command key. A command runs with a single `extensions.invokeCommand` call (outside the engine queue); `notify` is shown as an app notification (`role="status"`), `openPanel` opens a panel, an error is shown as a message, and extension text is rendered as plain text. Extension panels are the "Extension panels" group in the side menu and the page `/ext/:extensionId/:panelId` (`pages/extension-panel`): "Back", an `h1` that takes focus on entry, a full-height frame; a missing panel shows an empty state with a link to the daily plan. The panel frame is the same `PanelFrame.vue` and `frame-bridge.ts` as for the input element, in `panel` mode: `iframe sandbox="allow-scripts"` even for a trusted extension; the app sets the height (the runtime does not send `size`); the app binds the frame to the extension (`PanelBinding`), and the identifier in the message is not read; `ctx.call` allows up to 20 calls per second and 4 concurrent, with a 15 s timeout; only Ctrl/⌘+K (`shortcut`) is forwarded to the parent. The frame is keyed `extensionId:panelId:revision`, so an extension update recreates it without reloading the window.

## Command registry

One reactive registry (`shared/lib/command-registry.ts`, ADR 0012) holds the commands of the app and of extensions. The palette, the shortcut dispatcher and "Settings → Keyboard shortcuts" read only the registry. Keys are `app:<id>` and `extension:<extensionId>:<id>`; a duplicate key throws. Extensions cannot call app commands: a command result is `none`, `notify`, `openPanel` or `data`, and none of them reaches the registry.

Add an app command in `features/app-commands/model/app-commands.ts` (titles and categories are getters, so they follow the language):

```ts
registry.register({
  key: 'app:go:graph',
  source: 'app',
  title: () => t('appCommands.go.graph'),
  category: () => t('appCommands.category.go'),
  keybinding: 'Mod+3', // optional; app commands only
  run: () => router.push({ name: ROUTE.graph }),
});
```

Dynamic sets use `syncCommands(registry, () => [{ descriptor, revision }])` (themes of extensions). Add `ru` and `en` messages for the title and category.

Shortcut rules (`shared/lib/shortcut-dispatcher.ts`, one `keydown` listener on `document` mounted in `App.vue`): Ctrl/⌘+K opens the palette everywhere, including text fields and, via the frame's `shortcut` message, extension panels. Other shortcuts (always with `Mod`) run only when the focus is not in an input, textarea, select or editable element, no dialog or menu is open, the key is not repeating, and the event did not come from an extension frame (a frame forwards only Ctrl/⌘+K). `preventDefault` is called only for a handled shortcut. Shortcuts are set in code and are not user-configurable yet.

## UI

The UI follows Feature-Sliced Design (`app` → `pages` → `widgets` → `features` → `entities` → `shared`; `features` and `entities` are introduced when code is needed by several screens: the selected course is read by the daily plan and "Courses", course data by the switcher and "Courses"). The `@` alias points to `src`. Components are Vuetify 4, with an "indigo + teal" theme (light and dark). The renderer is loaded via `file://`, so the router uses hash history. CSP allows fonts (`font-src 'self' data:`) — without this the MDI icons do not load.

**Localization** — `vue-i18n` (Composition API), languages `ru` and `en`. Messages live in the slice (`pages/<slice>/i18n/{ru,en,index}.ts`), shared ones in `shared/i18n`, the shell ones in `app/i18n`; `app/i18n/messages.ts` assembles the catalog, `app/i18n/vue-i18n.d.ts` types the keys from the `ru` catalog (a typo in `t('…')` is a `vue-tsc` error, and `en: typeof ru` keeps the key sets in sync). Russian plural forms have four variants `zero | one | few | many` (`russianPluralRule`), English has three. Language and theme are chosen in "Settings → Appearance"; `system` takes the system language (an unsupported one falls back to English). Vuetify's built-in strings come from the same catalog (the `createVueI18nAdapter` adapter). Engine data is not translated: course, lesson and exercise titles, runner `feedback`, engine error texts.

**Settings storage** — in `engine.db` (SQLite), not in files and not in `localStorage`: scheduler options (only differences from the defaults), preferences, saved filters and sessions, UI theme and language. Devices do not sync settings with each other.

Legacy JSON settings (`dataDir/settings`: `user_preferences.json`, `filters/`, `study_sessions/`) are migrated into the DB in one transaction on first launch (`importLegacySettings`, called from `electron/host/boot.ts`). The `legacy_settings_imported` marker in the `setting` table makes the migration one-time; records already in the DB are not overwritten; a corrupt file produces a log warning with no partial migration, and the migration repeats after the file is fixed. The files stay in place and are no longer read.

Layout is taken from `assets/wireframes-screens.pdf`; the palette is our own. Screens are implemented in order of importance; data comes only from the `LearningEngine` contract, so wireframe elements without data in the engine (day streak, time, "Reschedule", AI actions) are not drawn.

**Visual system.** Colors are only Vuetify theme tokens (`app/providers/vuetify.ts`): the daily plan's accent gradient uses the `hero-start`/`hero-end` tokens, not hex in a component; cards have no `variant="outlined"` (it paints the border in `currentColor` — white in the dark theme and almost black in the light one): the border is soft, from the global `VCard`. Page headings are `PageHeader` (`headline-large`), section headings within a page are `title-large`; margins on `h1–h6` are reset globally (`app/styles/global.css`). Status is conveyed by an icon and neutral text (color only on the icon): colored 12-pixel status text gave a contrast of 2.4–3.0:1. `v-btn` must not use `block` in a flex column (`flex: 1 0 auto` stretches the button): use `w-100` instead. Settings use tabs on top (`v-tabs`) rather than a second side menu: the content keeps enough width in a narrow window. "Appearance": the theme is a radio group of tiles with a swatch (`ThemeTile`: native `input type="radio"` — arrows, `aria-checked` and focus without custom code; the swatch is drawn from the theme's own colors, and "As in the system" is a diagonal of light and dark), the language is a row with "title and description on the left, list on the right", like the other settings. Verified in real Electron: axe reports no violations on "Courses" and "Appearance", text contrast is ≥ 5.7:1 (light) and ≥ 6.3:1 (dark), and a 760 px window has no clipped elements.

**Knowledge graph** (`pages/graph`). Lessons of the selected courses (`getGraph({rootIds: courses, depth: 1, kinds: ['lesson'], limit: 2000})`) are merged with progress (`getProgress({scope: {courseId}})`) into a view model (`lib/view.ts`: `buildGraphView`, `applyProgress`). A course is a header-less container frame (its title and "Lessons mastered: N of M" are in the toolbar above the canvas), nodes are lessons, exercises are not drawn; `superseded` edges are hidden. The layout is `@dagrejs/dagre` left to right (`lib/layout.ts`) **by `dependency` edges only**: `encompassed` edges are drawn on top as dashed lines with a weight label (the "Show coverage" toggle) and do not take part in ranking. Lessons without dependencies are laid out in a grid under the connected part. The layout is computed in a Web Worker (`lib/layout.worker.ts`, `model/use-layout.ts`): on a graph of hundreds of lessons it takes hundreds of milliseconds and must not block the interface; it depends only on structure, so a `progress` event updates statuses, grades and counters (`model/graph.ts`) without reloading the graph and without a new layout, while `library-reloaded` and `state-rebuilt` rebuild the structure. Rendering, pan/zoom and `onlyRenderVisibleElements` come from `@vue-flow/core`; nodes are Vue components, and the Vue Flow theme is overridden with Vuetify tokens (`--v-theme-*`). Vue Flow is compatible with the "deny everything" CSP (it creates no `<style>`, `eval` or workers, and sets node styles through `style` attributes, which `style-src 'unsafe-inline'` allows), so the CSP is not weakened; Vue Flow's built-in English keyboard-accessibility hint is disabled with `disable-keyboard-a11y`, and in its place a node has `role="button"`, an `aria-label` from vue-i18n, roving tabindex (one Tab enters the graph) and arrow-key navigation to the nearest lesson. The course comes from `useCourseScope`; `?course=` selects the course on navigation and is removed from the URL. "Learn" leads to `session` with the lesson's `?course=`: the session is built per course, and a single lesson is not among its parameters.

The graph shows **one course**: its course switcher has no "All courses" chip (`CourseScopeSwitcher` with `allow-all="false"`), because several courses in a row shrink to an unreadable zoom and dependencies between courses are not drawn (they are listed in the lesson panel). While the saved scope is "all courses", the graph takes the course with the latest attempt, otherwise the first one (`lib/course.ts`: `pickGraphCourse`), and leaves the setting untouched; picking a chip writes it like on the other screens. The course title and counter, the status legend and the zoom buttons live in a toolbar above the canvas rather than over it: floating panels covered nodes and swallowed mouse and focus, and a header inside the course frame scrolled out of view when panning. The screen height is the rest of the window below the page header (`min-height: 100vh`; the canvas takes the remainder, at least 20rem). A node shows the grade as a number next to the bar ("3.9 / 5"): the bar is the grade out of five, not the share up to the threshold, so a "Mastered" lesson can show a partial bar.

## Courses and parallel learning

Several courses are studied in parallel and are not mixed: the selected course narrows the daily plan, reviews and the study session to itself. A course is not "enabled" or "completed" — each one's progress is stored separately and is not lost when switching.

- **Scope is a query parameter.** `plan.getDay` and `practice.getDue` accept `courseIds` (empty or absent — all courses, an unknown course — `NOT_FOUND`); outside the scope, exercises appear neither in reviews, nor in new material, nor in reinforcing the basics. Switching the course **writes nothing to the journal**, so it does not affect other devices; a blacklist is unsuitable for this because it is journaled and synced. Semantics: `engine-ts/design/engine-ts-api.md` §4.1.
- **The selected course** is stored in engine settings (`UiSettingsDto.activeCourseId`, `engine.db`) and survives a restart. A course that disappears from the library is reset to "all courses" (with a write to settings), but only if the library has courses: an empty (broken) library does not erase the saved choice. `createCourseScope` is created in `app/main.ts` before mounting and provided through `provide`/`useCourseScope`.
- **Daily plan.** Under the heading are the date and "Total in plan: N" (the date and plan refresh after midnight), then the course switcher ("All courses" and one chip per course, wrapping; hidden when there is only one course). The screen is one column: an accent card for the first exercise, then a list of "Up next" (up to five, "and N more"); review items in the list have an icon and "remembered" as a percentage (color only on the icon: a colored 12-pixel chip fails contrast; exercises outside the review queue have no percentage). There is no separate "To review" list: the plan already contains reviews. "Start session" passes the plan's course in `?course=`, so the session is built from the same (`seed`, course) that is visible on screen. While a course is in focus, reviews of other courses are not mixed in but shown as outlined chips ("Git · 3"): a click switches to that course. An empty plan is a single card; it has the same chips, and if there is nothing to wait for — a "To courses" button. Lists without actions do not take part in Tab (`tabindex="-1"`), and side menu links are ordinary Tab stops. In the light theme `medium-emphasis` is 0.7 (0.6 gave 4.29:1 on subheadings). The window has a minimum size of 900×600 (`createWindowOptions`): at a smaller width the side menu leaves the page under 660px.
- **The "Courses" screen** (modeled on Vault from `assets/wireframes-screens.pdf`: cards in a grid, search, state and sorting lists). Grid columns are computed from the content width (`auto-fill, minmax(20rem, 1fr)`), not the window. A card has: a tile with an initial (theme colors in rotation), the title, the number of lessons and attempts, a description, progress — the share of mastered lessons (a single metric; the "completed" status means all lessons are mastered, so "Mastered" with incomplete progress is impossible), the state and the number of reviews. The only filled button on the screen belongs to the course in focus ("Course plan") or, while there is no focus, to the recommended one (`recommendCourse`: most reviews → most recently started → first unstarted); on the others "Learn" is muted. The course in focus is highlighted with a `primary` border, and "Show all courses" at the top clears the focus. The "Add New Source" card and streaming upload are not drawn (no data in the engine).
- **Dev courses:** `pnpm dev:seed` puts the SQL course `sql_kb`, the verifiable course `sql_analytics`, and `git_kb` and `http_kb` from `dev-library/` into the library; `pnpm dev:reset` resets the progress of all courses (settings, including the selected course, remain).
- **Courses from git.** "Add from Git" on the "Courses" screen (`pages/courses/ui/AddRepositoryDialog.vue`, model `model/add-repository.ts`) accepts the URL of a public `http(s)` repository and an optional branch or tag; the indicator follows `repository-progress` events, and "Cancel" calls `repositories.cancel` (the operation id is taken from the first event, and a cancel before it is deferred). "Settings → Library → Repositories" (`pages/settings/ui/RepositoriesCard.vue`) shows the URL, branch, commit, date, number of courses and state, and offers "Update" ("Already up to date" if the server commit matched) and "Delete" (progress in the journal is kept). Shared helpers are in `entities/repository` (URL and branch validation, error parsing by `code` and `details.reason`, the progress reducer). The engine (`repositories.*`, `@dolphy-app/engine-git`) keeps a commit snapshot without `.git` on disk in `<userData>/library/repositories/<id>/`, and the registry in the `repository` table in `engine.db`; the contract is in `engine-ts/design/engine-ts-api.md` §3.1. The app goes to the network only on a learner's action; there are no automatic updates.
- **Course library:** the open repository [`dolphy-app/dolphy-courses`](https://github.com/dolphy-app/dolphy-courses) holds the ready-made courses. Add it with "Add from Git" (`https://github.com/dolphy-app/dolphy-courses`): the `javascript` course ("JavaScript: language", 93 lessons, multiple-choice questions and tasks checked by the `dolphy.js` runner) appears in the catalog. The course carries its tests inside the exercise front matter, so it works from `<libraryRoot>/repositories/<id>/`.

## Dev data

The `userData` directory of a dev run is `~/Library/Application Support/@dolphy/desktop` (macOS), `$XDG_CONFIG_HOME` or `~/.config/@dolphy/desktop` (Linux), `%APPDATA%\@dolphy\desktop` (Windows; the Linux and Windows paths follow the Electron documentation and has not been verified). The library lives in `library/`, the journal and settings in `data/engine.db`. A different directory is set with `--user-data <directory>`, for example for the packaged app (`Dolphy`).

- `pnpm dev:seed` — courses: `sql_kb` (the reference one, an engine fixture), `sql_analytics`, and `git_kb` and `http_kb` from `dev-library/`. `sql_analytics` ("SQL: data analytics") is a "real" course: 18 lessons, 72 exercises on two practice databases (employees/departments and a shop), a dense `encompassed` graph, and material for every lesson; the answer is written as a `SELECT` and checked by the runner against a fixture with a reference CSV (its own `fixtures/`, `checks/`, `solutions/` live inside the course directory, and `engine-cli validate <directory> --run-checks` runs the reference solutions). `git_kb`, `http_kb`, `js_smoke` are 3 lessons × 3 exercises each with self-assessment, in Russian (there is no runner for Git/HTTP/JS). A repeated run overwrites these files and does not touch other courses. The app picks up the courses at startup or via "Settings → Library → Rescan". Library validation: `pnpm -F @dolphy-app/engine engine-cli validate <directory>`.
- `pnpm dev:reset` — deletes the rows of `log_entry`, `log_conflict`, `imported_segment`, `study_session`; `setting`, `saved_filter` and `meta` (device id) remain. This edits the DB bypassing the engine: the journal is append-only and synced, so the command is for dev data only. The app must be closed: on macOS and Linux the script refuses to run if `SingletonLock` points to a live process (Windows has no such check).

## Smoke

The smoke code (a shell in main, a bridge in preload, scenarios in the renderer, the runner log in the host) exists **only in the smoke build**: `DOLPHY_SMOKE_BUILD=1 vite build` sets the constant `__DOLPHY_SMOKE_BUILD__` to `true` through `define` and writes to `dist-smoke/`. In a normal build the constant is `false`, the code behind it is stripped, and all smoke names are collected in `shared/smoke.ts` and unreachable: the release `dist/` and `dist-electron/` contain neither `smoke` (case-insensitive) nor the scenarios' exercise ids. This is verified by `test/release-bundle.test.ts`: it builds the release variant with `vite build` into a temporary directory (`DOLPHY_BUILD_OUT`) itself and searches for the markers, and for the smoke variant checks that the same markers are found (the detector is not blind). The build into the packaged `.app` comes only from `dist-smoke/`; the regular `pnpm build` does not touch it.

The mode is enabled by `DOLPHY_SMOKE=1` in the environment (and only in the smoke build). It runs with a hidden window, a temporary `userData`, and a copy of the `sql-course` library (`packages/engine/test/fixtures/libraries/sql-course/lib_kb`). The renderer runs the scenarios through the real path renderer → preload → main → host → engine and reports the result to main, which prints `DOLPHY_SMOKE_RESULT …` (including `packaged`) and exits with code 0 or 1:

1. `basic` — `library.getInfo`, `recordAttempt`, a repeated `recordAttempt` (`duplicate: true`), a `progress` event;
2. `sql` — `beginAttempt` / `submitAnswer` (wrong and correct SQL) / `completeAttempt`; the check is performed by the `dolphy.sql` extension in the extension host (the runner worker is spawned from a `utilityProcess`);
3. `choice` — the same for the `dolphy.choice` extension (`view` contains the options, a wrong and a correct answer);
4. `js` — the same for the `dolphy.js` extension (a one-exercise `js_smoke` course written by `scripts/smoke.mjs`; `view` contains only the starter, a wrong and a correct solution; the check runs in a child process forked from the extension host);
5. `renderer` — the input element scripts (`dolphy.sql`, `dolphy.choice`, `dolphy.js`) are loaded in the renderer via `dolphy-ext://` under CSP and `file://` CORS and define their tags (`ensureAnswerElement`);
6. `isolated` — an exercise of a "hostile" extension (`e2e/fixtures/hostile-extension`, copied into `<userData>/extensions`): the check runs in a restricted process; reading `/etc/hosts`, writing, spawning a process and threads are forbidden, and the `HOME` variable is not visible. This scenario and the process test `restricted.test.ts` are guards in case permission mode stops being applied after an Electron update;
7. `crash` — killing the host, restart by the supervisor, client reconnection, a retry of an idempotent call, `duplicate: true` after the restart (the journal is on disk), `progress` after reconnection.

- `pnpm smoke` — smoke build and a run of the unpackaged app (`electron dist-smoke/dist-electron/main/index.js`).
- `pnpm smoke:packaged` — the same build, packaged by `electron-builder --dir` without signing (`CSC_IDENTITY_AUTO_DISCOVERY=false`) into a temporary directory outside the repository; the `.app` binary is launched: the hosts load from `app.asar`, extensions from `Resources/extensions` (outside asar), `better-sqlite3` from `app.asar.unpacked`, and the SQL runner worker starts with `ELECTRON_RUN_AS_NODE`. The script checks `packaged` in the report, the presence of `app.asar` and `app.asar.unpacked`, and after exit waits up to 5 s, then kills and treats as an error any remaining processes from the packaged app's directory. Verified on macOS arm64 and on Linux x64 (xvfb) in CI (`.github/workflows/desktop-checks.yml`); the Windows binary path follows the electron-builder layout and has not been verified.
- `--verbose` prints the stderr of the host and main and the build output.

## E2E

`e2e/` holds scenarios from the learner's point of view: real Electron, clicks and reading the screen (Playwright `_electron` under vitest, `vitest.e2e.config.ts`); they are not part of the root `pnpm test`. `pnpm -F @dolphy/desktop e2e` itself builds the release bundle into `dist-e2e` (`DOLPHY_BUILD_OUT`; the `dist` of a running `pnpm dev` is not touched; `DOLPHY_E2E_SKIP_BUILD=1` reuses the build) and runs each test on a temporary `userData` with the same courses that `dev:seed` puts in place. The app is launched with `--user-data-dir` and `--lang=ru` (selectors use the Russian UI strings), so it does not conflict with a dev run. Windows are shown on screen. On macOS the run holds `caffeinate -i -s` (`e2e/global-setup.ts`) so the machine cannot go to sleep mid-scenario: after waking, the vitest and Playwright timers count the slept time, and the test in progress fails with a timeout after ~16 minutes of wall time.

## Developer mode

`DOLPHY_DEV_EXTENSIONS=<directory>` in the app process environment (works for both `pnpm dev` and a packaged build) adds the directory as an extension root with `dev` origin. It is read last and wins over the user and bundled roots on an id match; usually this is the output directory of `dolphy-ext build --watch` (`<project>/dist-ext`, with `<id>/extension.json` inside). Extensions that fail validation are visible in "Settings → Extensions" as `invalid`.

`DOLPHY_APP_VERSION=x.y.z` sets the app version in an unbuilt mode (`pnpm dev`, e2e): otherwise the extensions' `minAppVersion` check is not performed. In a packaged build the variable is ignored and the app supplies the version.

`DOLPHY_EXTENSION_CATALOG_URL=<catalog address>` overrides the extension catalog address (`http(s)`; `index.v2.json` is read next to it). It is read only in an unpackaged app (`pnpm dev`, e2e); in a packaged build it is ignored and the official one is used. An invalid value produces a warning in the engine log and the official address. For a local catalog: `dolphy-ext catalog build --src <src> --ids <id> --out <site>`, a static server over `<site>`, and `DOLPHY_EXTENSION_CATALOG_URL=http://localhost:<port>/index.json pnpm dev` (see `docs/design/extensions.md`, "Development setup").

Main watches the directory (`fs.watch` with `recursive`). An edit to any file (except names starting with `.` and `node_modules`) sends the engine host a `reload-extensions` message: the engine re-reads the set, the extension host replaces it, and the window receives `contributions-changed`. Hosts are not restarted and the window is not reloaded (`dolphy-ext://` scripts are served with `Cache-Control: no-cache`, and the window's modules carry a file revision in the URL). A series of changes (a build writes many files) is merged by a 300 ms delay into a single application; while the engine host is starting, the request is repeated after `ready`. An open session stays: mounted input elements of extensions with `dev` origin are recreated (the element's state may be lost), and `dev` content blocks are rendered again.

Limitation: if the directory does not exist at startup, a warning is logged and watching is not enabled; a directory created later is not watched — the app must be restarted.

An extension from `DOLPHY_DEV_EXTENSIONS` is isolated the same way as a user one and automatically receives the permissions declared in the manifest. To lift the restrictions during development, enable "Trust" for it in "Settings → Extensions": the change takes effect immediately.

**DevTools of the extension frames.** While `DOLPHY_DEV_EXTENSIONS` is set — in any build, packaged ones included — `F12`, `Cmd+Alt+I` (macOS) and `Ctrl+Shift+I` toggle DevTools of the main window (`electron/main/shells/devtools-shortcut.ts`: subscribes to `before-input-event` of every created window and calls `webContents.toggleDevTools()`; the key is swallowed so the page does not see it). The app sets no menu, so there is no menu item. Without the variable the shell registers nothing and a packaged build has no DevTools, as before; `pnpm dev` keeps opening them at start (`window.ts`). Extension frames (answer views, panels, markdown blocks) are `<iframe>`s of `dolphy-ext://<id>/__dolphy/frame.html`: they are listed in the console context selector ("top" drop-down) and in "Elements" under that address; a bundle built by `dolphy-ext build --watch` carries an inline source map, so "Sources" shows the extension's TypeScript. The unit test is `test/devtools-shortcut.test.ts`; e2e does not cover it (an open DevTools window would break the "e2e without focus capture" rule), so check by hand:

1. `dolphy-ext dev <project>` in a project that has a view or a panel (or `DOLPHY_DEV_EXTENSIONS=<project>/dist-ext <Dolphy executable>`).
2. Open a page with the extension's view or panel and press `F12` (or the combination of your platform): DevTools of the main window open, the same key closes them.
3. In the console, pick the context `dolphy-ext://<id>/__dolphy/frame.html`; `document.title` or a `console.log` from your view code is evaluated in the frame. In "Sources" find `src/index.ts` of the project and set a breakpoint.
4. Quit the app, start it without `DOLPHY_DEV_EXTENSIONS`: the keys do nothing.

## Safe mode and extension health

**Safe mode** starts the app without third-party code (`docs/design/extensions.md`, "Diagnostics and safe mode"). Turn it on with the `--safe-mode` launch flag, with `DOLPHY_SAFE_MODE=1` in the environment, or with the "Safe mode" switch in "Settings → Extensions" (stored in `engine.db` as `extensions.safeMode`). Main reads the flag and the variable (`electron/main/safe-mode.ts`, the flag wins) and passes them to the engine as `EngineConfig.forceSafeMode`. In the mode every extension that is not bundled (user and `DOLPHY_DEV_EXTENSIONS` ones) is `disabled` with the `safe-mode` diagnostic, contributes nothing and its code does not run; bundled extensions work, installing and removing still work. A banner at the top of every window (`app/layouts/SafeModeBanner.vue`) says so. When only the setting is on, the banner has a "Turn off safe mode" button and the extensions load at once, without a restart; when the flag or the variable is on, there is no button and the banner says what to remove.

**Extension health.** "Settings → Extensions" shows, per extension, the failures since the app started (a failed command, event handler or exercise type), the last reason and "Paused until HH:MM" when the restricted process crashed five times in a minute. Health is kept in memory and resets when the extension files change. The extension host (`electron/main/ext-supervisor.ts`) is restarted with a backoff after a crash; after `MAX_CRASHES` crashes in a minute it stops, the page shows "The extension host stopped after repeated failures" and the "Restart host" button starts it again (`ExtSupervisor.reset()`).

## Logs and limits

Main, the engine host and the extension host write one rotating **file log**: `<userData>/logs/dolphy-YYYY-MM-DD[.N].log`, one JSON record per line (`level`, `source` = `main` | `engine` | `ext-host`, `message`, `at`, plus the record's fields such as `extensionId`). Only main writes it (`electron/main/log-file.ts`): the engine and extension host `utilityProcess`es are forked with `stdio: 'pipe'`, main reads their stderr line by line, normalizes it, appends it to the file and repeats the output on its own stderr and stdout, so the developer output and `pnpm smoke` see the same lines as before. A new file starts every local day and at 2 MiB; at startup and at every file change files older than 7 days are deleted, then the oldest ones while the total exceeds 10 MiB (the current file is never deleted). A failed write never crashes the app.

"Settings → Extensions" has a **Log** button (general, and a per-row action that presets the extension filter): the last 500 records, newest at the bottom, filtered by extension id and minimum level (`extensions.readLogs`, contract 17; the engine gets the directory as `EngineConfig.logsDir`). **Copy diagnostics** puts an English technical report on the clipboard through main (`platform.copyText`): app, contract, engine, Electron, Chrome and Node versions, platform, safe mode and host state, and every extension (id, version, origin, state, diagnostic codes, isolation, health). Home-directory paths are replaced with `~`; library content, learning data, setting values and extension storage are never included, and nothing is sent anywhere.

A restricted extension process is limited: its stdout/stderr reach the log at most 64 KiB per minute (one `output truncated` record with the dropped byte count closes the window), and a message over 1 MiB or more than 200 messages per second kill the process (`error` record with reason `ipc-size` or `ipc-rate`, the same reason as the last failure in the extension's health; the next call starts a new process that counts toward the crash loop). `ctx.logger` of trusted and bundled extensions carries `extensionId` too (`docs/design/extensions.md`, "Журнал и пределы").

## Security

`sandbox: true`, `contextIsolation: true`, `nodeIntegration: false`; navigation is forbidden, `window.open` is rejected; CSP is "deny everything", scripts `'self'` and `dolphy-ext:`, frames `frame-src dolphy-ext:` (in dev a websocket for HMR is added); the `dolphy-ext` protocol serves only scripts (`.js`/`.mjs`) and assets (`css`, `svg`, `png`, `webp`, `jpg`, `jpeg`, `woff2`) from the extension directory (escaping the directory, a symbolic link out of it, a manifest or README yields 404; the window CSP `style-src`/`img-src`/`font-src` are not widened); each frame's own CSP names only its `dolphy-ext://<id>`; non-bundled extensions are isolated: code runs in a restricted process (Node permission mode is a "seat belt", not a security boundary), the UI in `iframe sandbox="allow-scripts"`; trusted and bundled extensions are unrestricted (`docs/design/extensions.md`, "Permissions and isolation", "Limits"); `ipcMain` accepts messages only from the top frame; the bridge does not expose `ipcRenderer`; RPC arguments are validated by zod on the host.

The main process follows the Electron security checklist for every `webContents`, not only the main window: all session permission requests and checks are denied, and navigation (`will-navigate`, `will-frame-navigate`; only a reload of the main frame's current address and the first load of an extension frame page into an empty subframe are allowed), `window.open` and `<webview>` are blocked. Pages of extension frames additionally carry a `Permissions-Policy` header that disables sensors, camera, microphone, geolocation, USB and similar features.

### Packaging fuses

`electron-builder.json` (`electronFuses`) sets the Electron fuses of the packaged app before signing; for unsigned macOS arm64 builds the ad-hoc signature is reset so the app still launches:

| Fuse                                    | State | Why                                                                                                                                                                                                                         |
| --------------------------------------- | ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `RunAsNode`                             | on    | The restricted extension process and the `ext-sql` / `ext-js` workers run as `process.execPath` with `ELECTRON_RUN_AS_NODE=1`                                                                                               |
| `EnableNodeOptionsEnvironmentVariable`  | off   | `NODE_OPTIONS` is ignored                                                                                                                                                                                                   |
| `EnableNodeCliInspectArguments`         | off   | `--inspect` and friends are ignored                                                                                                                                                                                         |
| `OnlyLoadAppFromAsar`                   | on    | The app code is loaded only from `app.asar`                                                                                                                                                                                 |
| `EnableEmbeddedAsarIntegrityValidation` | on    | `app.asar` is validated on load (macOS, Windows)                                                                                                                                                                            |
| `GrantFileProtocolExtraPrivileges`      | on    | The renderer is loaded from `file://` inside `app.asar`; with the fuse off the window fails with `ERR_FILE_NOT_FOUND` (checked on the packaged app). Serving the renderer from a custom protocol would allow turning it off |

`pnpm smoke:packaged` reads the fuse wire from the built app with `@electron/fuses` (`getCurrentFuseWire`), prints it and fails with the list of mismatching fuses if it differs from the table above; the `isolated` and `sql` scenarios then run on the packaged build.
