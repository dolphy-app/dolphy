# 0001. Виды заданий — расширения-каталоги в отдельном процессе

## Контекст

Проверка ответов была закрытым портом `Verifier` с единственной реализацией (SQL) и закрытыми union'ами в контракте (`SubmissionDto`, `FailedReason`, `ErrorReason`, `ExerciseContentDto`). Новый вид задания (выбор, перетаскивание, сопоставление) требовал правок движка, контракта и UI. Нужна расширяемость в стиле VS Code: виды задаются данными и кодом снаружи ядра, в том числе пользователем.

## Решение

Мы делаем каждый вид задания расширением: каталогом с `extension.json`, кодом проверки (`main.mjs`), элементом ввода ответа (`view.mjs`) и JSON Schema для `spec` и ответа. Ядро знает конверт «вид + spec + ответ → вердикт» (порт `ExerciseTypes`), причины вердикта — открытые строки, данные расширения — `data`. Код расширений исполняется в отдельном `utilityProcess`; движок вызывает `project`/`grade`/`referenceAnswer` по RPC с дедлайном и обработкой падений. Виды по умолчанию (`spirula.sql`, `spirula.choice`) — такие же каталоги, поставляемые вне кода приложения; пользовательские лежат в `<userData>/extensions` и побеждают по `id`. Манифест — отдельный `extension.json`, а не `package.json`. Контракт `@spirula-app/engine-contract` поднят до версии 2.

## Рассмотренные варианты

- Закрытый набор видов в коде движка (`TaskKind` со zod-схемами) — новый вид требует правки репозитория, расширяемость нулевая.
- Расширения в процессе движка — сбой или зависание расширения роняет движок и журнал.
- Хост расширений как `child_process.fork` из движка — то же по изоляции, но выбран `utilityProcess` под управлением main: единая супервизия и перезапуск.
- `package.json` как манифест — связывает рантайм с семантикой npm; выбран отдельный файл, установка — копирование каталога.
- Встроенные виды внутри приложения — не проверяют, что интерфейс не подогнан под SQL, и не дают пользователю заменить вид.

## Последствия

- Любой новый вид задания — расширение; менять движок и контракт не нужно. Схемы `spec` и ответа — JSON Schema, проверяются Ajv в процессе движка без запуска кода расширения.
- Оценка FSRS остаётся за ядром (`GradePolicy` по `outcome`); расширение оценку не выставляет.
- Ключи ответов не уходят в renderer: там только `view` от `project`.
- Пользовательский код исполняется без песочницы и прав, а его renderer-часть — в общем JS-контексте приложения; безопасность держится на доверии к каталогу расширений. Изоляция потребует замены слоя `ExerciseAnswer.vue` (`iframe sandbox`) и системы прав.
- Новые точки вклада (`contributes`) добавляются совместимо: неизвестные ключи отклоняются, `apiVersion` не меняется, пока манифест только растёт.
- Расширение из поставки и пользовательское с тем же `id` расходятся по версиям без релиза приложения; ответственность за совместимость — на авторе копии.
- Журнал синхронизируется между устройствами: попытка по виду, которого нет на устройстве, в UI остаётся недоступной (`EXERCISE_TYPE_UNAVAILABLE`), запись журнала при этом не теряется.
- Скачивание и установка расширений не входят; формат каталога для них пригоден.

## Проверка

`packages/extension-host` (тесты процесса, дедлайна, перекрытия), `apps/desktop/test/release-bundle.test.ts` (расширения по умолчанию собираются и находятся), `pnpm smoke`, `pnpm -F @spirula/desktop e2e` (пользовательское расширение и переопределение по `id`).
