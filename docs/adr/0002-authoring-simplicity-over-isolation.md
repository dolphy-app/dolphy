# 0002. Простота автора и установки важнее изоляции сторонних расширений

Один ADR — одно решение. Дополняет ADR 0001 (виды заданий — расширения-каталоги в отдельном процессе); не отменяет его.

## Контекст

Исследование `docs/research/extension-systems.md` сравнило VS Code, Theia, Hyper, Obsidian, Joplin и Figma. Владелец продукта задал приоритеты: расширение должно быть максимально легко писать и понимать (в том числе сторонним разработчикам платформы) и максимально легко ставить (в будущем — каталог/маркетплейс); безопасность сторонних расширений сознательно вторична; копировать модель доверия VS Code (доверенный код + Marketplace) не нужно.

## Решение

Мы берём форму расширения по образцу Obsidian, а ядро оставляем как есть: хост расширений в отдельном `utilityProcess` (защита от зависаний и падений, не мера безопасности).
- Минимальный манифест и соглашения вместо конфигурации: умолчания `main`, `renderer`, `element`; схемы можно писать прямо в манифесте.
- Автор пишет на SDK (`@dolphy-app/extension-sdk`: `defineExtension`, `defineAnswerElement`, помощники тестов), собирает и проверяет одинаковыми инструментами с нами (`dolphy-ext build`, `dolphy-ext validate`), стартует из шаблона (`create-dolphy-extension`), разрабатывает с перезагрузкой (`DOLPHY_DEV_EXTENSIONS`).
- Единица установки — каталог `<id>` с фиксированным набором файлов; будущие установка и каталог опираются на него.
- Безопасность не усиливается: нет `permissions`, нет ворот для сторонних расширений, нет изоляции интерфейса (iframe); сторонний код исполняется с правами пользователя, его элемент ввода — в общем JS-контексте приложения.

## Рассмотренные варианты

- Модель VS Code: доверенный код + Marketplace + подпись пакетов — требует серверной инфраструктуры и обзора, которых у нас нет; тяжёлый манифест и десятки точек вклада для автора.
- Совместимость с API VS Code (Theia) — постоянная стоимость догона (~8000 записей API, сотни заглушек), для малой команды неподъёмна.
- Строгая изоляция (iframe с отдельным origin, WASM/QuickJS как у Figma, `permissions`) — безопасно, но усложняет автора и платформу; отложено.
- Внутренности хоста как API (Hyper) — API нестабилен по природе.

## Последствия

- Автору достаточно манифеста из нескольких строк, короткого TypeScript и одной команды сборки; в остальном авторские инструменты те же, что использует платформа для расширений по умолчанию.
- Риск цепочки поставок принят: расширение из ненадёжного источника может читать данные приложения. До открытия публичного каталога или автообновления нужно отдельное решение по доверию (подпись и сканирование релизов, `permissions`, изоляция интерфейса) и новый ADR; текущее решение его не отменяет и не откладывает бессрочно.
- Схема манифеста строгая: добавление новых ключей (например `permissions`) старые приложения отклонят; такие изменения сопровождаются поднятием версии API.
- `DOLPHY_DEV_EXTENSIONS` и перезапуск хостов в режиме разработчика доступны в любой сборке; перезапуск хоста движка — `SIGKILL`, журнал SQLite это переносит.
- Контракт `@dolphy-app/engine-contract` поднят до версии 3 (сервис `extensions`).
