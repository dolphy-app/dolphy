# 0012. Общий реестр команд окна: команды приложения и расширений рядом, расширения не вызывают команды приложения

Один ADR — одно решение. Опирается на ADR 0008 (команды и панели расширений); не отменяет его.

## Контекст

После ADR 0008 палитра напрямую читала хранилище вкладов расширений и была жёстко типизирована под `CommandContributionDto`; Ctrl/⌘+K слушал сам компонент палитры; у самого приложения команд не было вообще, а логика смены языка жила внутри экрана настроек. Любая команда приложения («Перейти: Курсы», «Тема: Тёмная») потребовала бы отдельной ветки кода рядом с расширениями.

## Решение

В окне один реактивный реестр команд (`shared/lib/command-registry.ts`), и мы принимаем пять правил.

- **Команды приложения и расширений лежат в одном реестре.** Запись: ключ (`app:<id>` или `extension:<extensionId>:<id>`), источник, название и категория (читаются при каждом чтении, поэтому следуют за языком), необязательные сочетание клавиш, признак «выбрано», доступность, признак «показывать в палитре» и обработчик. Палитра, диспетчер сочетаний и раздел «Настройки → Сочетания клавиш» читают только реестр и не знают, откуда команда. Расширения попадают в него адаптером (`features/extension-commands`) по реактивным вкладам, команды приложения регистрирует `features/app-commands` в корне композиции.
- **Расширения не могут вызвать команды приложения.** В протоколе `invokeCommand` и в результатах команд (`none`, `notify`, `openPanel`, `data`) нет способа обратиться к реестру; `openPanel` открывает только панель того же расширения; рамка пересылает родителю только Ctrl/⌘+K. Ключ включает источник, поэтому ни одно расширение не может заменить команду приложения совпавшим `id`.
- **Сочетания клавиш — только у команд приложения, один диспетчер.** Один обработчик на `document`: Ctrl/⌘+K открывает палитру везде, остальные сочетания (все с `Mod`) не срабатывают в полях ввода, редактируемых элементах, при открытых диалогах и меню и при повторе клавиши; `preventDefault` — только для обработанного. Из рамок произвольные клавиши не передаются. `keybinding` расширения остаётся подсказкой.
- **Значение — отдельная команда.** «Тема: Полночь», «Язык: English» — самостоятельные записи, а не параметр одной команды. Команды тем строятся по реактивному списку тем: тема установленного расширения появляется и пропадает вместе с ним без перезагрузки.
- **Палитра открывается только сочетанием и кнопкой на странице «Сочетания клавиш».** Кнопки в боковом меню нет (решение владельца продукта: меню не должно быть перегружено). Сочетания видны в разделе настроек «Сочетания клавиш» (только чтение).

Смена темы и языка командой и с экрана «Внешний вид» идёт через одно вызываемое API (`theme-selection`, `locale-selection`). Контракт `engine-contract`, RPC и `engine.db` не меняются.

## Рассмотренные варианты

- Открыть команды приложения расширениям в стиле VS Code (`executeCommand`) — расширение из каталога стало бы управлять приложением (смена темы, переходы, будущие разрушающие команды); если понадобится, на конкретных командах появится явный флаг «открыта расширениям» отдельным решением.
- Две отдельные палитры (приложения и расширений) — два входа вместо одного поиска, дубль кода списка и выбора.
- Двухшаговая палитра с выбором значения («Тема» → список тем) — сложнее одношаговой и хуже ложится на реактивный список тем.
- Пользовательские сочетания (аналог `keybindings.json`) сейчас — нужны хранилище, экран переназначения и разрешение конфликтов; сочетания задаются в коде, раздел настроек только показывает их.
- Контекстные условия `when` в виде выражений сейчас — доступность команды задаёт реактивная функция в коде приложения.

## Последствия

- Компромисс: у палитры нет кнопки в меню, пользователь узнаёт о ней из раздела «Сочетания клавиш» и по описанию; возможная доработка — подсказка при первом запуске.
- Новая команда приложения — одна регистрация плюс строки `ru` и `en`.
- На macOS `Cmd+,` и `Cmd+1…3` в окне свободны (меню Electron нет); на других платформах конфликтов со встроенными сочетаниями окна нет.
