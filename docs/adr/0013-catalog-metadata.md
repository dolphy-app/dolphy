# 0013. Метаданные каталога: названия вкладов на уровне записи, теги из закрытого словаря на уровне версии

Один ADR — одно решение. Дополняет ADR 0004 (формат каталога) и ADR 0010 (два индекса, `index.json` для выпущенных приложений и полный `index.v2.json`): по тем же правилам совместимости в индекс добавляются названия вкладов и теги.

## Контекст

- Запись каталога и `ExtensionContributesDto` несут только списки id вкладов («Темы: `dolphy.theme-midnight`»). Названия (`label` у темы, правила оценки и настройки; `title` у команды и панели) есть лишь в манифесте, поэтому окно до установки видит идентификаторы.
- Каталог растёт (уже 14 тем), а фильтровать его можно только по виду вклада. Нужны человеческие группы («Обучение», «Оформление и интерфейс», «Для разработчиков») и теги.
- Выпущенные приложения разбирают индекс строго (`strictObject`), а `extension.json` — тоже строго: неизвестный ключ делает каталог недоступным, а манифест — недействительным.
- Названия берутся из новейшего манифеста, а установка может выбрать запасную более старую версию: сверять названия при установке нельзя, иначе будут ложные расхождения.

## Решение

Мы принимаем одно решение из двух связанных частей.

- **Названия вкладов — необязательная карта `titles` на уровне записи `index.v2.json`**, рядом с `contributes`: «точка → {id → название}» для `themes`, `gradePolicies`, `settings`, `commands`, `panels` (1–60 символов, ключи — id из `contributes` той же записи). Это только отображаемые данные: они не входят в `manifestMismatch`, как `name` и `description`. `catalog build` заполняет карту сам из новейшего манифеста, `legacySubset` вырезает её из `index.json`, запись остаётся видимой. Терпимый разбор окна молча отбрасывает непонятную карту, не запись.
- **Теги — необязательный список `tags` в манифесте и в записи версии `index.v2.json`** (как `icon`): до 5 уникальных значений закрытого словаря `EXTENSION_TAGS` (`learning`, `language`, `content`, `theme`, `interface`, `productivity`, `developer`). Версия с тегами не попадает в `index.json`, более старые версии без тегов остаются; установщик сверяет теги манифеста с записью без учёта порядка. Терпимый разбор окна отбрасывает теги вне своего словаря, не версию.
- **Запасные теги и группы живут в окне.** Эффективные теги — явные теги автора, а если их нет, вычисленные по вкладам (таблица в `docs/design/extensions.md`); явный список заменяет вычисленный. Группы фильтра — одна чистая таблица «тег → группа» (`pages/settings/lib/tags.ts`), тест следит, что каждый тег входит ровно в одну группу. Так уже опубликованные темы получают группы без новой версии.

## Рассмотренные варианты

- Объекты в массивах `contributes` (`{id, title}` вместо строки) — массивы строк общие для форматов 1 и 2, на них держатся десятки фикстур и фильтров; объекты сломали бы эту форму и выпущенные приложения.
- Проверяемые названия на записях версий — запасная версия старше новейшего манифеста, сверка давала бы ложные отказы установки; цена — рост индекса на каждую версию.
- Теги на уровне записи, а не версии — выпущенное приложение, не знающее ключа `tags`, отвергло бы манифест установленной версии; версия с тегами должна исключаться из старого индекса, не скрывая расширение целиком (как `icon`).
- Свободные теги — нет единого словаря: фильтр превращается в облако опечаток, группы нельзя описать таблицей, перевод невозможен.
- Только вычисленные теги — у автора нет способа выразить намерение (`language`, `developer` вычислить нельзя), эвристика ошибается для смешанных расширений.
- Группы отдельным полем манифеста — ещё один строгий ключ с тем же риском совместимости; группы — решение окна, их состав можно менять без правки расширений.

## Последствия

- `tags` — новый строгий ключ манифеста: приложение без этой функции отвергнет `extension.json` с ним. Автор, который нацелен на уже выпущенные приложения, не должен полагаться на теги; расширению достаточно запасных тегов окна.
- Репозиторий каталога должен поднять `@dolphy-app/extension-tools` до версии с этой функцией, прежде чем использовать теги: старый инструмент отвергнет манифест, а `catalog build` без поддержки не запишет теги в индекс.
- Словарь тегов растёт осторожно: новый тег в манифесте несёт тот же риск для приложений без поддержки, что и сам ключ; окно игнорирует неизвестные теги, но манифест их отвергает.
- Публикующий конвейер по-прежнему выкладывает оба индекса вместе (ADR 0010); `titles` лишь в полном индексе, а `tags` ещё и исключают версию из старого.
- Контракт `@dolphy-app/engine-contract` версии 13 (поля `titles` и `tags` в DTO), новых RPC нет.
- Названия видов заданий и языков рендереров остаются идентификаторами, пока у них нет `title` в манифесте.

## Проверка

- `packages/extension-catalog/test` (схема `titles`/`tags`, `legacySubset`, терпимый разбор) и замороженный разбор выпущенной схемы: выход `catalog build` для расширения с названиями и тегами виден в `index.json` без новых версий.
- `packages/extension-tools/test` (сборка, порядок, `docs-contributions.test.ts`), `packages/extension-install/test` (`manifestMismatch` по тегам).
- `apps/desktop/test/settings-tags.test.ts`, `settings-catalog-lib.test.ts`, `settings-catalog.test.ts`, `settings-extensions.test.ts` (запасные теги, группы, фильтры, названия в чипах) и e2e `catalog.e2e.test.ts` (группы, теги, «Ещё фильтры», названия вместо id, старый каталог без `index.v2.json`).
