# 0015. Диагностика расширений, безопасный режим и журнал

Один ADR — одно решение: состояние расширений наблюдаемо и обратимо через единый структурированный контракт. Уровень безопасности — «как у Obsidian» (обзор, безопасный режим, диагностика); ADR 0003 и 0011 не меняет.

## Контекст

Причина, по которой расширение не загрузилось, была свободным текстом (`message`) на английском, без локализации и без возможности отличить случаи программно. Сбои расширений и хоста нигде не копились, хост после повторных падений молча «сдавался» до перезапуска приложения, вывод ограниченного процесса и IPC не имели пределов, журналы шли только в stderr. Пользователь не мог запустить приложение без чужого кода. Внешних пользователей API нет (ADR 0014), независимый аудит и песочница ОС вне объёма.

## Решение

1. Состояние расширения описывают структурированные диагностики `diagnostics: [{code, data}]` с закрытым списком кодов `EXTENSION_DIAGNOSTIC_CODES` в `@dolphy-app/engine-contract`. Это единственный контракт: окно строит текст по коду и данным (ru/en), CLI и журнал — через `formatDiagnostic` (английский). Поле `message` не существует.
2. Безопасный режим — объединение трёх источников: флаг `--safe-mode`, переменная `DOLPHY_SAFE_MODE=1`, сохранённая настройка `extensions.safeMode` в `engine.db`. Расширения не из поставки получают `disabled` с диагностикой `safe-mode`, их код не запускается; поставляемые работают. Снимается настройкой только режим, включённый настройкой.
3. Здоровье расширений (сбои, последняя причина, длительность активации, приостановка) и состояние хоста считает движок в памяти и отдаёт `extensions.diagnostics()`; на диск оно не пишется. Хост после серии падений останавливается (`gave-up`) и перезапускается только действием пользователя.
4. Журнал — файлы JSON-строк в `<userData>/logs` с ограничениями: ротация по дню и 2 МиБ, хранение 7 суток и 10 МиБ суммарно; пишет один писатель — main. Ограниченный процесс ограничен по выводу (64 КиБ/мин) и IPC (1 МиБ на сообщение, 200 сообщений/с). Диагностика уходит наружу только копированием в буфер по действию пользователя, без путей домашнего каталога и пользовательских данных.

## Рассмотренные варианты

- Свободный текст сообщений — нельзя локализовать, сопоставить в тестах и отличить причины; каждая правка формулировки ломала бы потребителей.
- Только окно сбоя у каждого расширения, без безопасного режима — не помогает, когда приложение не запускается или расширение ломает окно.
- Журнал через системный логгер ОС — разные способы чтения на платформах, нет фильтра по расширению и единой ротации, пользователю не показать в окне.
- Удалённая телеметрия — требует согласия, инфраструктуры и политики данных; приложение локальное, достаточно копирования.
- Хранить здоровье в `engine.db` — нужна схема и миграция ради счётчиков сеанса.

## Последствия

- Новая причина состояния — новый код (контракт, тексты ru и en, `formatDiagnostic`, тест перебора кодов); код можно только добавлять осознанно.
- Безопасный режим отключает и расширения режима разработчика; разработчик снимает его флагом.
- Приостановка и убийства не считаются сбоями, поэтому счётчик показывает ошибки кода, а не состояние системы.
- Лимитов кучи V8 и квот процессора по-прежнему нет; пределы IPC измеряются после приёма сообщения и защищают от лавины, не от одного огромного кадра.
- Журналы читает только пользователь; расследование чужих сбоев опирается на то, что он скопирует и пришлёт сам.
