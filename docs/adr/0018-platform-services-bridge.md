# 0018. Мост платформенных сервисов: main — шифровальная машина и источник уведомлений, состояние — в движке

Один ADR — одно решение. Дополняет ADR 0007 (данные расширений в `engine.db`) и ADR 0003 (изоляция): секреты и уведомления получают общий путь к возможностям ОС.

## Контекст

Расширениям нужны секреты (токены внешних сервисов) и системные уведомления. `safeStorage` и `Notification` есть только в главном процессе Electron: в `electron.d.ts` 44.4.5 пространство `Utility` их не содержит. Хост движка и хост расширений — `utilityProcess` с единственным каналом `process.parentPort` к main; запросов «движок → main» с ответом до этого не было. Данные расширений (хранилище, значения настроек) живут в `engine.db` под управлением движка, код расширения не из поставки исполняется в ограниченном процессе и не доверен.

## Решение

Мы вводим порт движка `PlatformServices` и протокол «хост движка ↔ main» и принимаем четыре правила.

- **Порт `PlatformServices`** (`packages/engine/src/ports`): `cipher` (`available`, `encrypt`, `decrypt`) и `notifier` (`show({ source, title, body }) → boolean`). Реализация «платформы нет» — `createUnavailablePlatform()`. Движок ничего не знает об Electron.
- **Протокол по `parentPort`.** Адаптер хоста (`electron/host/platform.ts`) шлёт `platform-request` (`id`, `op`: `cipher.available|encrypt|decrypt|notify`), main (`electron/main/platform-services.ts`) отвечает `platform-response` с тем же `id` (`ok` + `result` либо `ok: false` + код `UNAVAILABLE|INVALID` без текста). Срок — 5 с; срок, закрытый хост и отказ дают «платформа недоступна» (`SecretsUnavailableError` для секретов, `false` для уведомлений). Типы протокола — `apps/desktop/shared/platform.ts`.
- **Main без состояния.** Шифртекст секретов хранит движок (`engine.db`, таблица `extension_secret`, base64); main только шифрует и расшифровывает. Права, лимиты (длины, число ключей, 3 уведомления в минуту и 30 в час), очистку текста и переключатели проверяет служба `ExtensionHostServices` движка, потому что ограниченный процесс не доверен, а жизненный цикл данных (очистка, удаление расширения) один. Main логирует операцию и код отказа, но не значения и не сообщения платформы.
- **Хранилище без защиты считается недоступным.** `isEncryptionAvailable() === false`, бэкенд `basic_text` на Linux (фиксированный пароль — ложное ощущение защиты) или вызов до `app.whenReady()` — `SECRETS_UNAVAILABLE`; `get` несуществующего ключа и `delete` работают.

## Рассмотренные варианты

- API на стороне расширения (код расширения сам вызывает Electron) — `safeStorage` и `Notification` недоступны ни в `utilityProcess`, ни в ограниченном процессе `ELECTRON_RUN_AS_NODE`; их пришлось бы открыть недоверенному коду мимо разрешений и лимитов движка.
- `keytar` или иной нативный модуль — лишняя нативная зависимость (сборка под три ОС и архитектуры, упаковка); `safeStorage` уже в Electron и использует ту же связку ключей ОС.
- Секреты открытым текстом в `engine.db` — копия БД (синхронизация, диагностика, резервная копия) раскрывала бы токены; противоречит смыслу отдельного API секретов.
- Шифртекст в файле main — второе хранилище с отдельным жизненным циклом очистки и удаления данных расширения; движок уже владеет `engine.db`.
- Уведомления из окна (`new Notification` в renderer, Web Notification API) — требуют открытого окна и разрешения Chromium, не работают, пока окно закрыто, а лимиты и права пришлось бы проверять в недоверенной для движка стороне; клик не может вернуть фокус приложению так же надёжно.
- Общий `ipcMain` с каналом на каждую операцию — у хостов нет `ipcRenderer`; единственный канал — `parentPort`.

## Последствия

- Новая платформенная возможность — операция протокола, метод порта, ветка обработчика main и подмена в тестах; пока вызывающего нет, порт не расширяется.
- Пока хост движка не запущен или main не ответил за 5 с, секреты недоступны, а уведомления дают `false`; авторы обрабатывают оба случая.
- Смена связки ключей ОС делает старые значения нечитаемыми: `get` бросает ту же ошибку, автор может `delete` и записать заново.
- e2e и смоук не обращаются к настоящей связке ключей (на macOS это запрос пароля): в несобранном приложении `DOLPHY_FAKE_SAFE_STORAGE=1|unavailable` и `DOLPHY_NOTIFICATION_LOG=<файл>` подменяют платформу; настоящие `safeStorage` и `Notification` покрыты юнитом с подменой и ручной проверкой на macOS.
- Уведомления работают, только пока приложение запущено.
