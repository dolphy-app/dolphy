# Порт Trane на TS/Python vs своё ядро vs Trane как библиотека

> **Статус артефактов (2026-09-29).** Решение принято: делаем TS-порт на ts-fsrs с сохранением структуры Trane (`engine-ts/design/engine-ts.md`). Скрипт подсчёта строк работал по `spike/trane-mvp/trane-src/src` (каталог удалён; тот же исходник — `engine-ts/reference/trane-pristine/src`).

Вопрос: если брать код Trane и переписывать на TypeScript/Python — дешевле ли это, чем написать F1–F7 самим? Метки: `[ОЦЕНКА]` — расчёт по LOC, время не измерялось; `[ВЫВОД]` — наше умозаключение; `[НЕ ПОДТВЕРЖДЕНО]` — не проверено.

## 2. Что бы мы портировали — и что из этого нам нужно

Целевой дизайн (`platform-synthesis.md`) — **FSRS + FIRe-слой**, а не Trane-скорер. В Trane это:

| Часть Trane | В целевом дизайне |
|---|---|
| `PowerLawScorer` (281 LOC + rewards 87) — эвристика «inspired by FSRS», параметры не обучаются, в отчёте нет опубликованных метрик | **Заменяется** на FSRS (`ts-fsrs` v6 MIT, 801★, есть отдельный пакет-оптимизатор параметров по логам; `py-fsrs` MIT, 481★) |
| `reward_propagator` (108) — FIRe-подобный, константы `0.8/0.9/0.2` | Заменяется нашей семантикой FIRe (веса encompassing, дисконт раннего повторения); негативный reward у Trane идёт к dependents, а нужен ещё targeted remediation к prerequisites |
| `review_knocker` (158) — пороги `≥4.5 & вес ≥10` срабатывают только на больших графах | Заменяется repetition compression (set-cover) — своя логика |
| Хранение rewards/deltas как побочные эффекты записи (~370 LOC) | **Не нужно**: если состояние = чистая функция от журнала, эти таблицы не нужны, а с ними уходит и порядко-зависимость replay |
| `graph.rs` (479), gating (`passes_threshold`), `dead_end`, окна мастерства, relearn pile, shuffler | **Остаётся** идейно: это то, что реально ценно (≈ 1.3k LOC) |

**Вывод `[ВЫВОД]`:** из ≈3.1k LOC ядра «живым» после замены на целевую модель остаётся порядка **1–1.3k** — граф, gating, окна, relearn, shuffle. Остальное мы всё равно переписали бы под FSRS/FIRe. Порт всего Trane — это порт кода, который мы выкинем.

## 3. Четыре варианта

| Вариант | Что пишем | Объём нового кода `[ОЦЕНКА]` | Плюсы | Минусы |
|---|---|---|---|---|
| **A. Своё ядро, идеи Trane/MA/KST** | Граф+gating+окна (~1–1.3k), FSRS через готовую библиотеку, FIRe-слой, F-слой | ≈ 2.5–3k `[ОЦЕНКА]` | Состояние = `fold(sorted events)` — чистая функция, F7 тривиален (merge множества событий), FSRS сразу; лицензия на ваш выбор; один язык | Дороже A в 2×; тюнинг Trane (windows, dead_end, relearn) воспроизводим только по идеям и без готовых 353 тестов; риск ошибок в gating |

## 4. Аргументы, которые не видны в таблице

1. **Порт — худший вариант при любой раскладке.** Платим больше всех, получаем ту же AGPL и код, который целевая модель выбросит. Выигрыш «один язык» достижим вариантом C дешевле.
2. **Лицензия.** Порт — производная работа ⇒ AGPL-3.0-or-later. Переписывание «глядя в код» тоже рискует считаться производным, если воспроизводятся структура и константы `[ВЫВОД, юридически не проверялось]`. Чистый вариант C — на опубликованных идеях: пост Skycak о FIRe (в исходниках Trane он сам указан как источник), документация KST, спецификация FSRS. Если закрытая или дуальная лицензия вообще возможна как цель — вариант C единственный.
3. **F7 проще в C.** У Trane rewards/deltas материализуются при записи, поэтому порядок событий меняет результат (спайк: `join` 2.97 / 2.94 / 2.63 при разном порядке одних и тех же 60 событий) и merge = полный replay. Если состояние — чистая функция журнала, порядок влияет только через сортировку по `(ts, event_id)`, а инкрементальные снапшоты возможны. Это не косметика, а единственный способ иметь дешёвый sync `[ВЫВОД]`.
4. **FSRS «из коробки» в TS/Python, но не в Trane.** В Trane скорер зашит (`Box::new(PowerLawScorer{})`, `unit_scorer.rs:95`) — нужен форк. Любая экосистемная библиотека FSRS (MIT) подключается к варианту C без форка; `ts-fsrs` заявляет FSRS v6 и Node ≥ 20, оптимизатор параметров — отдельный пакет `[НЕ ПОДТВЕРЖДЕНО: качество и точность не проверялись]`.
5. **Ценность Trane меньше, чем кажется, а скорер — его слабейшая часть (измерено).** На 65 пользователях Anki (588 454 тестовых отзыва, `docs/research/fsrs-vs-trane.md`) `PowerLawScorer` уступает FSRS-6 с параметрами по умолчанию по Log Loss во всех 16 протестированных вариантах: разрыв 0.053–0.365 нат на отзыв (для маппингов M0–M2 — 0.053–0.126), FSRS лучше у 90.8–100% пользователей. Вероятность `1−urgency` у Trane хуже константы «среднее по пользователю»: обгоняет её у 1.5–23.1% пользователей. Оговорки: домен — Anki-карточки, а не навыки с проверкой тестами; Trane запускался без `practice_deltas` и `rewards`; сравнивалось предсказание, а не эффективность расписания. «Проверенность» самого Trane — 353 теста поведения кода, а не педагогическая валидация.
6. **Раннер, авторинг, F2, F3, F6 стоят одинаково в любом варианте** — от выбора движка не зависят. Для SQL-раннера у Python `sqlite3` в stdlib; у TS нужен npm-пакет `[ВЫВОД]`.
7. **Гипотезы MVP не зависят от движка.** Плотность encompassing в SQL, время авторинга темы, реакция на gating — проверяются на любом варианте.

## 5. Решение

Правило выбора:

- **Есть Rust-навык и цель — скорее проверить педагогику на SQL → A.** Дёшево, форк не нужен. Границу держать за собственным интерфейсом `Scheduler` и собственным журналом событий, чтобы движок можно заменить.
- **Продуктовый стек TS/Python и важны FSRS, sync, лицензия → C.** Не порт, а свой граф+gating (≈1–1.3k) поверх ts-fsrs/py-fsrs.
- **B — не делать.**
- A′ имеет смысл только как временный мост при уже готовом TS/Python-UI; цена — 200–400 строк Rust-обвязки без готового сервера.

Рекомендация `[ВЫВОД]`: **A для MVP → C после подтверждения гипотез.** Порядок: журнал событий, формат курса и раннер живут снаружи движка с первого дня (они переносятся без изменений); при уходе на C заменяется только слой планировщика. Точка переключения: когда упрёмся в FSRS, порядко-зависимый replay или лицензию.

## 6. Что не измерено

- Время реализации — только LOC.
- Сколько строк TS даст порт 3.1k строк Rust: коэффициент 0.7–1.2 условный `[НЕ ПОДТВЕРЖДЕНО]`.
- Сложность gating/`dead_end` при воспроизведении по идеям без кода Trane — не оценивалась экспериментально.
- Качество `ts-fsrs`/`py-fsrs` в наших сценариях: `py-fsrs` 6.3.2 (FSRS-6, параметры по умолчанию) измерен только на Anki-логах (см. п. 5); оптимизатор параметров не запускался, `ts-fsrs` не проверялся.
