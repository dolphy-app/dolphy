# REPORT-integration: FSRS-6 как `ExerciseScorer` Trane 0.34.1 на сквозных сценариях

> **Статус артефактов (2026-09-29).** Каталог `spike/trane-fsrs/` (харнесс `scenario/`, патченный Trane, сырой вывод `results-*.txt`) удалён; остаётся этот отчёт. Раздел «Как воспроизвести» не выполняется.

Крейт: `spike/trane-fsrs/scenario` (бинарь `scenario`, зависимости: `trane` = path `../trane` (патченный), `fsrs-scorer` = path `../fsrs-scorer`, anyhow, ustr, vfs, serde_json, serde_yaml). Курс: 7 уроков SQL (`lib_json/`, `src/course.rs` скопированы из trane-mvp). Каждый запуск сценария копирует `lib_json` в новый каталог `$TMPDIR/trane-scn-<pid>/runN` (свой `.trane`), поэтому состояние учеников не разделяется; каталог удаляется в `Drop`. Сырой вывод: `scenario/results-all.txt` (S1-S6, S8), `scenario/results-s7.txt` (S7).
Машина: Apple Silicon, macOS arm64, release-сборка. Стохастические сценарии повторены 10 раз, ячейки: `медиана (min..max)`, `-` = «никогда».

Обозначения: **PL** = upstream `PowerLawScorer` (`SchedulerOverrides::default()`); **H** = Hybrid + RunnerMap; **P** = Pure + RunnerMap; **H50** = H + `num_trials = Some(50)`. **Сводка: ошибок `Err` от scorer/scheduler — 0, паник — 0** во всех сценариях (в конце каждого прогона печатается `ERRORS/PANICS logged: 0`; все вызовы `get_exercise_batch`/`score_exercise`/`get_unit_score` обёрнуты логгером, сценарии — в `catch_unwind`).

(2) У PL гейт потом снова ОТКРЫВАЕТСЯ: в upstream `PowerLawScorer` есть «old-good retrievability floor» (`OLD_GOOD_MIN_AGE = 50` дней, `OLD_GOOD_FLOOR = 0.75`, `OLD_GOOD_MIN_SCORE = 4.0`, >= 2 trials) — после 50 дней у упражнения с хорошей историей retrievability не падает ниже 0.75, value = 0.75*5 = 3.75 (виден 3.750 при +60/+120/+240; диагностика в фиксированные дни: 45 → 2.537, 50 → 3.750). PL: гейт закрыт с 19-го дня и до срабатывания пола (между днями 45 и 50), затем открыт постоянно (точный день не искался); FSRS-варианты этого пола не имеют. (3) Как следствие у H/P зависимые уроки (`where`) исчезают из батча навсегда после ~63-го дня, пока ученик не вернётся и не повторит `select` (сам `select` в батче 100 % во все моменты у всех скореров — review предлагается всегда, потому что в батче нет других уроков с такой urgency [ЧАСТИЧНО ПОДТВЕРЖДЕНО: наблюдение верно, причина не проверялась]). (4) Значения H и P на этих трёх упражнениях совпадают (при Five,Five S >= 2 дней, Pure = 5r и Hybrid = r·pl.value=r·5). (5) Оба поведения — «закрыть гейт после долгого перерыва» и «поднять пол» — политические решения; FSRS их принимает явно: нужен либо отдельный пол, либо принятие «возврат к prerequisite после ~2 месяцев».

## S6. Replay/порядок независимость: 60 случайных trials (оценки 1/3/5, 10 дней, 2 устройства), 10 seeds × 4 порядка; `now` = T0+11d

Максимум |Δ| `get_unit_score` относительно порядка «по ts» (медиана / максимум по 10 seeds):

| scorer | пара | упражнения (все 21) | уроки (все 7) | Err |
|---|---|---|---|---|
| PL | sorted vs sorted (детерминизм) | 0 / 0 | 0 / 0 | 0 |
| PL | sorted vs A-then-B | 0.621 / 1.03 | 0.284 / 0.478 | 0 |
| PL | sorted vs reverse ts | 0.802 / 1.13 | 0.298 / 0.438 | 0 |
| H | sorted vs sorted | 0 / 0 | 0 / 0 | 0 |
| H | sorted vs A-then-B | 0.696 / 1.11 | 0.279 / 0.506 | 0 |
| H | sorted vs reverse ts | 0.839 / 1.24 | 0.292 / 0.464 | 0 |
| P | sorted vs sorted | 0 / 0 | 0 / 0 | 0 |
| P | sorted vs A-then-B | 0.0687 / 0.206 | 0.0359 / 0.104 | 0 |
| P | sorted vs reverse ts | 0.0107 / 0.177 | 0.0069 / 0.0589 | 0 |

**Интерпретация S6.** (1) Детерминизм есть (два прогона в одном порядке дают побитово одинаковые значения). (2) Порядок поступления влияет на оценки во ВСЕХ вариантах, включая upstream PL: расхождения до 1.1-1.2 балла на упражнении. Это НЕ свойство FSRS. (3) Механизм, [INFERENCE из чтения `scheduler.rs::score_exercise`, экспериментом не изолирован]: при записи trial Trane сохраняет `delta = score.float_score() - existing_score`, где `existing_score` — текущая оценка упражнения на момент `now` планировщика (в S6 = T0+11d), а не на момент trial-а; trials в `practice_stats` читаются по `ORDER BY timestamp`, но дельты и rewards (у уроков/курса) зависят от порядка вставки. PL/H используют дельты в `PowerLawScorer` (H — через PL-множитель), поэтому у них расхождение большое; у P скорер дельты не читает, остаётся вклад rewards (`score + reward`) — расхождение на порядок меньше (медиана 0.011-0.069, макс. 0.21). (4) Вывод для продукта: FSRS-Pure ближе всех к «функции множества trials», но не идеален; если нужна строгая независимость от порядка (multi-device), нужно переигрывать trials в ts-порядке на чистом состоянии (как в первом столбце), либо отказаться от дельт/rewards. (5) Оба FSRS-варианта не возвращают `Err` на неупорядоченный ввод (в отличие от `PowerLawScorer`, который возвращает `Err`, если trials не отсортированы по убыванию ts); в Trane порядок гарантирован SQL-запросом, поэтому в сценарии ни один Err не сработал.

## S8. H vs H50 (`num_trials` 20 vs 50)

12 дней (10 повторов), день первого появления: `where`/`aggregate` 2 (2..2) у обоих; `join` 4 (4..5) у обоих; `subquery` H 7 (6..7), H50 6 (6..8); `window` 9 (8..10) у обоих. Расширение (не заказано, 40 дней, чтобы у упражнений накопилось > 20 trials): `join` 4 (4..5) у обоих; `subquery` H 7 (6..8) / H50 6 (6..8); `window` H 9 (8..11) / H50 8 (8..10); финальные оценки на дне 39 — 5.00 у обоих (у `window` H 5.00 (4.97..5.00), H50 4.99 (4.96..5.00)); число уроков в батче: 6 (5..7) у обоих на днях 12-39.

**Интерпретация S8.** За 12 дней у упражнения < 20 trials, поэтому `num_trials` 20 vs 50 не может дать разницы; наблюдаемые сдвиги на 1 день внутри размаха — шум выборки батчей. На 40 днях в сильном сценарии разницы тоже нет (5.00 против 4.99-5.00): усечение до 20 последних trials при FSRS-replay не влияет на устойчивую ситуацию «все Five». Влияние на длинные истории со сбоями не проверено [НЕ ПОДТВЕРЖДЕНО] (см. `REPORT-truncation.md`).

## Общий вывод

FSRS-6 подключается без проблем к паутине Trane: 0 ошибок и паник во всех сценариях; скорость разблокировки, размеры батчей и стоимость в S1/S2/S7/S8 совпадают с PL в пределах шума. Различия — политика: (a) Three/retry: PL никогда не открывает зависимые, H открывает на 9 trials, P — на 6 (S3/S4), Pure «прощает» слабого ученика; (b) закрытие гейта после перерыва: 18 дней (PL, и потом снова открывается с 50-го дня благодаря old-good floor) против 63 дней у FSRS, без повторного открытия (S5); (c) порядок trials: не улучшается и не ухудшается относительно PL, определяется дельтами/rewards Trane, а не скорером (S6).

## Friction points

1. `Trane::new_local` не принимает скорер: понадобился патч (`SchedulerOverrides`), в upstream 0.34.1 API отсутствует.
2. `score_exercise` в Trane считает `delta` относительно оценки упражнения на момент `now` планировщика (не на момент trial-а) — даёт зависимость от порядка/момента replay для любого скорера (S6). Для FSRS-only режима логично отключить дельты/rewards (нет такого switch в `SchedulerOptions` [НЕ ПОДТВЕРЖДЕНО]).
3. Кэш оценок Trane живёт 2 часа (`MAX_CACHE_AGE`); при same-day интервалах +2h/+4h инвалидация после `score_exercise` работает (S2), но `override_current_timestamp` нужно ставить до оценки (иначе в кэше окажутся значения на неверный момент).
4. Old-good floor (PL) отсутствует у FSRS-вариантов: гейт закрывается после ~63 дней без практики и не открывается (S5).
5. `PowerLawScorer` возвращает `Err` на неупорядоченных trials, FSRS-адаптер сортирует сам — различие контрактов; в Trane это скрыто SQL `ORDER BY`.
6. Размер батча по умолчанию 10 на курсе из 21 упражнения (все S1-S6), в S7 достигает 50: в поведении гейта участвует и `min_fraction` (доля упражнений урока при скоре около порога) — в отчёте не изолировано [НЕ ПОДТВЕРЖДЕНО].
7. Порог 3.0 у `where` в S3 для H пробивается на 0.03 (2.968 в момент батча): малейшая перенастройка `S_PASS`/RatingMap изменит «открывает/не открывает».
8. `FsrsScorer::with_defaults` возвращает `FsrsScorer`, а не `Result` (различается с `FsrsScorer::new`, возвращающим `Result`) — мелкое неудобство API.
9. Trane использует thread RNG для семплирования батчей: сценарии невоспроизводимы побитово; поэтому 10 повторов и median/min/max.

## Как воспроизвести

```
cd spike/trane-fsrs/scenario
cargo build --release
./target/release/scenario all              # S1-S6, S8 (~11 c)
./target/release/scenario s1|s2|s3|s4|s5|s6|s8   # по отдельности
for s in PL H P H50; do ./target/release/scenario s7 $s; done   # S7 (генерирует $TMPDIR/trane-scn-big один раз; по процессу на скорер для честного RSS)
rm -rf target /tmp/trane-scn-big           # уборка
```
