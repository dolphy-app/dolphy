# FSRS-6 при усечении истории до последних N обзоров (ограничение Trane `num_trials=20`)

> **Статус артефактов (2026-09-29).** Скрипты и CSV исследования (`spike/trane-fsrs/truncation/`) удалены; остаётся этот отчёт. Раздел «Воспроизведение» не выполняется.

## Вопрос
Trane передаёт скореру только последние 20 trials упражнения; состояние FSRS зависит от всей истории. Насколько падает точность FSRS-6 (параметры по умолчанию), если состояние восстанавливать только по последним N обзорам (новая карточка в начале окна), N ∈ {3, 5, 10, 20, 50, 100, all}?

## Методика
- Данные: fsrs-dataset `float-delta-t`, 30 файлов пользователей (300 КБ – 12 МБ, seed 1 и 2, суммарно ≈115.8 МБ по `data_files.txt`; списки в `truncation/files_selected*.txt`). Один дубликат (ry-9b3b6b2) отброшен по хешу содержимого, как в prep.py → **29 пользователей** (больше заданных 12–20: оба набора файлов были скачаны, чтобы найти пользователей с длинными историями; в подвыборке `long` остаётся 18).
- Логика prep.py: `MIN_REVIEWS=1500`, eval-строка = не первый обзор карточки и elapsed ≥ 1 день, y = rating>1, отсечка = медиана времени eval-обзоров пользователя, оцениваются только обзоры позже отсечки. AVG = среднее y по eval-строкам до отсечки.
- Предиктор: py-fsrs (`fsrs` из pip), `Scheduler(learning_steps=(), relearning_steps=(), enable_fuzzing=False)`, параметры по умолчанию. Для каждой eval-строки прогоняются последние N обзоров этой карточки перед строкой (свежая `Card`), затем `get_card_retrievability` на момент строки. N=all — эталон (полная история карточки).
- Два режима (скрипт `study.py rep|long`):
  - **rep** (репрезентативный): случайные ≤800 карточек на пользователя (seed 0), 29 пользователей, 58 013 оцениваемых строк.
  - **long** (стресс-тест): только карточки с ≥21 обзорами (≤1500 на пользователя), 18 пользователей (11 не имеют таких карточек), 39 874 строки. Выбор по итоговому числу обзоров карточки — селекционное смещение (отбор по «будущему»), используется только как стресс-тест усечения, не как оценка качества.
- Метрики считаются по пользователю, затем усредняются; 99% CI — bootstrap по пользователям (10 000 ресэмплов, перцентили 0.5/99.5) для парных разностей с N=all. Log Loss с clip 1e-6.

## Вывод (implication)
- N=20 практически без потерь: ΔLogLoss vs all = +0.0000 (rep) / +0.0002 (long, 35% строк усечены), CI включают ноль или ≤0.0009 нат; mean |R_20−R_all| = 0.0001 / 0.0013. Усечение «кусается» только на строках с >20 предыдущими обзорами: там ошибка |ΔR| ≈ 0.004–0.015, ΔLL порядка 1e-3 и статистически незначима.
- N ≤ 10 уже вредно и значимо: N=10 в long теряет +0.0196 нат (CI +0.0110…+0.0272) и весь выигрыш над AVG; N=5 и N=3 хуже AVG. Т.е. **окно меньше ~20 для FSRS недопустимо**.
- Какое N восстанавливает ≥99% выигрыша FSRS над AVG: N=20 (99.9% в rep, 98.1% в long с шумным CI), N=50 — 100.00% в обоих режимах (CI rep 99.99…100.01%). Итог: **N=20 достаточно при типичных историях Anki; N=50 гарантирует ≥99%** и стоит малую цену (чтение 50 trials вместо 20), поэтому при интеграции разумно поднять `SchedulerOptions.num_trials` до 50, но это не обязательно.
- Поскольку окно в 20 покрывает ≥95% строк даже в обычной выборке, ключевой риск — не усечение, а то, что `MasteryScore`→rating и отсутствие обзоров в единицах ≥1 дня искажают состояние (вне рамок этого исследования).
- Оговорка: Anki-карточки — одиночные факты с интервалами Anki (в основном ≥1 дня; строки с elapsed<1 дня исключены). В Trane упражнения показываются чаще и сессиями, поэтому число trials на упражнение может быть значительно больше (или короче интервалы), и доля усечённых строк там может оказаться выше, чем 3–35%, а внутрисуточные повторы FSRS-6 обрабатывает с ограниченной точностью (delta_t в целых днях в fsrs-rs, здесь — вещественное время py-fsrs). Результат для Trane `[НЕ ПОДТВЕРЖДЕНО]` без прогона на логах Trane.

## Ограничения
- Параметры FSRS по умолчанию, не оптимизированные; AVG — сильная база на этих пользователях (FSRS выигрывает лишь 0.008–0.010 нат в среднем; у 13 из 29 пользователей rep и 6 из 18 в long FSRS с параметрами по умолчанию хуже AVG).
- 800 карточек на пользователя в rep; в long выбор карточек по числу обзоров смещён.
- Мало строк с prior>50 (rep 115, long 507, из 1–2 пользователей).
- Не сравнивалось с оптимизированными параметрами; не проверялась реализация fsrs-rs (только py-fsrs).
