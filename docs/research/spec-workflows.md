# Как в индустрии ведут спеки, планы и историю решений по фичам

Вопрос: как устроить `specs/<feature>/SPEC.md` так, чтобы у проекта была хронология и иерархия, а завершённые и неактуальные фичи не влияли на разработку новых — ни у людей, ни у агентов.

Метки: факты взяты из первичных документов по ссылкам в §8 (прочитаны 2026-09-30); `[ВЫВОД]` — наше умозаключение; `[НЕ ПРОВЕРЕНО]` — в источниках не нашли. Эксперименты не ставились: это обзор практик, а не измерение. Инструменты SDD меняются быстро (об этом предупреждает и Böckeler), поэтому описание инструментов привязано к дате чтения.

## 1. Итог

1. Во всех просмотренных процессах, где жизненный цикл определён (PEP, Rust RFC, KEP, ADR, OpenSpec), различают два артефакта: **предложение об изменении** (временное, привязано к фиче) и **описание текущего состояния** (постоянное). Старые фичи не мешают новым, потому что не претендуют на роль источника истины о текущем поведении. У Kiro и ExecPlan жизненный цикл в прочитанных материалах не определён.
2. Завершённый документ становится **неизменяемой исторической записью**. PEP 1 говорит это прямо: после `Final` PEP — «исторический документ, а не живая спецификация», формальное описание поведения «поддерживается в другом месте». Rust RFC и KEP устроены так же.
3. Замена делается **новым документом со связью** (`Replaces` / `Superseded-By`, `replaces` / `superseded-by`, `superseded by ADR-0123`), а не правкой старого. Правки старого допускаются только мелкие.
4. **Статус — машиночитаемое поле** в шапке документа, а не место в дереве каталогов. Каталог `archive/` из просмотренного есть только у OpenSpec.
5. **Иерархия — через владельца и метаданные**, а не через вложенную нумерацию: KEP лежат в подкаталогах SIG, PEP имеют поле `Topic`, у KEP есть `see-also`.
6. **Спека — не для всего.** Rust, KEP, OpenSpec и Böckeler признают порог: багфикс и мелочь идут без спеки.
7. Для агентов действует тот же принцип, но жёстче: контекст ограничен, «context rot» растёт с объёмом (Anthropic). `[ВЫВОД]` Устаревший документ, попавший в поиск, хуже, чем его отсутствие. Наблюдение Böckeler: агент принял заметки исследования о существующих классах за новую спецификацию и сгенерировал их заново.
8. Индустрия **не сошлась** в одном: архивировать (OpenSpec) или оставлять на месте со статусом (PEP, KEP, Spec Kit). Обсуждение в §7.

## 2. Процессы предложений в открытых проектах

| | Python PEP | Rust RFC | Kubernetes KEP |
|---|---|---|---|
| Единица | одно ключевое предложение; «если сомневаешься — раздели» | «существенное» изменение | «доработка» (enhancement), видимая пользователю или широко затрагивающая разработчиков |
| Порог | большинство багфиксов и улучшений идёт без PEP | багфиксы, рефакторинг, невидимые пользователю изменения — без RFC | «более-менее обязательно» для нетривиального; SIG сами решают, что не требует |
| Номер | следующий свободный | номер PR, файл переименовывается при принятии | номер tracking issue |
| Статусы | Draft, Active, Accepted, Provisional, Deferred, Rejected, Withdrawn, Final, Superseded | «active» после слияния RFC; отклонённые закрываются, часть помечается `postponed` | provisional, implementable, implemented, deferred, rejected, withdrawn, replaced |
| Связи | `Requires`, `Replaces`, `Superseded-By` | новая RFC + пометка в старой | `see-also`, `replaces`, `superseded-by` |
| Иерархия | поле `Topic` (Governance, Packaging, Release, Typing) и `Type` | подкоманды (lang, libs, compiler) | подкаталоги `keps/sig-*`, поля `owning-sig`, `participating-sigs` |
| Что после реализации | `Final`: в общем случае существенно не меняется; поведение — в Language/Library Reference | после принятия существенно не менять; существенное — новая RFC с пометкой в старой; RFC может не отражать финал | `implemented`: больше не меняется активно; отклонённые хранятся как исторические |
| Работа «в процессе» | Draft в PR | RFC + tracking issue в репозитории rust | GitHub issue отслеживает работу, KEP хранит решение; «issues для работы в полёте, вместо зонтичных issue» |

Заметное:
- PEP и Rust явно называют слой, где живёт текущая истина, отдельно от предложения. У Python это Language Reference, у Rust — реализация и документация: авторы оговаривают, что смерженная RFC не обязана отражать итоговый результат к следующему релизу.
- KEP осознанно копируют Rust, а тот — PEP и IETF; процесс дрейфует медленно, поэтому набор статусов и связей можно считать устоявшимся.
- Хронология в KEP: черновики называются `draft-YYYYMMDD-название.md` до присвоения номера; в метаданных есть `creation-date` («чтобы файлы читались и без VCS») и `last-updated`.
- Все три процесса проектировались для сообществ с сотнями участников и ревью-комитетами. `[ВЫВОД]` Из них стоит брать схему статусов и связей, но не ревью-церемонии (FCP, sponsor, editor).

## 3. ADR: решения отдельно от планов

Michael Nygard (2011), MADR:
- Один ADR — одно значимое решение. Короткий (1–2 страницы). Большие документы не обновляют, и их никто не читает (Nygard).
- Нумерация последовательная, номера не переиспользуются. Путь у Nygard `doc/arch/adr-NNN.md`, у MADR `NNNN-title-with-dashes.md`.
- Отменённое решение не удаляют: статус `superseded` со ссылкой на замену. Важно знать, что оно было решением, но больше не является им.
- Статусы: `proposed | accepted | deprecated | superseded by ADR-NNNN` (MADR добавляет `rejected`).
- Цель — не слепо принять и не слепо изменить чужое решение: ADR передаёт контекст и последствия («разговор с будущим разработчиком»).
- В MADR есть необязательные поля `Decision Drivers`, `Considered Options`, `Confirmation` (как проверяется соблюдение решения).

`[ВЫВОД]` ADR решает ровно ту часть проблемы, которую не решает спека: **решение переживает фичу**, а её план и чек-лист — нет. Спека фичи не должна быть единственным местом, где записано «почему так».

## 4. Инструменты spec-driven development (SDD)

### 4.1. Таксономия Böckeler (Thoughtworks, 2025-10-15)

- **Spec-first**: спека пишется до кода и после задачи может быть выброшена.
- **Spec-anchored**: спека сохраняется и правится при развитии фичи.
- **Spec-as-source**: человек правит только спеку, код генерируется.
- Все просмотренные подходы — spec-first; политика «что со спекой потом» чаще всего не определена.
- Отдельно от спек она выделяет **memory bank** (`AGENTS.md`, `constitution.md`, `steering/*.md`): контекст, нужный всем сессиям, тогда как спека относится только к задачам, меняющим конкретную функциональность.

Критика из той же статьи (наблюдения автора, не измерения):
- Один процесс на все размеры не работает: баг превратился в 4 user stories и 16 критериев приёмки.
- Много повторяющегося markdown, который скучнее ревьюить, чем код.
- Ложное чувство контроля: агент игнорирует инструкции или чрезмерно им следует. Заметки исследования о существующих классах агент воспринял как новую спеку и создал дубликаты.
- Аналогия с MDD: «унаследовать недостатки обоих — негибкость и недетерминизм».

### 4.2. GitHub Spec Kit

- `specs/NNN-feature/` с файлами `spec.md`, `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md`, `tasks.md`. Номер и ветка создаются автоматически (`003-chat-system`).
- Проект-уровневый контекст — `constitution` («неизменные принципы»), отдельно от фич.
- **Политика жизни спеки не задана.** Документация `concepts/spec-persistence` называет три модели и оговаривает, что ни одна не по умолчанию:

| Модель | Правило изменения | Риск |
|---|---|---|
| flow-forward | завершённые артефакты неизменны; изменение — новая папка с перекрёстными ссылками | дублирование и разбросанный контекст |
| living spec | правится `spec.md`, `plan.md`/`tasks.md` перегенерируются | потеря обоснований в перегенерированных файлах |
| flow-back | правка в любом артефакте, потом согласование | тихий дрейф |

- Discussion #152 «Evolving specs» (44 комментария, 88 ответов на 2026-09-30) ставит ровно нашу проблему: спека изменения не отражает систему целиком, чтобы понять, что делает система, надо читать обе спеки. Ответы расходятся: новая спека на каждое изменение; по папке на крупную область с цепочкой спек; спека — это изменение к состоянию системы на момент её написания, а правки без спеки допустимы. Отдельная ветка спора — что считать источником истины, спеку или код.
- Böckeler делает вывод из «ветка на спеку»: в Spec Kit спека живёт как **изменение**, а не как **фича**.

### 4.3. OpenSpec (Fission-AI)

Единственный из просмотренных, где жизненный цикл описан целиком.

```
openspec/
  specs/<домен>/spec.md                     # текущее поведение, по доменам
  changes/<имя>/                            # активные изменения
    proposal.md  design.md  tasks.md
    specs/<домен>/spec.md                   # дельта: ADDED / MODIFIED / REMOVED
  changes/archive/YYYY-MM-DD-<имя>/         # после слияния
```

- `specs/` — «источник истины о том, как система работает сейчас»; `changes/` — предложенные изменения.
- `archive` сливает дельты в `specs/` и переносит папку в `archive/ДАТА-имя/`. Рекомендуется **архивировать после слияния PR**; допустимо в самом PR.
- Спека — контракт поведения, не план реализации. Критерий: «если реализацию можно поменять без изменения наблюдаемого поведения, в спеке этому не место».
- «Progressive rigor»: по умолчанию lite-спека (требования, границы, несколько проверок); full — для контрактов, миграций, безопасности.
- Brownfield-first: полное описание системы не пишут заранее, `specs/` заполняется по мере работы.
- Конфликты возникают только в `specs/`, когда два изменения правят одно требование; авторы считают это признаком реального расхождения.
- Весь `openspec/` коммитится; спека и код идут в одной ветке и ревьюятся вместе; сначала ревью `proposal.md` и дельты, потом код.
- `openspec/config.yaml` содержит `context:`, который подмешивается в каждый запрос планирования.

### 4.4. Kiro (AWS)

- `.kiro/specs/<имя>/requirements.md` (или `bugfix.md`), `design.md`, `tasks.md`. Два типа: feature и bugfix; есть Quick Spec без гейтов.
- Memory bank называется steering (`product.md`, `tech.md`, `structure.md`).
- На прочитанных страницах документации политика хранения спеки после завершения задачи не описана `[НЕ ПРОВЕРЕНО]`; Böckeler отмечает то же: примеры — одна задача или user story, без объяснения, как требования используются в долгую.

### 4.5. OpenAI ExecPlan (`PLANS.md`)

- Один самодостаточный документ на задачу, читатель — «полный новичок без памяти о прошлых планах».
- Обязательные живые разделы: `Progress` (чек-лист с временными метками), `Surprises & Discoveries`, `Decision Log` (решение, обоснование, дата/автор), `Outcomes & Retrospective`.
- `AGENTS.md` содержит только правило «когда использовать ExecPlan».
- Изоляция от старых планов заложена намеренно: если новый план опирается на прежний, тот включается по ссылке (если закоммичен) или пересказывается.
- Прямого механизма архивации нет `[НЕ ПРОВЕРЕНО]`.

## 5. Смежные практики

**Shape Up (Basecamp).** Нет бэклога; ставка делается на один цикл вперёд; незавершённое не переносится, а заново оформляется как новая ставка. `[ВЫВОД]` Это тот же принцип изоляции от прошлого, применённый к планированию, а не к документам: старый замысел возвращается на общих основаниях, а не по инерции.

**Diátaxis.** Документация делится на tutorial / how-to / reference / explanation; reference (что есть сейчас) и explanation (почему) не смешивают: примеры в справочнике легко разрастаются в объяснение, и страдают оба. `[ВЫВОД]` Соответствует нашему разделению «текущее состояние» / «решения»: спека фичи — смесь того и другого, и в этом её слабость как долговременного носителя знаний.

**Контекст агентов (Anthropic, 2025-09-29).**
- Контекст — конечный ресурс; с ростом числа токенов точность извлечения падает («context rot»). Цель — минимальный набор высокосигнальных токенов.
- «Just-in-time»: агент держит лёгкие идентификаторы (пути файлов) и подгружает данные `glob`/`grep`. Иерархия папок, имена и **временные метки** служат сигналами релевантности.
- Гибрид: `CLAUDE.md` кладётся в контекст сразу, остальное — по требованию.
- Structured note-taking: агент ведёт `NOTES.md`, чтобы переживать сброс контекста.
- `[ВЫВОД]` Из этого следует практическое правило: всё, что лежит в дереве и находится поиском, участвует в контексте. Архивная спека с формулировками требований конкурирует с актуальной, если её не пометить и не исключить из типовых обходов.

## 6. Сводка по подходам

| Подход | Где текущая истина | Судьба завершённого | Хронология | Иерархия | Цена |
|---|---|---|---|---|---|
| PEP / KEP / Rust RFC | реализация + справочная документация | остаётся на месте, статус `Final`/`implemented`, не редактируется | номер, `creation-date`, статусы | `Topic`, SIG-каталоги | нужны редакторы и ревью-процесс |
| ADR | сами ADR-ы (журнал решений) | остаётся, при замене `superseded` | последовательный номер | нет (плоский), связи по ссылкам | мало; дисциплина писать «почему» |
| Spec Kit, flow-forward | нет единого места: цепочка спек | остаётся неизменной | номер `NNN` | нет | дублирование, читать цепочку |
| Spec Kit, living spec | сама `spec.md` | правится на месте | git | нет | потеря обоснований |
| OpenSpec | `specs/<домен>/` | `changes/archive/ДАТА-имя/` | дата в имени, git | домены в `specs/` | слияние дельт, два слоя |
| Kiro | не определено | не определено | git | нет | 3 файла на любую задачу |
| ExecPlan | сам план (живой) | не определено | метки в `Progress` | нет | самодостаточность → объём |
| Shape Up | не документ, а продукт | не переносится | цикл | нет | нужна стабильная команда |

## 7. Открытые расхождения

1. **Архив или статус на месте.** В PEP/KEP достаточно статуса: искать будут по индексу и ссылкам, читать по запросу. У агента поиск идёт по дереву. `[ВЫВОД]` Для репозитория, где работают агенты, физическое разделение (`archive/`) плюс явная пометка в шапке снижают риск, но платят стоимость переноса при закрытии. Альтернатива — статус в шапке и правило в `AGENTS.md`; дешевле, но зависит от дисциплины.
2. **Дельта-слой (`specs/` как текущее поведение) или существующие документы.** OpenSpec окупается, когда параллельно идёт много изменений и есть общая доменная модель. `[ВЫВОД]` Для одного репозитория с уже существующими `docs/design`/README пакетов второй слой описания конкурирует с ними; `[НЕ ПРОВЕРЕНО]` где порог, после которого он окупается.
3. **Живая спека или историческая.** Отраслевые процессы (PEP/Rust/KEP) выбирают историческую; SDD-инструменты формально хотят живую, но на практике (Spec Kit: ветка на спеку) получают историческую. Böckeler считает spec-anchored не доказанным.
4. **Размер процесса.** Все источники, включая авторов инструментов, признают порог. Точные пороги называет только Rust/KEP на уровне примеров.
5. **Один файл или несколько.** Kiro: 3 файла, Spec Kit: 7+, OpenSpec: 3 + дельта, ExecPlan: 1. Böckeler жалуется на объём ревью при многофайловой схеме; ExecPlan — единственный, кто выбрал один файл, но добавил жёсткую структуру разделов.
6. Нет данных о том, как эти схемы ведут себя за пределами первых месяцев: у OpenSpec и Spec Kit срок практики короткий; Böckeler сама пишет, что ждёт отчётов о долгом использовании на реальных кодовых базах `[НЕ ПРОВЕРЕНО]`.

## 8. Что это значит для нашего репозитория

Контекст: `docs/design` и `docs/research` — «состояние» и исследования; `engine-ts/design` — дизайн v1; ветки `feature/<name>` вливаются `--no-ff` в `develop`; `CHANGELOG.md` ведёт semantic-release; агенты работают через `AGENTS.md` и скиллы.

`[ВЫВОД]`, без принятого решения:

1. **Ядро схемы подтверждается** практикой PEP/KEP/OpenSpec: активные спеки отдельно от завершённых, завершённая неизменна, замена — новым документом со связью, решения — в ADR, поведение — в постоянных документах.
2. **Статусы взять из KEP/PEP** и сократить: `draft`, `active`, `done`, `superseded`, `dropped` (rejected + withdrawn). Отклонённое и брошенное **хранить** (KEP оставляет rejected как исторический документ) — это защита от повторного обсуждения.
3. **Связи двусторонние**: `supersedes` в новой спеке и `superseded-by` в старой (как `Replaces`/`Superseded-By`).
4. **Хронология** — из трёх источников: дата закрытия в имени каталога архива (OpenSpec), `created`/`closed` в шапке (KEP: файлы должны читаться и без VCS), номер PR или имя ветки в шапке (KEP-номер = номер tracking issue; у нас `feature/<name>` ↔ имя каталога).
5. **Иерархия** — поле `touches: [пакеты]` (аналог `owning-sig`/`Topic`) и `depends-on`, без вложенных каталогов: KEP делят по каталогам SIG, вероятно, из-за числа предложений; у нас спек будут единицы и десятки.
6. **Не вводить слой `specs/capabilities` (delta-модель OpenSpec)**, пока текущее поведение описывают `docs/design` и README пакетов; пересмотреть, когда одновременно будет много активных изменений с конфликтами по одним требованиям.
7. **Порог**: багфикс и правка в одном пакете без изменения контракта идут без спеки; спека нужна при изменении контракта `@lms/engine-contract`, схемы БД, нового пакета или экрана. Иначе процесс тонет в бумаге (Böckeler: баг → 16 критериев).
8. **Файловая структура активной фичи** — по ExecPlan: один файл-носитель с фиксированными разделами `Цель`, `Требования (проверяемые)`, `Решения` и живыми `Progress`, `Surprises & Discoveries`, `Decision Log`, `Outcomes`. Разделение на `SPEC.md` (стабильное) и `TASKS.md` (меняющееся) — вторая опция; аргумент за неё — проще чистить при закрытии, аргумент против — больше файлов для ревью.
9. **Закрытие фичи** — три действия: перенос долговечного в `docs/design`/README; ADR для решений, ограничивающих будущее; перенос в архив со статусом и `Outcomes`.
10. **Правила для агентов** (в `AGENTS.md`): читать активные спеки и ADR; архив — только по явной ссылке; в шапке архивной спеки — строка «исторический документ, не источник требований» (аналог PEP 1 и ответ на наблюдение Böckeler о дубликатах).

Решения для нашего репозитория приняты в §9.

## 9. Решение для проекта

Исходные данные `[ИЗМЕРЕНО]` по репозиторию на 2026-09-30: 119 коммитов в `develop` (один автор), 17 локальных веток `feature/*`, 14 merge-коммитов `--no-ff`, релизы настроены через semantic-release (`release.config.js`), правила и контекст агентов собраны в `AGENTS.md`, текущее состояние описано в `docs/design`, `engine-ts/design` и README пакетов. `[ВЫВОД]` Малый состав, активная работа агентов.

Выбрано: **облегчённая схема «один файл на активную фичу → архив → ADR по необходимости»**, без delta-слоя.

| Вопрос | Выбор | Почему именно так для этого проекта |
|---|---|---|
| Хранение завершённого | `specs/archive/ГГГГ-ММ-ДД-<имя>/SPEC.md`, дата — день слияния в `develop` | Дисциплины «не читай устаревшее» у малого состава не будет, агенту нужна физическая граница. Перенос делается `git mv` в той же ветке, отдельного шага не требует. Статус в шапке остаётся как второй сигнал |
| Число файлов | один `SPEC.md` в стиле ExecPlan: `Цель`, `Не цели`, `Требования`, `Решения`, `Progress`, `Surprises & Discoveries`, `Decision Log`, `Outcomes` | Агент может продолжить работу после сброса контекста из одного файла; меньше файлов на ревью (жалоба Böckeler); совпадает с исходной идеей `specs/<feature>/SPEC.md`. `TASKS.md` не нужен: `Progress` и есть список задач |
| Порог | спека обязательна при изменении контракта `@lms/engine-contract`, схемы RPC или БД, нового пакета, нового экрана или настройки; иначе не нужна. При сомнении — короткая спека на полстраницы | Список проверяем без суждения; багфиксы и правки внутри пакета не превращаются в бумагу |
| Delta-слой (`specs/capabilities`) | не вводить | Текущее поведение уже описано в `docs/design` и README пакетов; второй слой стал бы конкурирующим источником. Пересмотреть при устойчивых конфликтах между параллельными изменениями |
| ADR | `docs/adr/NNNN-название.md`, короткий формат MADR, создавать **только** при первом решении, ограничивающем будущее; папку заранее не создавать | Часть таких решений уже записана правилами `AGENTS.md` (например, настройки только в `engine.db`); ADR нужен для тех, что в `AGENTS.md` не попадают |
| Старые фичи | **не переносить задним числом** | История уже есть в `git log` и merge-коммитах `feature/*`. Ретро-спеки стоили бы времени и были бы менее точны, чем сами коммиты; вопрос «почему так» закрывается ADR по мере необходимости |

Шапка `SPEC.md`:

```yaml
status: draft | active | done | superseded | dropped
branch: feature/<name> # имя каталога = имя ветки
created: ГГГГ-ММ-ДД
closed: ГГГГ-ММ-ДД # заполняется при закрытии
pr: <номер> # заполняется при закрытии
touches: [engine, desktop] # пакеты @lms/*
depends-on: [] # другие активные спеки или ADR
supersedes: null # архивная спека или ADR
superseded-by: null
```

Правила для `AGENTS.md`:

1. Работа по пункту порога начинается с `specs/<feature-name>/SPEC.md`; имя совпадает с веткой `feature/<feature-name>`.
2. Источники требований: активные спеки из `depends-on`, `docs/adr/`, `docs/design`, README пакетов. `specs/archive/` без явной ссылки не читать и не использовать как источник требований.
3. Закрытие фичи в той же ветке до слияния: долговечное переносится в `docs/design` или README пакета; решения, ограничивающие будущее, — в ADR; `git mv` в `specs/archive/` с датой слияния, `status: done`, заполненные `Outcomes`, `closed`, `pr`.
4. Спека закрытой фичи неизменна; изменение поведения — новая спека со `supersedes`, в старой ставится `superseded-by`.
5. В первой строке архивной спеки: «Исторический документ. Не источник требований».

Отказ от альтернатив и когда вернуться:

- **Статус на месте без архива** — если спек станет мало и агенты не будут путать их с актуальными.
- **`SPEC.md` + `TASKS.md`** — если `Progress` разрастётся настолько, что мешает читать требования.
- **Delta-слой** — если появятся параллельные изменения, правящие одни и те же требования.
