engine-ts v1: слой бизнес-логики (TS-порт Trane + ts-fsrs), F1–F7

Порты и адаптеры: чистый синхронный домен, async DTO-фасад, журнал событий в SQLite; 4 пакета, хост в utilityProcess, раннер SQL — пул дочерних процессов, синхронизация папкой. Пояснения — engine-ts.md

Четыре пакета и границы

  • • @spirula/engine-contract: только типы DTO, коды ошибок, CONTRACT_VERSION; renderer-safe
  • • @spirula/engine: домен + приложение + fs/memory-адаптеры; модули authoring/, placement/, planning/, verify/, sync/; без electron и нативных зависимостей
  • • @spirula/engine-sqlite: better-sqlite3 13.0.3 за портом SqlDatabase; зависит от @spirula/engine только типами портов
  • • @spirula/engine-sql-runner: SqlVerifier и пул дочерних процессов на node:sqlite; зависит от @spirula/engine только типами портов
  • • ядро от sqlite и раннера не зависит: приложение регистрирует их в EngineDeps (eventStore, verifiers)
  • • @spirula/testkit: dev-пакет (FakeClock, SeededRng, TestId, билдеры), не публикуется

Процессы Electron

  • • main только супервизор: поднимает хост и перезапускает его (авто-перезапуска в Electron нет [ИЗМЕРЕНО]), держит single-instance lock
  • • хост движка — utilityProcess (решение владельца); код движка от этого не зависит
  • • renderer говорит с хостом по MessagePort, наружу идут только plain-DTO (structured clone)
  • • раннер SQL: пул дочерних процессов (не worker_threads: worker.terminate() не прерывает sqlite3_step); пулом владеет SqlVerifier в процессе хоста, дети — child_process.fork; kill процесса 1–8 мс [ИЗМЕРЕНО]
  • • наблюдатель RSS работает во всех профилях раннера (порог 256–400 МБ, опрос 20 мс)
  • • порождение детей внутри utilityProcess в настоящем Electron 44 — смоук M5 [НЕ ПОДТВЕРЖДЕНО]

Синхронизация папкой (F7)

  • • журнал устройства — SQLite: WAL, synchronous=FULL + fullfsync (≈ 3 мс на коммит [ИЗМЕРЕНО])
  • • каждое устройство пишет только свои неизменяемые сегменты <deviceId>/seg-*.jsonl и head.json в общую папку
  • • папку разносит файловый синхронизатор или Git; сегмент применяется целиком или остаётся pending
  • • слияние — множество + карантин конфликтов; вектор — непрерывный префикс seq; at по HLC-правилу
  • • iCloud, Syncthing, Dropbox, Git не проверялись [НЕ ПОДТВЕРЖДЕНО]

Из Trane: сохранено и изменено

  • • Сохранено: граф, DFS-планировщик, окна, knocker, rewards, фильтры
  • • PowerLaw → FSRS (вариант H) за интерфейсом ExerciseScorer
  • • practice_* → журнал событий и проекции, deltas удалены
  • • Clock и Rng инъектируются, единый holder опций
  • • Новое: компилятор курса, placement, план дня, ремедиация, проверка ответов, синхронизация

Проверено измерениями

  • • ts-fsrs next_state совпадает с py-fsrs (S ≤ 1.4e-7); next() расходится на 47% интервалов
  • • Открытие 3 000 уроков: 0.31–0.50 с из каталога, 33 мс из артефакта; журнал 500k: 0.21 с с маппингом
  • • Компилятор: 48 внесённых дефектов, 35 из 36 кодов; SQL: authorizer закрывает 27 из 30 угроз, проверка 0.06–0.15 мс на прогретом пуле
  • • Синхронизация: 65 тестов, 16 строк матрицы отказов, потерь 0; план дня 40 позиций — 1.6–2.7 мс
  • • Placement и неявный повтор измерены только в круговой синтетической модели

Слабые места

  • • F6 ремедиация: спайка нет, пороги (2 неудачи, 3 элемента) — предположения [НЕ ПОДТВЕРЖДЕНО]
  • • Неявный повтор выключен по умолчанию: без него в реальности удержание падает (0.99 → 0.42–0.47 в модели); нужен A/B
  • • Латентность батча в TS — оценка, замер на M3; потеря питания и Windows/Linux не проверялись
  • • Смоук раннера в настоящем Electron 44 и упаковка (pnpm + electron-builder) не пробовались
  • • AGPL на всё приложение: допущение A1; ts-fsrs 6.0-beta — pin 5.4.2
