# engine-ts: стратегия тестирования (vitest)

Статус: проект v1, 2026-09-29 (v0 + тесты F-слоя F1–F7: T-21…T-60, §7.1–7.2, §10–§13). Основной документ: `engine-ts.md` (§1.1, §5.1, §6a, §9, §11); контракт: `engine-ts-api.md`. Пометки: **[ИЗМЕРЕНО]** — прогнано, **[ВЫВОД]**, **[ОЦЕНКА]**, **[НЕ ПОДТВЕРЖДЕНО]**.

## 1. Принципы

- Тестируем поведение, границы, инварианты, переходы состояний, приоритеты и ошибки. Не тестируем проводку, копирование полей, «эхо» моков, исходный текст и случайные значения по умолчанию.
- Все источники недетерминизма инъектируются (`Clock`, `Rng`, `IdGenerator`, `CourseSource`, `EventStore`), поэтому доменные тесты быстрые, изолированные и воспроизводимые. SQLite и файловая система нужны только контрактным и интеграционным тестам.
- Эталон поведения — настоящий Rust-Trane v0.34.1 (коммит `6f5f84a`): расхождения ловятся golden-тестами, а не чтением кода.
- Тест, чьё утверждение проверяет реализацию Trane, а не наше поведение (формат serde, приватные функции, `Utc::now()`), не переносится слепо; его смысл переписывается под TS-API.
- Найденные дефекты Trane и порта становятся регрессионными тестами в момент обнаружения.
- Оракул не совпадает с реализацией: ожидаемые CSV для SQL-проверок, веса кредита и семантика `progress_reset` считаются вручную или брутфорсом. Ожидаемые значения, порождённые прогоном тестируемого кода, — тавтология; в спайке ручной расчёт сразу поймал арифметическую ошибку автора теста (`window-default-frame-peers`: 190/290 вместо 270/370) [ИЗМЕРЕНО].
- Утверждения о результатах симуляций с синтетическим или круговым учеником — инвариантные (детерминизм, границы, направление эффекта), не точные числа: числа спайков F3/F4 получены на моделях, которые подчиняются допущению метода (§12).

Запуск подмножеств: `vitest run --project unit`; типы: `vitest run --project types`; медленное: `vitest run --project property-slow --project process`; бенчмарки: `vitest bench --run --reporter=verbose` (фильтр по проекту — `--project "bench (bench)"`; в vitest 5 `bench` — фикстура теста, а не экспорт; таблица печатается только с `verbose`). Пороги покрытия — настройка CI; пороги `coverage.thresholds` в песочнице не проверялись [НЕ ПОДТВЕРЖДЕНО]. Дочерние скрипты на TypeScript (crash-child, sync-child, раннер) запускаются самим Node (`node --disable-warning=ExperimentalWarning child.ts`, Node ≥ 22.22 и 24 без `tsx`, как в спайках): синтаксис должен быть стираемым (`erasableSyntaxOnly`, без parameter properties и `enum`), импорты — с расширением `.ts`.

## 4. Дифференциальное тестирование против Rust-Trane

Метод проверен на `PowerLawScorer` (`engine-ts/research/report-powerlaw-port.md`): генератор на настоящем Rust-коде пишет JSONL, TS-порт сверяется. 5 919 кейсов, 90 из них — ошибки; повторный прогон генератора даёт побайтово тот же файл [ИЗМЕРЕНО].

| Уровень | Что сверяем | Источник эталона | Статус |
|---|---|---|---|
| **L1** чистые функции | `PowerLawScorer`, `WeightedRewardScorer`/`apply_reward`, `initial_reward`+propagation, `candidate_cost/weight`, `select_candidates` (длина), `dynamic_batch_size`, окна | публичный код Trane через harness (`tools/golden-rs`); приватные функции — через копию исходника в harness, как для `filter.rs` в спеках | PowerLaw готов; остальное M2–M3 |
| **L1b** FSRS | `MemoryModel`/`FsrsScorer` против py-fsrs 6.3.2 и Rust-адаптера `fsrs-scorer` | `engine-ts/spike/fsrs-check/fixtures/reference.json` (600 историй), Rust-адаптер | эталон py-fsrs есть; адаптер — M2 |
| **L2** агрегаты | `get_unit_score` всех юнитов после скриптовых последовательностей попыток; граф на реальных библиотеках | публичный API Trane; `dump-rs` (15 секций дампа графа) | граф: 0 расхождений на 6 библиотеках [ИЗМЕРЕНО]; оценки — M2 |
| **L3** ported unit | тесты Rust-модулей планировщика в виде vitest | инвентарь тестов в `engine-ts/research/spec-*.md` | M3 |
| **L4** распределение | частоты попадания упражнений в батч на скриптовом состоянии | Rust: 2–5 тыс. батчей на состояние (тред-RNG), таблицы частот в fixture | M3 |

**Допуски** (измерены на PowerLaw): критерий `|got − expected| ≤ atol + rtol·|expected|`, никогда чисто относительный (`urgency = 1 − R` и `velocity` около нуля). Дискретные исходы — Ok/Err и текст ошибки, `None`/`Some`, попадание в окно и переход через порог — **без допуска**.

| Выход | f32-двойник (строго) | f64 (продукция) | Основание |
|---|---|---|---|
| value | atol 1e-6 | atol 1e-5 | f32: максимум 4.77e-7 = 1 ulp; f64: 2.6e-6 вне разрывов |
| urgency | atol 2e-7 | atol 1e-6 | f32: 6e-8; f64: 2.4e-7 |
| velocity | atol 1e-9, rtol 1e-6 (фактически бит-в-бит) | atol 1e-2, rtol 5e-5 | шум сокращения f32 у Rust при секундных интервалах |
| пороги планировщика | 0 пересечений | ≤ 10 кейсов, каждый — «ничья» `|value − θ| ≤ 1e-5` | наблюдалось 7 |

**Правило двойника.** В модулях с чувствительными порогами (`PowerLawScorer`, `CandidateFilter`, `selectCandidates`) одна реализация с параметром `precision: 'f64' | 'f32'` (`r` = identity или `Math.fround`, порядок операций как в Rust); golden сверяются с f32-двойником строго, продукция создаётся без параметра. Причина не косметическая: квота окна `current` при success rate > 0.9 и `batch_size = 50` — 15 в f32 и 14 в наивном f64 [ИЗМЕРЕНО]. Разрывы f64 против f32 (условие «old-good floor» на почти-4.0 оценках) генераторы помечают и в f64-сверке не сравнивают.

**Ограничения паритета.** Сверка идёт с `scorer: 'power-law'`, `precision: 'f32'`, без deltas. Скриптовые состояния ограничены ≤ 2 попытками на упражнение: при ≥ 3 попыток Rust применяет награды и deltas, которых в TS-паритетном режиме нет (deltas удалены); награды покрывают L1 (чистые функции) и публичный `get_rewards`. Оценки `FsrsScorer` (вариант H) Rust-Trane не воспроизводит; они проверяются L1b и поведенческими тестами. Fixtures чувствительны к libm: `powf` сгенерирован на macOS arm64, на glibc до 0.3% вызовов могут отличаться на 1 ulp — TS-сторона переносима (V8 `Math.pow` детерминирован), допуски f32-двойника это покрывают; бит-точные проверки `velocity` (без `powf`) остаются жёсткими.

**L4: статистический тест.** Для скриптового состояния Rust сохраняет частоты `p_i` включения каждого упражнения и распределение размеров батча по `n₁` батчей; TS с фиксированным seed прогоняет `n₂` батчей на малой библиотеке (≤ 200 упражнений, около 1 мс на батч). Критерий: для каждого упражнения и урока с `p̂ ∈ (0.01, 0.99)` значение `|p₁ − p₂| / √(p̂(1−p̂)(1/n₁ + 1/n₂)) ≤ 4.5`; квоты окон и размер батча совпадают точно (f32-двойник). Прогон на трёх seed, все обязаны проходить, чтобы не подгонять seed. Ложная тревога на состояние ≈ 10⁻³ [ВЫВОД по нормальному приближению].

**Регенерация fixtures.** Только через `tools/golden-rs` с закреплёнными Trane `v0.34.1`, rustc и seed; рядом `MANIFEST.json` с sha256 каждого fixture и версиями; CI проверяет, что хеши не изменились без записи в `CHANGELOG` fixtures. Fixtures — тестовые артефакты в репозитории (для PowerLaw 3.5 МБ, gzip 0.65 МБ).

## 11. Ложные срабатывания и хрупкость

Ловушки, найденные в спайках (со ссылками) или проверенные при подготовке этого документа:

1. **fast-check + vitest: стрелочная функция с `expect` внутри свойства.** `fc.property(fc.integer(), (x) => expect(x).toBe(x))` в vitest 5.0.2 + fast-check 4.10.2 проваливается даже на верном утверждении (`Counterexample: [0]`, воспроизведено в песочнице) [ИЗМЕРЕНО]; в спайке `journal-sync` это выглядело как возврат `false`. Правило: тело свойства — блок `{ … }` без возвращаемого значения; выражение-предикат допустимо только когда `false` — намеренный отказ. Ложное свойство `x < 1000` fast-check ловит и даёт минимальный контрпример `[1000]` (§2). Кандидат на lint-правило.
2. **`Math.sign` и `-0`.** `Math.sign(-0)` — `-0`, `toBe` сравнивает через `Object.is`: `expect(Math.sign(-0)).toBe(0)` падает [ИЗМЕРЕНО]. Нормализовать `+ 0` перед сравнением (`Math.sign(x) + 0`) либо сравнивать знаки числами через `===`.
3. **ts-fsrs округляет до 8 знаков** (`forgetting_curve`, `next_state`). Свойства «S не убывает», «R монотонно по `w`» верны лишь до 1e-8: без допуска fast-check находит `S = 0.9999995`. Допуски: `atol 1e-8` для монотонности, `2e-8` для `R(now) = R0 + w(1 − R0)` (T-53); против py-fsrs — S ≤ 1.4e-7, R ≤ 7e-9 (T-07). Побитовое `toEqual` — только там, где сравниваются два прогона одного и того же кода (`rebuild == incremental`, T-24, T-52); точные `toBe` на значениях ts-fsrs запрещены.
4. **Параллельные фоновые `node` молча не стартуют.** В спайке `fire-plan` `node … &` из подоболочки не запустился (пустые логи); финальные числа получены последовательными вызовами. Отсюда `fileParallelism: false` в `process` и `property-slow`. Каждый тест, порождающий процесс, обязан проверить, что процесс что-то сделал: `exitSignal`, пустой `stderr`, непустая кампания (`count() > 100` в T-30) — иначе «ноль нарушений» получается из пустого прогона.
5. **Файлы результатов `*-mixed-code`.** `results/limits-node22-none-mixed-code.txt` и `limits-node24-none-mixed-code.txt` сняты, пока код префильтра правился по ходу (`report-sql-runner.md` §4): цифры из них доказательством не служат. Эталонные файлы в репозитории тестов несут `{node, sqlite, commit}`, а генерация эталона на неполном коммите отклоняется [ВЫВОД].
6. **Тесты не закрепляют случайные формулировки.** Тексты ошибок SQLite различаются по версиям и драйверам (`deep-subquery`: `sqlite_limit` на `node:sqlite`, `sql_error` на `better-sqlite3` — оба `failed`), `sqlite_version()` и `median`/`percentile` зависят от сборки, `ExperimentalWarning` шумит; диагностики компилятора — по коду и файлу (строка — только где детерминирована), не по тексту; порядок строк без `ORDER BY` совпал лишь на 9-строчной фикстуре. Пинуем `status` + `code`, не `reason`.
7. **Ошибка теста, выглядящая как ошибка дизайна.** При повторной порче того же файла тест сохранял уже испорченную копию, и «сходимость» падала на 11-м прогоне (`Counterexample: [-5,26]`). Правило: получив контрпример, сначала воспроизвести его с сжатым seed и проверить собственные фикстуры теста по составу векторов реплик, и только потом менять дизайн.
8. **Вывод в stdout теряется.** `console.log` внутри теста при запуске с `-t` и `| head` не показался; контрпримеры и результаты пишутся в файлы (`results/counterexamples.json`); репортёры `json`/`junit` vitest 5 пишут в `.vitest/` (§9).
9. **Молчаливые различия драйверов.** `node:sqlite` на Node 22 принимает опцию `defensive` и **игнорирует** её; `prepare('SELECT 1; DROP TABLE t')` выполняет только первый оператор (`better-sqlite3` бросает); `INSERT OR IGNORE` проглатывает нарушение `CHECK`. Тест обязан читать состояние обратно (проба возможности, число вставленных строк), а не считать, что успешный конструктор включил защиту (T-31, T-39).
10. **Эквивалентные мутанты.** Замена `<=` на `<` на границе `progress_reset` не меняет поведение (у двух разных записей ключ `(at, deviceId, seq)` не совпадает) — граничный тест на такой мутант не может упасть и не пишется (T-25).
11. **Ручные ожидания вместо сгенерированных.** Ожидаемые CSV для SQL-проверок и веса кредита считаются руками; сгенерированное эталонным SQL было бы тавтологией (§1).
12. **Файловая система.** Поведение `stat`, `ctime`, `ino` наблюдалось на APFS; на других ФС и на Windows — нет. Тесты `isFresh` (T-37) создают файлы и репозиторий в tmp на той же ФС, что и проверяемое поведение.
13. **TS 7 и дочерние скрипты.** `erasableSyntaxOnly` запрещает parameter properties (`constructor(private x)`) и `enum`; при `noEmit` и `.ts`-спецификаторах нужен `allowImportingTsExtensions`; скрипт, который Node запускает напрямую (`--experimental-strip-types`), с нестираемым синтаксисом падает с `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX` (`report-sql-runner.md` §9 п.8).
14. **Времена — односторонние границы.** Пороги по времени (kill, watchdog, бюджеты бенчей) зависят от машины и нагрузки CI: верхняя граница с запасом, никогда нижняя; точные числа спайков (kill 1–8 мс, 41–52 мс на респавн) — справка, а не утверждение.

## 12. Что тесты не доказывают

- **Синтетические и круговые модели ученика (F3, F4).** Истинное знание в F3 — случайный downset, а метод (жёсткое замыкание, λ = 1, K = ∞) угадывает структуру, заданную самим генератором; реальные ученики нарушают downset — не измерено. Accuracy завышена большим хвостом `unknown` (читать macro-F1); 60 учеников на ячейку, доверительные интервалы не считались. В F4 выигрыш от неявного повтора (очередь due 236 → 29; введено 292 из 300 уроков против 204) получен в модели, где ученик подчиняется той же модели, что планировщик; если неявного повтора в реальности нет, доля R ≥ 0.8 падает с 0.99 до 0.42–0.47 (плотный режим). Дрейф сложности `D` при 55–144 кредитах на попытку, κ < 1, сравнение `subtractive` и `multiplicative` — не измерены. Тесты T-45…T-48, T-50…T-56 доказывают инварианты и воспроизводимость, но не пользу метода для реального ученика; A/B на реальных ответах — веха M7.
- **Ремедиация (F6).** Спайка нет; пороги (2 неудачи, 3 элемента) — предположения. T-55 доказывает согласованность реализации с определением, а не педагогическую пользу.
- **Потеря питания.** SIGKILL (T-30) убивает процесс, а не ОС: всё, что передано в `write(2)`, остаётся в page cache и переживает убийство даже при `NORMAL`, поэтому нули в строке «потеря ACK-нутого батча» не отличают `NORMAL` от `FULL`. Не проверены: потеря питания и kernel panic, torn write сектора, переупорядочивание записей диском, кэш накопителя, ENOSPC/EIO, файл БД внутри синхронизируемой папки, эффект `fullfsync` на носителе.
- **Реальные файловые синхронизаторы.** iCloud, Syncthing, Dropbox, Git не запускались: матрица отказов имитирует поведение копированием и обрезкой файлов в одной ФС; порядок появления, задержки и конфликтные копии реальных инструментов не наблюдались. Не проверены: `SIGKILL` посреди `export()`, HLC на общем случайном расписании с перекосами (только модель двух устройств и записанные сценарии), устройство с часами 2099 года, реальные `git stash`/`git worktree`/Syncthing для `isFresh`.
- **Windows и Linux.** Спайки — macOS arm64 (APFS). Не проверены: `SIGKILL`/`ps -o rss=` (на Windows `ps` нет), `ctime` и `ino`, регистронезависимые ФС, симлинки, `fsync` каталога, libm (`powf` golden сгенерирован на macOS arm64), поведение `fullfsync`.
- **Настоящий Electron `utilityProcess`.** Спайк SQL-раннера — Node 24.21.0 без Electron; способ порождения процессов раннера изнутри `utilityProcess`, авто-перезапуск хоста и латентность `getBatch` в нём не проверены; vitest этого не покрывает — нужен отдельный смоук на M5 [НЕ ПОДТВЕРЖДЕНО].
- **Реальные курсы и SQL.** `sql-course` неполон (21 вопрос-заглушка без фикстур); DDL/DML-уроки (режим «скрипт + проба») не покрыты моделью «один SELECT»; ОС-песочница раннера не проверялась; реальный Rust-Trane на курсе с `engine`-frontmatter не запускался до T-36.
- **Производительность.** Замеры — одиночные прогоны на тёплом кэше, фикстура 9 строк, синтетические файлы ~130 Б; холодный кэш, 40k-файловая компиляция и RSS при 500k объектов не измерялись; реальные `.md` с медиа дороже при хешировании.
- **Версии SQLite.** Сверены только 3.51.3 и 3.53.4; порядок без `ORDER BY` на больших фикстурах с индексами, `ANALYZE` и `STAT4` может разойтись.
- **Покрытие мутациями.** Мутационная проверка выполнялась руками на `proj.ts` (три мутанта убиты из пяти, два выжившие эквивалентны) и на константах PowerLaw; автоматического мутационного прогона нет.
