Порога ≥90% за ≤100 проб достигают лишь 67% учеников (медиана 19 проб среди достигших). Модель (как в задании): `z_u = logit p_u`; pass на `u`: `z_u += log((1-s)/g)`, предкам на расстоянии k≤K: `+= λ^k·log((1-s)/g)`; fail: `z_u += log(s/(1-g))`, потомкам на расстоянии k≤K: `+= λ^k·log(s/(1-g))`. Расстояние — кратчайшее по **редуцированному** графу. Тема «решена», если `p≤0.15` (unknown) или `p≥0.85` (known; опционально при `minPass`≥N подтверждениях с весом λ^k≥0.5). Стоп: всё решено или бюджет. Допущенные оценщиком guess/slip (по умолчанию 0.05/0.05) — **не** обязательно равны истинным шуму ученика. Логиты ограничены ±30. Детерминизм: seed для тай-брейков, при тех же ответах те же пробы (тест).

Варианты: V0 случайная нерешённая тема (+пропагация); V1 p ближе всех к 0.5, без пропагации; V2 `unc·(1 + p·A + (1-p)·D)` где A/D = сумма λ^k по ещё нерешённым предкам/потомкам; V3 самая длинная цепь нерешённых тем, проба в середине (при равных цепях случайный выбор, детерминированный seed-ом).

Тесты (`test/*.test.ts`): p∈[0,1]; pass не уменьшает и fail не увеличивает ни одно p (fast-check, все 4 варианта × λ×K×prior×minPass); нет повторов проб, бюджет соблюдён, повторный `answer` бросает; детерминизм; счётчик нерешённых = число `uncertain`; **при безшумных ответах и любой конфигурации ни один known/unknown не противоречит истинному downset** (80 прогонов), а при `minPass=0`, flat prior фронтир равен истинному; цепочка из 32 тем: V3 ≤7 проб, V2 ≤12; V1 не пропагирует; транзитивная редукция и BFS-расстояния; sql-course; гейт.

## 2. Симуляция

Условия: слоистые DAG, N∈{200,1000,3000}, ширина слоя {5,15,40}, 1–3 пререквизита (70% из предыдущего слоя, остальное из 2–5 слоёв назад), 20 учеников на (N,ширина) → в ячейках таблиц **60 учеников** (3 ширины × 20) на (вариант,N,шум). Шум: (slip,guess) ∈ {(0,0),(0.03,0.03),(0.10,0.10)}; общий поток случайных чисел для всех вариантов (common random numbers). Оценщик считает guess=slip=0.05 (для «assumed.10» — 0.10).

DAG (сокращённо, из `tables.md`): N=3000 w=5: 5972 ребра → 5287 после редукции, макс. уровень 584; w=15: 199; w=40: 74. N=200: уровни 39/13/4.

**Истинное знание ученика** = случайный downset: целевой размер `m~U[0,N]`, набор растёт добавлением доступных тем, затем N шагов случайных add/remove. Распределение доли известных тем (N=3000, по 20 учеников): w=5 mean 43.0% (min 4.2, p50 40.4, p90 93.0, max 99.0); w=15 mean 55.6% (6.5/57.8/97.1/98.4); w=40 mean 40.5% (8.2/40.4/77.6/78.3). N=200 mean 37–44%, N=1000 mean 44–60%. Полная таблица — в `results/tables.md`.

Метрики: accuracy = (верные known + верные unknown)/N, `uncertain` считается ошибкой; false-known = предсказано known, истинно unknown (доля N); фронтир предсказанный/истинный — тема не known, все прямые пререквизиты known.

## 3. Что показали варианты (факты и причины)

1. **V1 (без пропагации) и V0/V2/V3 soft бесполезны на больших N**: p шагает по 2.9 лог-единиц за проб и пробы не покрывают 3000 тем (B/N).
2. **V2 hard с плоским prior хуже случайного (V0 hard).** Наблюдение: среднее нормализованное значение уровня первых 5 проб = 0.00 (все пробы в корнях: одноразовый скрипт вне репозитория, не сохранён: N=1000 w=15, 20 учеников, 5 проб). Причина (гипотеза, подтверждается измерением): при p=0.5 у всех тем коэффициент `unc` одинаков, `A+D` максимален у корней с максимумом потомков; pass корня решает лишь его самого — коэффициент покрытия завышает выгоду, т.к. взвешивает только «сколько сдвинется», а не вероятность исхода. С depth-aware prior V2 hard берёт первые пробы на уровне ≈0.50 и достигает 43 (N=1000) — лучше, но всё равно хуже V3.
3. **V3 не зависит от prior**: depth-prior не меняет V3 (точность совпадает до 0.1–0.3 п.п.; на N=200 depth prior даже хуже: 94.3% против 97.2% при B=100).
4. **Мягкая пропагация помогает только при большой дальности**: V2 l.85K6 (N=3000, B=100, шум 0.03) 69.4% против 19.2% у V3 soft (λ=0.7,K=3), 12.2% у V0 soft; на N=200 V2 l.85K6 — 94.1%.
5. **Ложное «known»** возникает из pass-по-угадыванию (g) на теме за границей знаний, которая затем через замыкание выдаёт «known» всем её предкам. Один угаданный pass на глубокой теме — сразу до сотен false-known. Поэтому false-known растёт с g, а `minPass=2` (два независимых подтверждения весом ≥0.5) гасит его: N=3000 шум 0.10: 7.1% → 1.0% от предсказанных known.
6. **Ложное «unknown»** (slip) при жёстком замыкании роняет всех потомков; на N=200 при 10% шуме 1.9% от N — самоисправляется ранними повторами.
7. `hi=0.95` при `minPass=2` дал идентичные числа с `hi=0.85` (после одного прямого pass p ровно 0.95) — граничный эффект округления `p>=0.95`; **[НЕ ПОДТВЕРЖДЕНО]** без отдельной проверки.

Frontier precision/recall (из `tables.md`): V3 hard N=3000 шум 0.03, B=40: P=0.37, R=0.71; B=100: P=0.48, R=0.80. Precision низкая потому, что предсказанный фронтир включает всю `uncertain`-границу (тема не known и все пререквизиты known) — то есть **фронтир завышается**, а не ошибочно «открывает» уже известное: повторное открытие темы лишь стоит одной вводной попытки.

## 4. Placement-маппинг и гейт Trane (пункт 3 задания)

`placementAttempts(lessons, classes, tsMs)`: для каждого урока с классом `known` — **по 2 попытки на каждое упражнение** (score=4 по умолчанию, шаг 1 с, `source:'placement'`). Гейт из Trane v0.34.1 (`passes_threshold`, порог из `PassingScoreOptions::default`: min_score 3.0, min_avg_trials 1.8): score урока = среднее по упражнениям (упражнение без попыток даёт 0 — так считает `get_lesson_score`? см. friction), avg_trials = среднее число попыток по упражнениям **с попытками**. 2 попытки при score 4 → avg trials 2.0 ≥ 1.8, score 4.0 ≥ 3.0 → открыт.

Проверено тестами (`test/placement.test.ts`):
- граничные случаи: 1 попытка на упражнение → avg trials 1.0 < 1.8 → закрыт; 2 попытки только на 1 упражнении из 3 → средний score 1.33 < 3.0 → закрыт; score ровно 3 при 2 попытках открывает, score 2 — нет;
- пример из 8 тем (граф: 0←1←2, 0←3, {2,3}←4, 4←5, 0←6←7), истинный downset {0,1,2,3,6}: безшумная диагностика V2 hard → known = {0,1,2,3,6} → 30 попыток → **строгий гейт открывает [4,7]**, что равно и диагностическому фронтиру, и истинному;
- sql-course (7 уроков, `reference/sql-course/lib_json`): диагностика находит downset {select,where,aggregate} менее чем за 7 проб; гейт открывает истинный фронтир.

**Опасность буквального Trane:** `passes_threshold` возвращает `true`, если хоть одно значение `None` (нет данных не блокирует). Тест `literal Trane` показал: при режиме `'trane'` **все уроки без попыток считаются пройденными**, гейт не блокирует ничего. Значит placement сам по себе гейт не «открывает» — в Trane реальную работу (кандидаты, `dead_end`) делает подсчёт `avg_score`/`avg_trials` в `get_candidates_from_lesson_helper` на уроках с данными, а урок без данных пропускается. Для F3 нужно явно проверить, как движок-порт обрабатывает уроки без попыток, до включения placement **[ВЫВОД]**; в тесте строгий режим это моделирует. Как именно Trane считает score урока без попыток (`get_exercise_score` для упражнения без попыток), я не проверял до конца: в `get_lesson_score` усредняются `get_exercise_score(id).ok()`; моё «0 для непройденного» — упрощение **[НЕ ПОДТВЕРЖДЕНО]**.

Числа — для модели «downset + независимый шум + V3 hard»; на живых учениках (забывание, частичное знание внутри темы, нарушения иерархии) будет хуже **[ВЫВОД]**.

| 1000 | B=20: 81.8%; B=40: 86.8%; B=60: 89.6%; B=100: 93.3% | 30–40 проб даёт 85–87%; 90% достижимо у 75% учеников медианой в 30 |

Нужно понимать, что accuracy тут завышена долгом большого «unknown» хвоста: у учеников с малым known-множеством большинство тем unknown, и 85% можно получить, почти ничего не спросив; поэтому смотреть надо на macro-F1 (0.86 при B=10, N=3000) и на F1 known.

**Когда false-known неприемлем.** Каждая ложная «known» открывает материал, которого ученик не умеет, и при жёстком замыкании порождает каскад. Наблюдения (V3 hard, B=40): 0.5–2.7% от N, но **2–18% от предсказанных known** при 3–10% шуме; N=200 хуже всего (18%) — на малом графе один угаданный pass даёт большую долю known. Практический порог **[ВЫВОД]**: если проверки детерминированы (SQL-раннер, g≈0, s≈0) — жёсткое замыкание безопасно (в безшумных прогонах false-known = 0.0% во всех ячейках). Если g ≥ 3% (проверка допускает угадывание, тест с выбором) — fk/known ≥ 2–8%, нужны меры ниже.

Что делать (по возрастанию цены):
1. **minPass=2 перед `known`** — измерено: fk/known на N=3000 шум 0.10: 7.1% → 1.0%; N=200: 18.2% → 7.6%; N=1000: 6.7% → 3.3%; цена: −4…−8 п.п. accuracy, доля достигающих 90% падает с 67% до 53% (N=3000). Рекомендуется по умолчанию для проверок с g>0.
2. **Ограничить пропагацию вверх K** (мягкая) — измерено, что мягкая пропагация K≤6 резко теряет точность (V2 l.85K6: 69% при B=100, N=3000); полезна только как поддержка, не как замена замыкания. Кап дальности при жёстком замыкании **не измерен**.
3. **Подтверждать placement ранними повторениями**: в журнале `source='placement'` попытки с низким весом, а первые повторения `known`-уроков включать в ближайший дневной план (F4). Не измерено **[ВЫВОД]**.
4. Для g>0 повысить порог: assumed guess 0.10 при истинном 0.03 (конфиг `assumed.10`) — без пропагации не работает (V2 soft assumed.10 ≈ V2 soft); при hard-замыкании не тестировался **[НЕ ПОДТВЕРЖДЕНО]**.
5. Финальный экран: показать ученику список тем `uncertain` и `known` на границе и дать «пересдать» — дёшево, но требует UI.

## 6. Ограничения

- **Синтетические ученики**: known-множество — случайный downset, то есть предположение «знания образуют downset» **зашито в генератор истины и в замыкание** — метод с λ=1,K=∞ угадывает структуру, которую мы сами сгенерировали (циркулярность). Реальные ученики нарушают downset (знают продвинутое без базового); результат для них **не измерен**.
- Шум независим между темами и между повторными пробами (пробы не повторяются). Забывания, усталости, зависимости ответов нет.
- DAG слоистый, сгенерирован автором; реальные курсы (SQL, math) могут иметь другую форму; sql-course (7 уроков) — только sanity.
- Учебный корпус: одна реализация оценщика; порог 0.15/0.85 и prior 0.5 не тюнились по отдельности; параметры `K∈{1,2,3,6,∞}`, `λ∈{0.5,0.7,0.85,1}` — небольшая сетка, не поиск.
- 60 учеников на ячейку: разброс между учениками большой (доля известного 2%…99%), поэтому различия <2 п.п. в таблицах не значимы; доверительные интервалы не считались **[НЕ ПОДТВЕРЖДЕНО]**.
- Время выбора пробы измерено при 9 параллельных процессах; `answer()` отдельно не замерялся.
- Число проб до 90% — по первому достижению в пределах 100 проб; ученики, не достигшие, исключены из медианы.
- Тесты проверяют инварианты и малые примеры, но не свойство «accuracy монотонно растёт с B» (не гарантируется при шуме).

## 8. Что вызвало трение

1. **`passes_threshold` при `None` → true** (Trane): пустой урок и урок без попыток проходят гейт, поэтому «placement» и «не проходил» неразличимы для гейта. Для F3 нужна явная семантика «нет данных = закрыто» в порте, иначе фронтир зависит от того, что считать данными.
2. **Гейт использует два разных агрегата** (средний score с нулями для непроверенных упражнений против средних попыток только по упражнениям с попытками) — отсюда правило «2 попытки на КАЖДОЕ упражнение»: 2 попытки на части упражнений урок не откроют.
3. **Транзитивная редукция меняет расстояния**: пропагация по «расстоянию k» зависит от редукции (избыточные рёбра сокращают пути). В `dag.ts` я использую расстояние по редуцированному графу; нужно зафиксировать, что диагностика всегда работает на редукции, иначе λ^k не воспроизводим.
4. **Coverage-приоритет (V2) без вероятности исхода вырождается** (все пробы в корнях при плоском prior). Простое «сумма λ^k нерешённых» — плохая оценка информационного выигрыша; V3 — устойчивее.
5. **Цена BFS-influence при K=∞ на N=3000**: списки достижимых O(N²) в худшем случае (для глубоких цепочек десятки МБ); построение при K=3 дёшево. Память не измерялась **[НЕ ПОДТВЕРЖДЕНО]**.
6. **Метрика accuracy обманчива при большом unknown**: тривиальное «всё unknown» даёт долю N-known; таблицы приведены с macro-F1 и uncertain, но порог «≥90%» без F1 может быть достигнут ничего не спросив у слабых учеников.
7. **`exactOptionalPropertyTypes` + `noUncheckedIndexedAccess`**: индексирование `Int32Array` возвращает `number|undefined`, весь горячий код приходится обвешивать `!`; при `erasableSyntaxOnly` нельзя использовать `enum`/параметр-свойства — классы пишутся вручную. Тесты fast-check: у `fc` в 4.10.2 нет `fc.GetType` — тип конфигурации выводится через `infer`.
8. **Node `--experimental-strip-types`**: `import.meta.url === \`file://${process.argv[1]}\`` для запуска-только-из-CLI, иначе `sim.ts` запускал бы симуляцию при импорте из `tables.ts` (константы вынесены в тот же модуль).
