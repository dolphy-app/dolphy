## 1. Реализация (что в коде)

`src/memory.ts` — `FireOptions` (единый объект констант: `lambda 0.9`, `minCredit 0.2`, `ratingMap [1,1,2,3,4]` (grade 1..5→Rating, «anki»-вариант из design), `implicitRatingCap 3`, `targetRetention 0.9`, `minNewFraction 0.25`, `passMinValue 3.0`, `passMinAvgTrials 1.8`, `valueScale 5`, `maxSameCourseRun 2`, `minTagDistance 2`, `fillWithNew`), `step`, `reviewReal`, `retrievability`, `stepFractional`.
`src/graph.ts` — `buildGraph(specs, 'trane'|'declared')` (Trane B.3.3–B.3.5: если ни один урок не объявляет `encompassed`, `encompasses = dependencies @1.0`; иначе объявленное + недостающие зависимости @1.0; режим `declared` — только объявленное, нужен для «нет encompassing» и «разреженный»), `CreditModel` (кредит урока-источника ко всем достижимым: `w_u = max по путям (∏ весов рёбер · λ^глубина)`, обрез при `< minCredit`; Дейкстра по максимуму, кэш по уроку).
`src/memory-index.ts` — `MemoryIndex`: `rebuild(log)` и `apply(entry)` (идемпотентно по `(deviceId, seq)`; поздний/внеочередной приход вставляется бинпоиском и **проигрывается весь журнал заново** — просто и измерено, не оптимально). Порядок `(at, deviceId, seq)`.
`src/planner.ts` — `Planner.planDay/planDayDetailed`: due (R≤target), `need=1−R`, провайдеры = упражнения открытых уроков (введённые или на фронтире), жадное взвешенное дробное покрытие с ленивой кучей (`gain=Σ min(residual,credit)·need`, ничья: случайный ключ, заданный в порядке id ⇒ детерминировано при равном seed), резерв `ceil(0.25·max)` слотов под новые (если есть), затем интерливинг (DFS с бюджетом узлов, три уровня ослабления: курс+теги → только курс → ничего, флаг `interleaveOk`). Вариант обновления остатка `'subtractive'` (по умолчанию: `residual −= min(residual,credit)`, как в задании) и `'multiplicative'` (`residual *= 1−credit`, покрыто тестами инвариантов, в симуляции не использован).
`src/gen.ts` — синтетические курсы (300/1500 уроков ×4 упр., ~3 зависимости из окна 12 предыдущих уроков курса, тег на урок из 24), три режима: `none`, `trane`, `sparse` (30% рёбер зависимостей получают вес U(0.3..1.0)); генератор журнала. `src/sim.ts`, `src/perf.ts`, `src/rng.ts` (mulberry32).

### Отклонения/решения, которых не было в задании (важно для прочтения результатов)
- **Фронтир.** Значение-прокси урока = среднее `R·5` по упражнениям с состоянием; `avgTrials` = среднее реальных попыток по ВСЕМ упражнениям урока (нулевые входят, как в Trane). Новый урок на фронтире, если **все** его зависимости «проходят порог» (введены, value≥3.0, avgTrials≥1.8). Я **не** реализовал «unknown = satisfied» для нетронутых зависимостей: в Trane «unknown» возникает для blacklisted/отсутствующих юнитов, а нетронутые зависимости там просто не достигаются DFS от стартовых уроков; здесь нетронутая зависимость блокирует. Уроки без зависимостей всегда на фронтире.
- **Новые упражнения**: сначала недоделанные упражнения уже начатых уроков, затем уроки фронтира по кругу между курсами.
- **Неявный кредит применяется по времени попытки** (`at`), реальное `trials` не увеличивается; кредит не получают упражнения без состояния; при провале кредита нет; `rating<2` (Again) не даёт кредита; рейтинг кредита `min(rating, Good)`.
- **Дробный шаг при t<1 дня**: `step(state, floor(t)=0, rating)` уходит в ветку short-term stability ts-fsrs (для Good/Easy `S·max(sinc,1)` ⇒ S+ = S, только рост R). Это следствие рецепта из задания, не баг кода.

## 4. Симуляция 90 дней

### 4.1 Постановка и ЕЁ ЦИРКУЛЯРНОСТЬ
Граф: 300 уроков × 4 упр., 6 курсов по 50 уроков, ~3 зависимости из предыдущих 12 уроков курса (граф зависит от seed). Три режима encompassing: `none`; `trane` (все зависимости @1.0); `sparse` (30% рёбер, вес U(0.3,1.0)). Бюджет 40 упражнений в день (бюджеты 10/20/40 — отдельный прогон `sim.ts budget`, п. 4.4), 90 дней, 6 seed (1..6; в таблицах mean [min..max]). Одно занятие в день в 09:00 UTC, попытки внутри дня с шагом 1 мин; план строится раз в день на старте и не адаптируется к провалам. Ответ ученика: `Bernoulli(R_true)`, для первого показа P=0.8 (допущение); успех → grade 4 (Good), провал → grade 1.
**Учeник — та же модель FSRS, что и в планировщике.** Основной прогон: истинная память ученика получает те же реальные обзоры **и те же неявные кредиты** (`truthHasCredit: true`) — то есть симуляция предполагает, что FIRe-кредит правдив, и потому **выигрыш P1/P2 в основных таблицах частично тавтологичен**: планировщик оптимизирует ровно ту модель, которой подчиняется ученик. Единственная проверка на «а если нет» — таблица 4.3 (`truthHasCredit: false`). Реального ученика/данных у нас нет.
Политики: **P0** — без неявного кредита в индексе, жадное «наименьший R первым»; **P1** — индекс с кредитом, планировщик без кредит-модели (наименьший R первым); **P2** — индекс с кредитом и жадное покрытие. Во всех политиках резерв 25% под новые и `fillWithNew`. Метрики считаются по истинному состоянию: backlog = число due (R≤0.9) на старте дня, среднее за дни 30..89; доля R≥0.8 — по введённым упражнениям на день 90.

| 0.7 | 83.4 / 223.3 \| 87.6 / 234.2 | 97.4 / 222.8 \| 88.5 / 233.7 | 139.9 / 219.2 \| 140.0 / 227.2 |
| 0.9 | 84.8 / 224.7 \| 82.0 / 238.5 | 87.5 / 225.3 \| 86.4 / 237.2 | 115.5 / 223.0 \| 107.7 / 235.0 |
| 1.0 | 79.5 / 224.5 \| 77.1 / 237.7 | 82.4 / 225.3 \| 79.6 / 237.7 | 101.3 / 224.5 \| 95.5 / 236.0 |
(Базовые P0: trane 236.5 / 204; sparse 248.9 / 209.2.)
Прочтение: (а) в **плотном** Trane-режиме результат почти не зависит от λ и MIN_CREDIT: при λ=0.9 порог 0.2 и 0.4 дают побитово те же числа (55.04 неявных обновл./попытку) — [ВЫВОД, глубину не измерял] значит наибольшая глубина кратчайшего пути в графе ≤ 8 (0.9⁸=0.43 ≥ 0.4), обрез по MIN_CREDIT не срабатывает, а высокая плотность с весом 1.0 покрывает почти всё; чувствительность проявляется лишь при λ=0.7/MIN=0.4 (fan-out вдвое ниже: 26.9 против 52–54 обновл./попытку — но backlog всё ещё 29.7). (б) В **разреженном** режиме порог важен: MIN_CREDIT 0.4 вдвое-втрое сокращает fan-out (1.8–3.7 против 3.9–6.9) и поднимает backlog с ~80–97 до ~100–140; выигрыш относительно P0 (249) остаётся, но уменьшается до ×1.8–2.5. (в) выигрыш P2 над P1 по числу введённых уроков почти постоянен (+11..+13 в trane, +5..+13 в sparse) — он определяется резервом слотов, а не λ. Разброс между seed (min..max) соизмерим с разницей между соседними ячейками sparse-таблицы (напр. backlog 62..108 при одной конфигурации), поэтому различия между соседними ячейками < ~10 backlog — шум.

### 4.6 Где компрессия НЕ помогает (из данных)
- **Нет рёбер encompassing** (`none`): P0=P1=P2 побитово (санити-проверка).
- **Разреженные рёбра**: P2 даёт лишь 1.11 покрытия на позицию и +5% уроков; backlog не меняется (86.4 vs 87.5, в пределах разброса 62..108).
- **Большой бюджет**: доля R≥0.8 упирается в 0.99 у всех политик; компрессия конвертирует сэкономленные слоты только в новые уроки, а они ограничены фронтиром и размером курса (потолок 300 уроков достигнут на 97%).
- **Метрика backlog**: считаем due по порогу 0.9 — упражнения «болтаются» около порога у P1 и P2 одинаково (28.5 vs 29.2), P2 backlog не уменьшает.
- **Если кредит неверен** (4.3): P2 хуже P1 (0.424 vs 0.469).
- Ограничение самой симуляции: план на день фиксирован; провал «сложного» упражнения отменяет весь кредит, а план об этом не знает (покрытия «ушли в никуда») — это занижает P2 в реальной жизни относительно идеала.

## 5. Ответы

**Защитима ли дробная модель?** Частично.
- Защитимо: (1) чисто вычислительно — свойства w=1↔реальный обзор, w=0↔тождество, монотонность R, S'∈[S,S+], непрерывность, отсутствие NaN — проверены; (2) она *самосогласованна* с FSRS: после шага R(now)=R0+w(1−R0) и последующее затухание идёт по той же кривой с новым S'; (3) дёшева (0.3 мкс).
- Слабо: (1) **нет эмпирического обоснования**, что R растёт на w(1−R0), а S — на w(S+−S) от неявной практики: FSRS обучен на *реальных явных ответах*, а неявный кредит — это допущение из FIRe (там оно эвристическое и для целых повторов с весами по «охвату»); (2) **сложность/difficulty**: `D' = D + w(D+−D)` с рейтингом Good снижает D при каждом кредите — при 55–144 кредитах на попытку D у базовых уроков неограниченно сползает к 1 ⇒ рост S будет завышен. Я это **не измерял** (нужен отдельный замер дрейфа D) `[НЕ ПОДТВЕРЖДЕНО]`; (3) рецепт `floor(t)` даёт ветку short-term при t<1 дня, S не растёт; (4) проходящий кредит применяется без учёта *качества* успеха (Hard/Easy) и без различия «неявно охваченный навык был реально задействован» — это про содержание курса, а не про формулу; (5) `S` не может убывать при rating≥2, но `next_state` округляет до 8 знаков, поэтому S+ иногда на 1e-8 меньше S (допуск в тесте) — кросс-совместимость с Rust-адаптером `[НЕ ПОДТВЕРЖДЕНО]`; (6) кредит зависит от `now`, а не от порядка: `rebuild` детерминирован по `(at, deviceId, seq)`, но **любое внеочередное событие пересчитывает весь журнал** (17.6 с на 500k в плотном режиме); для F7 (мультиустройство) этого недостаточно ⇒ нужны снапшоты/локальный пересчёт затронутых уроков `[ВЫВОД]`, не мерено.

**Известные слабости планировщика:** жадный набор покрытия оптимален лишь до (1−1/e) и завязан на `need=1−R`; остаточный `min(residual, credit)` — субтрактивная модель, при перекрытии нескольких провайдеров переоценивает суммарное покрытие (вариант `multiplicative` реализован, но в симуляции не сравнивался); план не адаптируется к провалам; интерливинг — эвристика с бюджетом узлов (на синтетике 60/60, на множествах ≤7 — оптимально по перебору); frontier-прокси `R·5` **не** есть Trane-`value` (у Trane — оценки 1..5 с окном 20 попыток).

**Какие параметры нужны от реальных данных до релиза:** (1) реально ли неявный повтор продлевает память, и с каким множителем κ на кредит (и одинаков ли он для «сложное охватывает лёгкое» и для «зависимость»; лучше явный A/B: часть лессонов с неявным кредитом, часть без, сравнить R по результатам последующего явного повтора) — ключевой параметр, симуляция 4.3 показывает цену ошибки; (2) λ, MIN_CREDIT, вес для дефолтных рёбер (в Trane «зависимость = 1.0» слишком щедро, потому что зависимость ≠ охват); (3) рейтинг неявного кредита (сейчас cap Good) и вклад в D; (4) начальная P(успех) для нового упражнения и `RatingMap`; (5) порог due (0.9) и `minNewFraction`; (6) правило фронтира (3.0/1.8 при value-прокси); (7) реальные размеры `encompassed`-fan-out курсов: плотный режим (43 урока в кредите на урок) даёт 144 обновл./попытку и 17.6 с rebuild на 500k событий.

## 7. Что не сделано / не подтверждено
- `[НЕ ПОДТВЕРЖДЕНО]` совместимость `stepFractional` с Rust-адаптером; дрейф D при массовом кредите; κ<1 (частично реальный кредит); сравнение `subtractive` vs `multiplicative` на симуляции; ≥5 seed для прогона 1500 уроков (только 1 seed); память проекции; учёт провала «сложного» упражнения внутри дня.
- Симуляции круговые по построению (см. 4.1); 4.3 — единственная проверка обратного допущения.
- Rebuild-бенчмарк использует равномерно случайный журнал (максимальный fan-out).

## 8. Что вызвало трение
1. **`forgetting_curve` и `next_state` округляют до 8 знаков**, поэтому «S не убывает при rating≥2» и «R монотонно по w» верны лишь до 1e-8; тесты нужны с допуском, иначе fast-check находит контрпримеры (`S=0.9999995`).
2. **`next_state(…, t=0, …)` при `enable_short_term=true` уходит в short-term ветку** — целочисленный `floor(t)` из рецепта для неявного кредита в первый день после последнего обзора даёт S+=S; дробность t (0<t<1) для S в ts-fsrs недоступна, а `R0` использует дробное t — расхождение между двумя шкалами времени в одном шаге.
3. **`forgetting_curve` привязан к `w` через `bind`**, а `computeDecayFactor` возвращает уже округлённый `factor`; формула обратной функции в задании (`tau = S/F·(R^(1/decay)−1)`) совпала с ts-fsrs (`decay=−w[20]`, `F=0.9^(1/decay)−1` с точностью 8 знаков — тест), но обратную функцию ts-fsrs не экспортирует — приходится дублировать.
4. **Семантика Trane B.3.4 «encompassing == dependency» — глобальный переключатель**: достаточно одного урока с `encompassed` в библиотеке, чтобы все остальные зависимости перестали автоматически считаться encompassed@1.0 в режиме «declared»; в режиме B.3.3 они добавляются — разница между «нет» и «разреженный» режимами определяется этим; два режима пришлось развести флагом `EncompassMode`.
5. **`MemoryIndex` зависит от порядка журнала по `at`, а не по `recordedAt`** (по дизайну), поэтому один поздний приход с другого устройства требует полного replay; API `apply` должен либо сообщать об этом, либо иметь `invalidateFrom(at)`.
6. **Порог фронтира требует «value» и `avgTrials`**, а FSRS-состояние их не даёт: пришлось ввести прокси `R·5`; интерфейс `PlannerState` должен получать value/avgTrials из отдельных проекций (Trane-`UnitScorer`), иначе F4 не согласуется с существующим фильтром кандидатов.
7. **Параллельные фоновые запуски `node` из подоболочки не стартовали** (пустые логи) — потратил время; последовательный запуск работает. Один `Command aborted` в ходе работы прервал бенчмарк планировщика (перезапущен).
