# F7 / журнал событий: проверка заявлений (spike `journal-sync`)

Код: `engine-ts/spike/journal-sync` (`src/`, `test/`, `results/`). Среда: macOS arm64 (Apple M5 Pro, 18 ядер), node v22.22.3, better-sqlite3 13.0.3 (SQLite 3.53.4), vitest 5.0.2, fast-check 4.10.2, TypeScript 7.0.2. Пометки: **[ИЗМЕРЕНО]** — получено прогоном; **[ВЫВОД]** — умозаключение, не замерено; **[НЕ ПОДТВЕРЖДЕНО]** — не проверено. `tsc --noEmit` — чисто; `vitest run` — 4 файла, 65 тестов, 34 с.

Модель, которую я реализовал (нужна, чтобы читать числа): состояние реплики — **множество** записей; `merge` — объединение множеств; «живые» записи, видимые проекциям, — чистая функция от множества (записи, попавшие в конфликт, остаются в множестве, но скрыты). Проекции: `AttemptIndex` (N=20, reset по предку курс>урок>упражнение), `FlagState` (LWW). Порядок — `(at, deviceId, seq)`; для записей с одинаковым `(deviceId, seq)` (бывает только при конфликте) добавлен `id` как последний ключ.

## 1. Итог: какие утверждения дизайна выдержали

| Утверждение (§5.1/5.2) | Итог | Основание |
|---|---|---|
| Слияние по `id` коммутативно/ассоциативно/идемпотентно | **Выдержало только в формулировке «состояние = множество записей + карантин конфликтов как функция множества».** Формулировка «конфликтующую входящую запись отклонить» (first-wins) **не коммутативна** — контрпример ниже | [ИЗМЕРЕНО] 3000 прогонов на свойство, seed 20260929 |
| `rebuild(merge(A,B)) == rebuild(merge(B,A))` | Выдержало (в т.ч. на «диких» логах с конфликтами; N=3 и N=20) | [ИЗМЕРЕНО] 3000 прогонов ×2 теста |

| Вектор `{deviceId: maxSeq}` даёт дельта-экспорт | **Не выдержало при переупорядочивании файлов**: нужен непрерывный префикс, не max; и вектор по одному не видит повторное использование seq | [ИЗМЕРЕНО] |

## 2. Property-тесты и контрпримеры

Команда: `npx vitest run test/merge.test.ts test/proj.test.ts`. Генераторы: устройства `a,b,c`, юниты `C > L1,L2 > E1..E4`, `at ∈ [0,25]` (узкий диапазон нарочно: много ничьих), «дикие» логи — крошечные алфавиты `id`/`(deviceId,seq)`, чтобы конфликты были частыми. Контрпримеры сохраняются в `results/counterexamples.json`.

Мутационная проверка чувствительности [ИЗМЕРЕНО]: три ручных мутанта `proj.ts` (reset только по самому юниту без предков; LWW флага «всегда перезаписывать»; fallback вместо пересчёта просто `count++`) убиты — падают 6, 2, 2 теста из 22. Два мутанта `<=`↔`<` на границе reset выжили: они эквивалентны, так как у двух разных записей ключ `(at,deviceId,seq)` не совпадает.

**Контрпример 1 — «отклонить конфликтующую входящую запись» не коммутативно** (shrunk fast-check): A=`[{id:i2, dev:a, seq:1, at:0, attempt E1 grade1}]`, B=`[{id:i2, dev:a, seq:1, at:0, unit_flag E1 blacklist set}]`. `mergeFirstWins(A,B)` оставляет attempt, `mergeFirstWins(B,A)` — флаг. Решение (реализовано, свойства проходят): обе записи остаются в множестве, обе скрыты из проекций, конфликт отчитывается (`id-content` или `seq-two-ids`).

**Контрпример 2 — конфликт, пришедший позже, отзывает уже применённую запись.** `apply(a#1)`, затем `apply(a#1 с другим id)`: инкрементальная проекция показывает 2 попытки, `rebuild(live)` — 0 (`conflict_retracts_live_entry`). Следствие: **обнаружение конфликта = `dirty` → полный rebuild**, а не инкремент. В `Replica` это так и сделано; тест `Replica` vs oracle проходит в fault-property.

**Контрпример 3 — перекос часов вперёд.** Устройство B с часами +1 сутки пишет attempt и флаг `blacklist=set`; устройство A с верными часами через 60 с после синхронизации пишет `progress_reset(C)` и `unset`. Итог при политике «`at = min(now, now+5мин)` по собственным часам писателя»: attempt переживает сброс, флаг остаётся включённым (`clock_skew_wall_policy`: `attemptAt=…086400000`, `resetAt=…060000`). Граница — свойство «сброс проигрывает ⇔ перекос ≥ 60 с» (500 прогонов, ±1 сутки). Зажим до now+5 мин ограничивает только запись «с запросом будущего `at`», но не собственные часы устройства. Проверено: с политикой `hlc` (`at = max(min(now, now+5м), max(увиденный at)+1, свой прошлый at)`) сброс, написанный после импорта, покрывает импортированную попытку для любого перекоса ±1 сутки (500 прогонов, свойство держится).

**Контрпример 4 — часы шагнули назад на одном устройстве** (NTP-коррекция, ошибка перевода времени): attempt(seq1) → reset(seq2) → часы −10 мин → attempt(seq3). При `wall` новый attempt получает `at` **меньше** собственного сброса и **игнорируется** (`alive=0`, `newAttemptAt=…999400000` < `resetAt=…000000000`). `monotonic` (`at ≥ последний свой at`) и `hlc` исправляют.

**Прочее, зафиксированное тестами** [ИЗМЕРЕНО]:
- Проекция зависит от **графа курса**, а не только от журнала: один и тот же журнал (attempt E1 + reset L1) даёт разные проекции, если обновление курса переместило E1 из L1 в L2. У двух устройств с разными версиями курса проекции разойдутся. Reset по предку лучше хранить с ним же «раскрытым» (список затронутых упражнений на момент записи) либо версионировать курс в записи — [ВЫВОД, не реализовано].
- `removePrefix` раскрывается на момент вызова: юнит, добавленный позже (или пришедший с другого устройства), не затрагивается (тест).
- Дубликаты в любом порядке и числе игнорируются; вектор по max(seq) даёт `{max:5, contiguous:2, missing:[3,4]}` для набора `{1,2,5}` — обнаружение дыр работает (`seqInfo`).
- Обнаружены собственные ошибки теста, не дизайна: `Math.sign` возвращает `-0`, `expect(0).toBe(-0)` падает (`Object.is`); стрелка `(x) => expect(...).toBe(...)` внутри `fc.property` — fast-check увидел `false`; после обёртки в `{ }` проходит.

## 3. FolderSync

Реализация: `src/folder-sync.ts` (+ `src/replica.ts`: реплика с id-индексом, непрерывным префиксом seq, карантином конфликтов, проекциями). Раскладка: `<syncDir>/<deviceId>/seg-<first>-<last>.jsonl`, `head.json` `{deviceId, maxSeq, segments[{name,firstSeq,lastSeq,count,sha256}], seen}`. Запись: temp-имя → `fsync` → `rename` → `fsync` каталога; строки сегмента — канонический JSON (`canon`, ключи отсортированы), поэтому sha256 воспроизводится на любом устройстве. Импорт: читает head, берёт сегменты с `firstSeq ≤ contiguous+1 < lastSeq+1`, проверяет sha256, число строк, схему каждой строки, `deviceId`, непрерывность seq; сегмент применяется целиком или не применяется. Отчёт: `{inserted, duplicates, rejected, pending, headErrors, corruptSegments, pendingSegments}`.

Три изменения появились **из-за падений моих тестов** (это результат, а не украшение):
1. Первая версия сравнивала только вектор `contiguous`: если импортёр уже имел диапазон seq 6–10, а устройство «восстановилось из бэкапа» и записало **другие** записи с seq 6–10, импортёр пропускал их молча (`rejected = 0`, тест упал). Исправление: журнал применённых сегментов `(dev/name#sha256)`; сегмент внутри уже покрытого префикса, но с неизвестным sha, перечитывается и даёт `seq-two-ids`. Реестр нужно **персистить** рядом с журналом; в спайке он в памяти [НЕ ПОДТВЕРЖДЕНО: после рестарта процесса без реестра импорт перечитает всё — цена 0.8 с на 500k, ниже].
2. Клон `deviceId` на двух машинах: вторая машина видела чужой `head.maxSeq` и экспортировала **ничего** (молчаливая потеря публикации). Исправление: `export()` пересчитывает sha256 последнего объявленного сегмента по собственным записям и бросает `DEVICE_ID_CLASH`.
3. `own` вывожу из журнала, а не из счётчика записанного: иначе после `checkRestore()` («догнали свой хвост из папки») экспорт считал бы собственные записи пустыми.

Размер: 183–184 Б/запись в JSONL (18.3 МБ на 100k, 92.0 МБ на 500k). Голова: ≈155–165 Б на сегмент, растёт линейно от числа сегментов. Повторный импорт без новых данных — <1 мс; повторный экспорт без новых записей — 14–144 мс (пересчёт sha последнего сегмента для проверки `DEVICE_ID_CLASH`; для крупного последнего сегмента дорого — ограничивать размер). Снимки проекций после импорта совпали с исходным во всех 7 прогонах (`converged: true`). Ограничения: один писатель; SSD APFS, тёплый кэш; реальный файловый синхронизатор (iCloud/Syncthing/Dropbox) и Git не измерялись [НЕ ПОДТВЕРЖДЕНО].

**Политика сегментов [ВЫВОД на основе таблицы]:** импорт от размера сегмента почти не зависит (0.6–0.85 М зап/с), экспорт зависит сильно из-за fsync (23k зап/с при 100 зап/сегмент против 180k при 1000). Пользователь пишет сотни записей в сутки, поэтому: один сегмент на сессию синхронизации (не на запись); **компактировать** сегменты старше ~30 суток в сегменты по ~10 000 записей: на 500k это 50 сегментов и head 8 КБ; без компактации 3 года по сегменту в сутки ≈ 1000 сегментов ≈ 150 КБ head — тоже терпимо. Компактация переименовывает сегменты, поэтому у каждого пира с префиксом перечитывается перекрытие (≈0.8 с на 500k) — приемлемо, но не бесплатно. Git-перенос: 92 МБ на 500k записей, старые сегменты неизменны, — это плюс; растущий head перезаписывается целиком (в Git — дельта ≈ размер head) [ВЫВОД].

## 4. SQLite EventStore (`src/sqlite-store.ts`, `src/crash-*.ts`, `src/bench-sqlite.ts`; выполнено подагентом, я проверил файлы результатов и прогнал `test/sqlite.test.ts` в общем `vitest run`)

Схема — ровно §5.1 (WAL, `foreign_keys=ON`, `user_version=1`). `appendBatch` — одна транзакция; `insertIgnore` — `INSERT OR IGNORE` + проверка `(device_id, seq)` с другим `id` как конфликта.

Команды:
```
node --disable-warning=ExperimentalWarning src/crash-driver.ts NORMAL 300 1 10   # results/sqlite-crash-normal.json, 205 с
node --disable-warning=ExperimentalWarning src/crash-driver.ts FULL   300 2 10   # results/sqlite-crash-full.json, 204 с
node --disable-warning=ExperimentalWarning src/bench-sqlite.ts                    # results/sqlite.json
```
Метод: одна и та же db переиспользуется во всех итерациях (WAL копится); ребёнок пишет батчи 1..50 (`extra={batch,size,idx}`), печатает `BEGIN` перед транзакцией и `ACK <lastSeq>` после `commit`; драйвер убивает `SIGKILL` через 20..400 мс (seed); каждая 5-я итерация — ручной `wal_checkpoint`; проверка — на копии db+`-wal` без `-shm`.

| | NORMAL | FULL |
|---|---|---|
| итераций / убито SIGKILL | 300 / 300 | 300 / 300 |
| ACK-нутых батчей / строк в базе | 10 553 / 271 498 | 10 196 / 260 063 |
| убито между `BEGIN` и `ACK` | 64 (из них 16 целиком в базе, 48 отсутствуют целиком) | 75 (26 / 49) |
| `integrity_check` ≠ ok, `foreign_key_check` ≠ ∅ | 0, 0 | 0, 0 |
| частично применённый батч, дубли `id`, дыры/нарушение порядка seq | 0, 0, 0 | 0, 0, 0 |
| потеря ACK-нутого батча | 0 итераций | 0 итераций |
| батч 200 000 строк, убийство на 10–90 % времени | 10/10 убито в транзакции, 0 строк осталось | 10/10, 0 |

**Чего SIGKILL не доказывает.** SIGKILL убивает процесс, а не ОС: всё, что передано в `write(2)`, остаётся в page cache ядра и переживает убийство даже при NORMAL. Поэтому нули в строке «потеря ACK-нутого» ожидаемы и **не отличают NORMAL от FULL**. Различие между ними (fsync WAL на каждый коммит) проявляется только при потере питания / kernel panic / отключении диска; такого теста нет [НЕ ПОДТВЕРЖДЕНО]. Не проверены: torn write сектора, переупорядочивание записей диском, кэш накопителя, ENOSPC/EIO, файл db внутри синхронизируемой папки. Гарантия, которую можно цитировать только из документации SQLite (не проверена мной): WAL+NORMAL не портит базу, но последние коммиты после последнего fsync могут откатиться; FULL их не теряет. На macOS `fsync()` не сбрасывает кэш накопителя; для этого нужен `PRAGMA fullfsync=ON` (в этой сборке `fullfsync=0`, `checkpoint_fullfsync=0` по умолчанию — проверено `PRAGMA`). 300 итераций — статистика по конкретному расписанию, не доказательство отсутствия редкого окна.

## 5. Рекомендуемые изменения дизайна

1. **§5.1 порядок и слияние [ВЫВОД, подтверждено тестами]:** ключ порядка `(at, deviceId, seq)`; при равенстве `(deviceId, seq)` (только конфликт) добавить `id`. Состояние слияния — множество записей; конфликт (`id` с разным содержимым либо `(deviceId, seq)` с двумя `id`) = **обе** записи скрыты из проекций и попадают в отчёт `conflicts[]`; при появлении конфликта проекции пересобираются полностью, не инкрементально.
2. **Часы:** заменить «`at` ≤ now+5 мин» на HLC-подобное правило на записи: `at = max(min(now, now+5мин), maxAtУвиденный+1, свойПрошлыйAt)`. Проверено: сброс/`unset`, написанные после импорта, всегда побеждают импортированное (перекос ±1 сутки), шаг часов назад безопасен. Риск, не измеренный: устройство с часами в 2099 году «отравляет» `maxAtУвиденный` у всех — нужен отсев на импорте (например, `at > recordedAt + 24 ч` → карантин) [ВЫВОД, не реализовано]. Хранить `recordedAt` как есть — по нему можно диагностировать перекос.
3. **Вектор:** `{deviceId: contiguous}` (непрерывный префикс), не `maxSeq`; отдельно `missing` из `seqInfo`. Плюс реестр применённых сегментов `(deviceId/name#sha256)` в БД — иначе повторное использование seq в уже покрытом диапазоне невидимо.
4. **Защита `deviceId` от восстановления/клона:** (a) в `head.json` публиковать `seen: {deviceId: contiguous}` — тогда пир знает, сколько наших записей видел; (b) при старте `checkRestore()`: если `max(folderMax, peerSeenMax) > localMax` — сначала импортировать свои сегменты из папки и продолжать с `maxSeq+1`; если данных нет нигде, **форк**: новый `deviceId`, seq с 1 (старые записи остаются под старым id); (c) `export()` проверяет sha последнего сегмента и бросает `DEVICE_ID_CLASH` вместо молчаливого no-op. Хранить `deviceId` в `meta` и в файле рядом с папкой данных **не** в синхронизируемом каталоге. Ручной сценарий «восстановил бэкап, пиры не видели, папка откатилась» отловить нельзя — только конфликт `seq-two-ids` и решение пользователя: в этом случае 10 настоящих записей скрыты, пока не выбрана сторона [ИЗМЕРЕНО].
5. **Reset и граф курса:** семантика `≤` и покрытие предков выдержали. Но проекция зависит от версии графа: записывать в `progress_reset` раскрытый список `exerciseIds` (или версию курса) либо документировать, что перемещение упражнения между уроками меняет проекцию на устройствах с разными версиями курса [ВЫВОД].
6. **Сегменты:** сегмент = одна сессия синхронизации; компактация старше ~30 суток до ~10 000 записей/сегмент; ограничить размер сегмента, чтобы проверка `DEVICE_ID_CLASH` (пересчёт sha последнего сегмента) была дешёвой (при 100k в одном сегменте — 144 мс на каждый пустой экспорт).
7. **SQLite:** оставить WAL. Для пользовательских данных, где потерю последнего часа терпеть нельзя, — `synchronous=FULL` **и** `fullfsync=ON` на macOS (≈3 мс на коммит; одна попытка — один коммит, это не мешает). NORMAL допустим, если откат последних коммитов после потери питания приемлем, — этот сценарий не измерен. Импорт делать батчами по ~1000 в одной транзакции; `INSERT OR IGNORE` глотает и нарушения CHECK — проверять факт вставки.
8. **Замечание к §5.2:** цифра «≈0.1 с на чтение 500k» — устарела: 0.21 с с маппингом, тёплый кэш.

## 7. Что не сделано / не проверено

- [НЕ ПОДТВЕРЖДЕНО] потеря питания (NORMAL vs FULL), torn writes, холодный кэш, ENOSPC/EIO.
- [НЕ ПОДТВЕРЖДЕНО] реальные файловые синхронизаторы (iCloud, Syncthing, Dropbox, Git) — поведение имитировано копированием/обрезкой файлов в одной ФС; порядок появления, задержки и конфликтные копии реальных инструментов не наблюдались.
- [НЕ ПОДТВЕРЖДЕНО] `RewardIndex` (§5.2) и FSRS-состояние — только `AttemptIndex` и `FlagState`.
- Реестр применённых сегментов в спайке — в памяти; при старте процесса без него импорт перечитывает всё.
- Запись `own` в реплике — в памяти; поведение при сбое между `rename` сегмента и заменой head проверено косвенно (сегмент без head игнорируется), отдельный тест на убийство процесса посреди `export()` не писался.
- Политика HLC проверена только на модели двух устройств и записанных сценариях, не на общем случайном расписании с перекосами.

## 8. Что вызвало трение

- **Конфликт при слиянии:** формулировка «по `id`, конфликт отклонить» звучит естественно и ломает коммутативность; чтобы `merge` остался решёткой, пришлось хранить отклонённое.
- **`(deviceId, seq)` не уникален в порядке** при конфликте — понадобился четвёртый ключ `id`, иначе порядок не полный.
- **Вектор `maxSeq`** — на первой версии импорт молча пропускал подменённый диапазон; тест упал с `rejected=0`.
- **Клон `deviceId`** — сначала «работал»: `export()` без ошибки публиковал ничего. Ошибка была бы видна только на втором устройстве спустя недели.
- **`own` как счётчик** ломал догон после `checkRestore()` — источник истины должен быть журнал.
- **TS 7 `erasableSyntaxOnly`** запрещает `constructor(private x)` — пришлось переписать конструкторы на явные поля; для `.ts`-спецификаторов при `noEmit` нужен `allowImportingTsExtensions`.
- **fast-check + vitest:** `Math.sign` даёт `-0`, `toBe` использует `Object.is`; стрелка `fc.property(…, (x) => expect(…).toBe(…))` в моём случае воспринималась как возврат `false`; `console.log` из теста при запуске с `-t` и `| head` не показался — контрпримеры пишу в `results/counterexamples.json`.
- **Тестовый баг, выглядевший как дизайн-баг:** при повторной порче того же файла я сохранял уже испорченную копию — «сходимость» падала на 11-м прогоне (`Counterexample: [-5,26]`), пока не исправил тест. Проверил, что причина в тесте, по составу векторов реплик, а не списал на дизайн.
- **`better-sqlite3`:** `INSERT OR IGNORE` проглатывает и CHECK-нарушения; на macOS `fullfsync` по умолчанию выключен, `synchronous=FULL` без него почти бесплатен и почти бесполезен для носителя.
