# packages

Пакеты слоя бизнес-логики `engine-ts` (проект — `engine-ts/design/`). Все пакеты — ESM, `private`, исходники в `src/`, тесты в `test/`. Импорты между пакетами идут прямо в исходники (`exports` → `./src/*.ts`), сборки нет: `dist/` содержит только `.d.ts` для `tsc -b`.

## Карта

| Пакет                    | Что                                                                  | Зависит от                                        |
| ------------------------ | -------------------------------------------------------------------- | ------------------------------------------------- |
| `@lms/engine-contract`   | типы DTO, `CONTRACT_VERSION`, `MAX_SQL_CHARS`, `RPC_METHODS`, `Rpc*` | —                                                 |
| `@lms/engine`            | домен, порты, приложение, fs/memory-адаптеры (`./ports`, `./node`)   | contract, ts-fsrs, yaml, zod                      |
| `@lms/engine-sqlite`     | `EventStore` на better-sqlite3                                       | engine, better-sqlite3                            |
| `@lms/engine-sql-runner` | `Verifier` для SQL в дочерних процессах                              | engine, better-sqlite3 (запасной профиль Node 22) |
| `@lms/engine-rpc`        | RPC: `./client` (renderer, без zod), `./host` (диспетчер, zod)       | contract, engine, zod                             |
| `@lms/testkit`           | часы, RNG, id, билдеры журнала и библиотек (dev-пакет)               | contract, engine, fast-check                      |

`@lms/engine` экспортирует подпути `./ports`, `./app`, `./node` (fs-адаптеры: `createNodeFsCourseSource`) и `./authoring` (сканер, компилятор курса, артефакт, `LibraryHolder`; `yaml` подгружается только компилятором). CLI компилятора — `pnpm -F @lms/engine engine-cli validate|compile <каталог библиотеки>` (`src/cli`, код выхода 1 при ошибках, 2 при неверных аргументах). `@lms/testkit` подключён в корневой `package.json` (`workspace:*`), поэтому тесты любого пакета импортируют его без цикла зависимостей `engine ↔ testkit`.

`@lms/engine/sync` — слияние журнала: `createReplica` (множество записей + карантин конфликтов `id-content`/`seq-two-ids`/`clock-skew`, вектор — непрерывный префикс, `exportSince`/`import` ≤ 5 000 записей, локальное `resolveConflict`), сегменты и `head.json` общей папки (`encodeSegment`, `decodeSegment`, `parseHead`), `importFromTrane` (порт чтения `TraneSource`), `parseEntry`/`canon`/`compareEntries`. Алгоритм слияния написан один раз поверх синхронных примитивов `StoreTx` порта `EventStore` (`engine/src/ports`): адаптеры хранилища реализуют только их. Хранилища: `createMemoryEventStore` и `createFolderSync` (общая папка сегментов, защита `deviceId`: `checkRestore`, `SYNC_DEVICE_ID_CLASH`) — в `@lms/engine/node`; `openSqliteEventStore` (WAL, `synchronous=FULL` + `fullfsync` на macOS, `durability: 'normal'`, порт `SqlDatabase`, миграции — `.sql`-строки, `STORE_BUSY`/`STORE_READONLY`/`STORE_CORRUPT`) и `readTraneDirectory` (`.trane/*.db`) — в `@lms/engine-sqlite`. Один набор контрактных тестов `EventStore` (`engine/test/store/contract.ts`) и одни свойства слияния и матрица `FolderSync` (`engine/test/sync/`) прогоняются на обоих хранилищах.

Проверка ответов (M5, F5): `@lms/engine/verify` — `GradePolicy` (`passAtN`: pass@1 → 5, pass@2 → 4, pass@3+ → 3, `gave-up` → 1, `null` — нужна самооценка; вердикты `error` не считаются) и хелперы вердиктов; `@lms/engine-sql-runner` — `createSqlVerifier({ source, logger, spawnWorker? })`: порт `Verifier` с `runner: 'sql'` поверх пула дочерних процессов `min(4, cores − 1)` (`recycleAfter`, респавн в фоне, kill по `timeoutMs + 100 мс` и по RSS, наблюдатель RSS обязателен). Драйвер выбирается пробой возможностей: `node:sqlite` с `setAuthorizer` и `db.limits` (профиль `full`) или better-sqlite3 (запасной профиль: `query_only`, read-only хэндл, префильтр). `fixture` и `expected` читаются из библиотеки через `source` (пути от корня), `verification.reference` — эталонное решение. Компилятор с `compile(source, { runChecks: { verifiers } })` прогоняет эталоны через порт и выдаёт `E_REFERENCE_FAILS` (`@lms/engine/authoring`: `checkReferences`); CLI — `engine-cli validate|compile <каталог> --run-checks` (пакет раннера подгружается динамически: ядро от него не зависит). Бюджет T-44 (1 000 проверок ≤ 1 с на прогретом пуле): `pnpm -F @lms/engine-sql-runner bench`, в `pnpm test` не входит. Смоук в настоящем Electron 44 (порождение процессов раннера из `utilityProcess`) — за проводкой `apps/desktop`, здесь не проверялся.

Планировщик (M3, F4): `@lms/engine/scheduler` — порт планировщика Trane. `createDepthFirstScheduler`: поиск DFS по графу → `ReviewKnocker` → `CandidateFilter` (окна мастерства с поправкой на success rate, взвешенная выборка без возвращения через порт `Rng`) → пул повторов → `Shuffler`; единый холдер опций `createSchedulerOptionsHolder` (`verify`, атомарный `set`, подписчики; компоненты читают опции при каждом вычислении, а не хранят клоны); `SessionState` (карта показов, пул повторов, счётчики успеха; `reset()` — `startSession`); чистые `getFrontier` (нет данных = закрыто; юнит без валидных упражнений прозрачен) и `getDue` (R по `MemorySource`); фильтры Trane и zod-кодеки wire (`filters.ts`, `filter-codec.ts`); `toScoringGraph` (`UnitGraph` → `ScoringGraph`). Источники состояния — узкие интерфейсы (`AttemptSource`, `RewardSource`, `BlacklistView`, `ReviewListView`, `SavedFilterSource`, `MemorySource`), проекции журнала их реализуют. Хранилище настроек ученика — `createJsonSettingsStore`/`createMemorySettingsStore` в `@lms/engine/node`. Тесты — `packages/engine/test/scheduler` (тестовый мир `helpers/world.ts`); эталон Rust — `test/scheduler/golden` (генераторы `golden-rs`: `scheduler_l4_golden`, `scheduler_frontier_golden`). Бенчмарк NF1 — `pnpm -F @lms/engine bench` (свой конфиг, в `pnpm test` не входит).

Адаптивный слой (M6, F3/F4): `@lms/engine/placement` — диагностика: `buildTopicGraph` (уроки на транзитивной редукции, CSR вверх/вниз), `createDiagnosticSession` (только V3 с жёстким замыканием λ = 1, K = ∞: проба — середина самой длинной цепочки нерешённых тем; логиты, пороги 0.15/0.85, `minPass = 2` для проб с угадыванием; `nextProbe` идемпотентен до ответа, детерминизм по (seed, ответы) — выбор пробы и пропагация побитово совпадают со спайком `spike/diagnostic`), `buildPlacementTopics` (пустые и blacklisted уроки прозрачны, проба — упражнение с `engine.verification`), `placementAttempts` (по 2 попытки на упражнение `known`-уроков, оценка 4, круги по порядку). `@lms/engine/planning` — `createPlanner` (due по R, жадное покрытие с ленивой кучей, резерв 25% под новое, ремедиация перед новым, интерливинг `interleave`; состояние приходит снаружи `PlanState`), `createMulberry32`/`createSeededRng` (uint32-seed → `Rng`), `createFractionalStepper` (`stepFractional` над портом `MemoryModel`; кривая забывания задана явно и сверяется с моделью), `buildPlanGraph` (`declared` — только объявленные `encompassed`; `graph` — с автоправилом Trane), `createCreditModel` (`λ`, `minCredit`, `κ`), `createMemoryIndex` (проекция `{S, D, lastAt}`; кредит выключен по умолчанию, в v1 не меняет `D`), `collectDue`. Сервисы `plan.getDay` и `placement.*` — `engine/src/app/services/{plan,placement}.ts`.

## Команды (из корня)

| Команда                    | Что делает                                                                 |
| -------------------------- | -------------------------------------------------------------------------- |
| `pnpm typecheck`           | `tsc -b` (TS 7) в каждом пакете: проект `src` и проект `test`              |
| `pnpm test`                | `vitest run` по проектам всех пакетов (`vitest.config.mts` → `packages/*`) |
| `pnpm -F @lms/engine test` | тесты одного пакета; `pnpm -F <имя> typecheck` — типы одного пакета        |
| `pnpm lint` / `pnpm fix`   | ESLint + Prettier для всего репозитория                                    |

## TypeScript 7 и корневой typescript

`typescript-eslint` и `vue-tsc` (`apps/desktop`) не работают с TS 7, поэтому корневой `typescript` остаётся `^6.0.3` (для ESLint и desktop). TS 7.0.2 подключён как `devDependency` каждого пакета `packages/*`; `tsc` запускается из пакета (`pnpm exec tsc`, ближайший `node_modules/.bin`) и берёт версию 7. Вызов `node_modules/.bin/tsc` в корне даст TS 6.

Конфиги: `tsconfig.base.json` (`strict`, `erasableSyntaxOnly`, `verbatimModuleSyntax`, `module esnext`, `moduleResolution bundler`); в пакете `tsconfig.json` — проект `src` (`composite`, `emitDeclarationOnly`, вывод в `dist/`), `tsconfig.test.json` — проект `test` (`noEmit`, ссылки на `src` и `testkit`). Корневой `tsconfig.json` — «решение» со ссылками на всё. `tsconfig.vitest.json` (contract, engine) — конфиг для typecheck-режима vitest без ссылок: он читает исходники, а не устаревший `dist/`.

## Тесты

Тип-тесты — `test/**/*.test-d.ts` (в `engine-contract`, `engine`): падают и в `pnpm typecheck`, и в `pnpm test`. `RPC_METHODS` сверяется с методами `LearningEngine` (`test/rpc-keys.test-d.ts`): лишний и пропущенный ключ — ошибка типов. Эталон py-fsrs для `MemoryModel` — `engine/test/fixtures/reference.json` (600 историй, 18 564 обзора; `gen_reference.py` — генератор), проверка — `engine/test/contract/memory-model.test.ts`.

Тяжёлые прогоны — по переменным окружения: `ENGINE_FULL_PROPERTIES=1` (слияние 3 000 прогонов на SQLite, сходимость `FolderSync` 150 прогонов на каждом хранилище, ≈ 1,5 мин), `ENGINE_CRASH_ITERATIONS=300` (SIGKILL-тест SQLite: 300 убийств на режим `NORMAL` и `FULL`, ≈ 205 с на режим в спайке; по умолчанию 15). Полная кампания со сводкой: `pnpm -F @lms/engine-sqlite crash NORMAL 300 1 10` (аргументы: режим, итерации, seed, «больших» транзакций, строк в них).

CI: job `typecheck` и `test` на Node 22 и 24, `lint` — на версии из `.nvmrc`.
