# Права и изоляция сторонних расширений

Живой документ, пока `status` — `draft` или `active`: `Progress`, `Surprises & Discoveries`, `Decision Log` обновляются вместе с кодом. По завершении фичи переносится в `specs/archive/` и не меняется. Правила — скилл `spec-workflow`.

## Цель

Расширение, которое поставил не мы (пользовательское или из режима разработки), по умолчанию работает в рамках: его код исполняется в ограниченном процессе и получает только объявленные в манифесте возможности, а его элементы интерфейса живут в изолированной рамке и не видят окно приложения. Пользователь видит в «Настройки → Расширения», что расширение просит, может его отключить или явно доверить (снять изоляцию). Расширения из поставки работают как раньше.

Это ответ на пункт «права и изоляция» из плана после `extension-contributions`; ADR 0002 принял риск, а эта спека его снижает там, где Chromium и Node дают настоящие механизмы, и честно называет то, что остаётся открытым (ADR 0003).

## Не цели

- Граница безопасности против намеренно вредоносного кода в Node: режим разрешений Node («Permission Model») по своей документации — «ремень безопасности», а не граница; ограничение сети им не задаётся. Настоящая изоляция на уровне ОС (контейнеры, sandbox-профили) сюда не входит.
- Подписи пакетов, проверка издателей, обзор кода, каталог и установка из приложения.
- Запрос разрешения у пользователя при каждом действии (runtime prompts): разрешения объявляются в манифесте и показываются заранее.
- Изоляция расширений из поставки.

## Требования

Наблюдаемое поведение, не реализация. У каждого требования есть проверка.

- R1. Манифест может объявить `permissions` — список из `library.read`, `process.spawn`, `worker.threads`, `native.addons`, `network`; дубли и неизвестные имена отклоняются. Без объявления у кода расширения нет ни одного разрешения. Проверка: тесты манифеста; `lms-ext validate` печатает ошибку неизвестного разрешения.
- R2. Код расширения не из поставки и не доверенного исполняется в отдельном ограниченном Node-процессе: чтение файлов только из каталога расширения, запись, запуск процессов, потоки и нативные модули запрещены, если не объявлены (`process.spawn` → запуск процессов, `worker.threads` → потоки, `native.addons` → нативные модули); `library.read` даёт `ctx.library` (чтение библиотеки курсов через посредника, а не прямой доступ к файлам). Окружение процесса минимально (без переменных окружения приложения). Попытка сделать запрещённое даёт ошибку внутри расширения (`ERR_ACCESS_DENIED` или `PermissionError`), а не падение хоста: проверка вида задания возвращает вердикт `error`, движок и остальные расширения работают. `network` объявляется и показывается, но не ограничивается (Node этого не умеет). Проверка: unit (сопоставление разрешений и флагов, посредник библиотеки); e2e с «враждебным» расширением, которое читает `/etc/hosts`, пишет в `/tmp`, запускает процесс и обращается к `ctx.library` без объявления.
- R3. Элементы ввода ответа и рендереры содержимого недоверенных расширений исполняются в `<iframe sandbox="allow-scripts">` без `allow-same-origin`: у рамки нет доступа к `window.lms`, DOM и хранилищу приложения. Рамка получает свойства (`view`, `value`, `disabled`, `verdict`) и тему через `postMessage`, возвращает ответ, отправку и высоту; ввод, фокус с клавиатуры, Ctrl/⌘+Enter, тёмная тема работают как у обычного элемента. Проверка: unit (мост, проверка источника сообщений); e2e: ввод ответа в рамке принимается, «враждебный» элемент не достаёт `parent.lms`.
- R4. Доверие и включение: у расширения не из поставки в «Настройки → Расширения» два переключателя — «Включено» и «Доверять» (без изоляции), плюс список объявленных разрешений. Состояние хранится в `engine.db`, действует сразу для новых проверок; отключённое расширение не даёт ни видов заданий, ни тем, ни рендереров, ни правил оценки, и отображается как отключённое. Расширения из поставки переключить нельзя. Пользовательская копия с id расширения из поставки — обычное пользовательское расширение. Проверка: тесты настройки (хранилища, сервис, RPC), e2e: отключение, доверие, изоляция по умолчанию.
- R5. Режим разработчика (`LMS_DEV_EXTENSIONS`) не требует ничего дополнительного: расширение из разработки изолировано по тем же правилам и получает объявленные разрешения без подтверждения, чтобы автор видел настоящее поведение. Проверка: e2e режима разработчика продолжает проходить.
- R6. Документация: ADR 0003 (что изоляция даёт и что нет), раздел «Права и изоляция» в `docs/design/extensions.md`, пример манифеста с `permissions` в руководстве автора; генератор проекта ничего лишнего не объявляет. Проверка: тест доков (примеры из раздела собираются и проходят `lms-ext validate`).

## Решения

**Факты, на которых стоит дизайн (проверены экспериментом 2026-09-30, Electron 44.4.5, Node 24.21).**
- `utilityProcess.fork(..., { execArgv: ['--permission', ...] })` флаг принимает, но **не применяет**: `process.permission` не определён, чтение `/etc/hosts`, запись, запуск процессов и потоки разрешены.
- Тот же бинарник, запущенный как Node (`child_process.spawn(process.execPath, ['--permission', '--allow-fs-read=<каталог>', entry], { env: { ELECTRON_RUN_AS_NODE: '1' }, stdio: [..., 'ipc'] })`), режим разрешений **применяет**: чтение вне каталога, запись, запуск процессов и потоки дают `ERR_ACCESS_DENIED`; IPC-канал работает. Так уже запускается воркер SQL.

**Pattern Decisions (уровень ARCHITECTURAL, скилл `patterns-and-refactoring`).**

1. Сила: один и тот же код расширения должен исполняться либо в хосте расширений (доверенные), либо в ограниченном дочернем процессе; протокол с движком и рантайм не должны знать разницы. Решение: Strategy «где исполняется расширение»: `ExtensionRunner` (`inProcess` — как сейчас; `restricted` — дочерний процесс с флагами). Рантайм хоста выбирает раннер по флагу `isolated` в запросе от движка; дочерний процесс запускает тот же `createExtensionRuntime` для одного расширения и общается по `MessageEndpoint` поверх IPC (как тест `process.test.ts`). Отвергнуто: второй `utilityProcess` на расширение — режим разрешений в нём не работает (см. факты выше).
2. Сила: доступ расширения к библиотеке курсов не должен требовать чтения файлов вне его каталога. Решение: Proxy-capability: в ограниченном процессе `ctx.library` — прокси, запросы которого выполняет родитель (хост расширений) через тот же IPC, если объявлено `library.read`; иначе методы бросают `PermissionError`. Отвергнуто: `--allow-fs-read=<корень библиотеки>` — выдавало бы чтение всего дерева, включая чужие курсы и фикстуры, без контроля `isSafePath`.
3. Сила: разрешения должны быть видны и проверяемы без запуска кода. Решение: `permissions` — данные манифеста, отображаемые в интерфейсе; сопоставление разрешение → флаги Node и возможности контекста — одна таблица (`permissions.ts`), Strategy через lookup. Отвергнуто: разбросанные проверки по рантайму.
4. Сила: интерфейс недоверенных расширений исполняется в окне приложения с доступом к `window.lms`. Решение: Adapter между custom element/рендерером и окном — sandboxed iframe с постоянным `postMessage`-контрактом; страницу рамки и её загрузчик отдаёт протокол `lms-ext` (`/__lms/frame.html`, `/__lms/frame.js`). Отвергнуто: shadow DOM (нет границы) и `iframe` с `allow-same-origin` (рамка получила бы настоящий origin `lms-ext://<id>`; без `allow-same-origin` Chromium даёт рамке непрозрачный origin, и она не видит ни `window.top`, ни хранилище приложения).
5. Сила: изменение доверия должно действовать сразу, без перезапуска. Решение: режим (`isolated`) вычисляет движок на каждый вызов по origin расширения и настройке; хост расширений держит активации раздельно по режиму (смена режима → новая активация, старая освобождается). Отвергнуто: режим в `init` хоста — потребовал бы перезапуска процессов.

```mermaid
flowchart LR
  S[(engine.db: extensions {disabled, trusted})] --> P[ExtensionPolicy: origin + settings -> enabled, isolated]
  P --> C[catalog / registry / contributions: фильтр отключённых]
  P --> Q[запросы к хосту: isolated]
  Q --> RT[runtime хоста расширений]
  RT -->|isolated=false| IN[inProcess: как сейчас]
  RT -->|isolated=true| RS[restricted: spawn ELECTRON_RUN_AS_NODE --permission ...]
  RS <-->|IPC MessageEndpoint| CH[дочерний runtime одного расширения + прокси library]
  P --> DTO[ExerciseTaskDto.isolated / MarkdownRendererDto.isolated]
  DTO --> UI[ExerciseAnswer / MarkdownView]
  UI -->|isolated| FR[iframe sandbox allow-scripts <- lms-ext://id/__lms/frame.html] 
  UI -->|trusted| EL[custom element в окне]
```

**Порядок работ:** (A) разрешения, настройка «включено/доверено», политика, DTO, экран; затем параллельно (B) изоляция кода и (C) изоляция интерфейса; (D) документация, ADR 0003, закрытие.

Контракт `@lms/engine-contract` поднимается до версии 6: `ExtensionInfoDto` (`permissions`, `isolation`, состояние `disabled`), `ExerciseTaskDto.isolated`, `MarkdownRendererDto.isolated`, сервис `extensions.getSettings/setEnabled/setTrusted`, схема RPC, хранилище настроек (`engine.db`, порт `SettingsStore`).

## Surprises & Discoveries

- Флаг `--permission` через `utilityProcess.execArgv` в Electron 44 не применяется (`process.permission === undefined`, всё разрешено); через `ELECTRON_RUN_AS_NODE` — применяется. Проверено временным скриптом (`/tmp/perm-test`, воспроизведение: спавн `process.execPath` с `--permission --allow-fs-read=<dir>` и `ELECTRON_RUN_AS_NODE=1`).

- Симлинк: на macOS `/var` — ссылка на `/private/var`, режим разрешений Node сверяет реальные пути, и `import()` расширения по «видимому» пути падал. Раннер теперь передаёт дочернему процессу `realpath` каталога и входа; регрессия покрыта тестом.
- Дочернему процессу нужен отдельный собранный вход (`restricted/ext-restricted.mjs`) вне `app.asar`: он собирается плагином `lms:restricted-child` и отправляется как `extraResources`. Вариант «внутри asar» не пробовали.
- `location.reload()` блокировался `will-navigate`; окно теперь пропускает переход на свой же адрес (нужно кнопке «Перезагрузить окно» после переключения доверия).
- В момент параллельной работы этапов B и C сквозные проверки кратковременно падали (`EXERCISE_TYPE_UNAVAILABLE`, типы в тесте рамки): промежуточное состояние дерева, на финальном дереве всё зелёное.
- Сценарий смоука `isolated` (враждебное расширение + проверка, что файл-маркер записи не появился) защищает от тихой потери `--permission` при обновлении Electron.

## Decision Log

- 2026-09-30. По умолчанию изолируются все расширения не из поставки (пользовательские и из разработки), а не только те, что просят опасные разрешения. Причина: безопасное умолчание важнее, чем сэкономить один процесс; неудобства авторам снимает «Доверять» и режим разработки.
- 2026-09-30. Разрешения применяются автоматически по объявленному, без запроса у пользователя. Причина: приоритет простоты установки (ADR 0002); информация и отключение — у пользователя в экране «Расширения».
- 2026-09-30. Расширения из поставки не переключаются и не изолируются. Причина: они часть приложения (`lms.sql` использует нативный модуль и воркеры).

## Outcomes

Сделано R1–R6. Расширения не из поставки (пользовательские и из режима разработчика) по умолчанию исполняются в ограниченном Node-процессе (`--permission`, чтение только из каталога расширения, прочее — по объявленным `permissions`, окружение из одной переменной, библиотека через посредника) и показывают интерфейс в `<iframe sandbox="allow-scripts">` с CSP от протокола `lms-ext` и мостом `postMessage`. «Настройки → Расширения»: «Включено» и «Доверять», разрешения, признак изоляции; состояние в `engine.db`; код переключается сразу, интерфейс — после перезагрузки окна. Контракт v6.

Проверено: `pnpm typecheck`, `pnpm lint`, `pnpm test` (198 файлов, 3410 тестов), `pnpm check:tests` (60/60), `pnpm -F @lms/desktop e2e` (35 сценариев, в том числе враждебные расширения кода и интерфейса, смена доверия), `pnpm smoke` и `pnpm smoke:packaged` (basic, sql, choice, renderer, isolated, crash; файл-маркер записи не создан), процессный тест на реальном дочернем процессе.

Отличия от плана: bundled-расширение никогда не считается отключённым или изолированным, даже если его id лежит в `disabled`/`trusted`; для id, которые есть только как `invalid`/`overridden`, сервис отвечает `INVALID_ARGUMENT` (`not-loaded`); вердикт враждебных фикстур — `failed`, а не `passed`, чтобы попытка оставалась открытой.

Осталось: ограничение сети для кода расширения, квоты ресурсов, подписи и проверка релизов (потребуют нового ADR перед публичным каталогом), установка расширений из приложения, команды, панели, импорт и экспорт.
