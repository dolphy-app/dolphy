# Единая точка входа расширения

> Исторический документ. Не источник требований.

Живой документ, пока `status` — `draft` или `active`: `Progress`, `Surprises & Discoveries`, `Decision Log` обновляются вместе с кодом. По завершении фичи переносится в `specs/archive/` и не меняется. Правила — скилл `spec-workflow`.

## Цель

Автор расширения пишет один исходный файл `src/index.ts` вместо россыпи `src/main.ts`, `src/view.ts`, `src/panel.ts`, `src/markdown.ts`. Сборка сама раскладывает его по контекстам исполнения (процесс расширений, окно, рамка) и выдаёт прежний набор файлов `dist-ext/<id>/`. Идентификаторы не нужно переписывать вручную в двух местах: типы строятся из `extension.json`, и расхождение кода с манифестом ловит компилятор. Приложение, хост, установщик и каталог не меняются.

## Не цели

- Генерация `extension.json` из кода: манифест остаётся статичными данными, которые приложение, каталог и проверки читают без исполнения чужого кода (ADR 0002, ADR 0004).
- Исполнение кода автора при сборке, обнаружении, установке или проверке каталога (`dolphy-ext catalog check` остаётся статическим).
- Изменение раскладки результата (`main.mjs`, `view.mjs`, `panel.mjs`, `markdown.mjs`, воркеры), контракта `engine-contract`, протокола хоста и каталога.
- Общие чанки, карты кода в каталоге, независимые версии пакетов.
- Поддержка старой раскладки `src/main.ts` + `src/view.ts`: чистый переход, без автоопределения (пакеты авторов ещё не вышли в npm, ADR 0005).

## Требования

Наблюдаемое поведение. Проверки — юнит- и интеграционные тесты `extension-tools`, `extension-sdk`, `create-extension`, `docs-contributions.test.ts`, `pnpm verify:packages`, e2e на собранных расширениях.

- R1. `dolphy-ext build` берёт `src/index.ts` с именованными экспортами `host` (результат `defineExtension`), `views` (запись `id вида задания → defineAnswerView(...)`), `panels` (`id панели → defineExtensionPanel(...)`), `markdown` (`язык → defineMarkdownRenderer(...)`). Результат — те же файлы, что и раньше, с теми же именами из манифеста (`main`, `renderer`, `module`), `extension.json` копируется как есть. Расширение без кода (темы, настройки) собирается из манифеста без `src/index.ts`. Отсутствие `src/index.ts` у расширения с кодом даёт ошибку с подсказкой переноса.
- R2. Код хоста попадает только в файл процесса расширений, код вида, панели и рендерера содержимого — только в браузерные файлы. Импорт `node:*`, встроенных модулей или `external` из `dolphy-ext.config.json` в браузерном файле — ошибка сборки с именем файла и модуля. Файлы остаются самодостаточными (без общих чанков). Воркеры (`nodeEntries` в `dolphy-ext.config.json`) остаются отдельными входами.
- R3. Сверка с манифестом при сборке: для каждого объявленного вида задания есть `views[id]`, для каждой панели — `panels[id]`, для каждого языка рендерера — `markdown[язык]`; ключи, которых нет в манифесте, — ошибка с именем ключа; вид, панель или язык, у которых несколько записей используют один файл, обслуживаются одним модулем (диспетчеризация по id). Хост после активации предупреждает в логе о командах, событиях, видах и правилах оценки, объявленных в манифесте, но не зарегистрированных кодом.
- R4. Импорт `src/index.ts` не имеет побочных эффектов: `defineAnswerView` возвращает описание без вызова `customElements.define`; регистрацию элемента (тег из манифеста) выполняет сгенерированная обвязка в браузерном файле. Поэтому `src/index.ts` можно импортировать в тестах в Node. `@dolphy-app/extension-sdk` помечен `sideEffects: false`.
- R5. Типизация id из манифеста: `dolphy-ext types` (и каждая сборка, и `--watch`) читает `extension.json` и пишет объявления типов в `.dolphy/ids.d.ts` (подключается в `tsconfig` шаблона). `defineExtension({ commands, events, exerciseTypes, gradePolicies })`, `views`, `panels`, `markdown` требуют ровно объявленные ключи (лишний или пропущенный ключ — ошибка компиляции), `ctx.settings.get(id)`, `ctx.settings.onDidChange`, `ctx.commands.register`, `ctx.events.on` принимают только объявленные id и дают тип значения настройки. Файл генерируется статически, без исполнения кода автора.
- R6. Тестирование: `loadExerciseType`, `loadEvents`, `loadCommands`, `loadGradePolicy` принимают экспорт `host` как есть; новые `loadView(views, id)` и `loadPanel(panels, id)` монтируют вид или панель в DOM-окружении тестов и возвращают помощников для проверки.
- R7. Миграция: `ext-choice`, `ext-sql`, `ext-math`, шаблон `create-dolphy-extension`, документация и проверяемые примеры (`docs-contributions.test.ts`, включая пример «серия дней целиком») переведены на единый вход. Сгенерированный проект собирается, проходит `validate`, `tsc` и свои тесты (`pnpm verify:packages`).
- R8. Режим разработчика: `dolphy-ext build --watch` пересобирает затронутые файлы при правке `src/index.ts` или `extension.json`; сообщения об ошибках называют выходной файл и экспорт; журнал сборки не дублируется по числу выходных файлов.

## Решения

- **Манифест статичен.** Генерация манифеста из кода отвергнута: она требует исполнять код автора при сборке и при проверке каталога (PR непроверенных авторов), ломает самоописываемость каталога исходников (CHECK-001…016) и дублирует JSON Schema в TypeScript. Единственный источник объявления — `extension.json`; код привязывается к нему типами.
- **Сборка по обвязкам.** Раскладка результата не меняется: для каждого выходного файла сборка создаёт виртуальную обвязку, импортирующую из `src/index.ts` нужный экспорт, и собирает её своим вызовом bundler (как сейчас — по одному на файл). Это сохраняет раскладку, фингерпринт, живое применение и каталог без изменений.
- **Побочные эффекты.** Деревья вызовов `defineX` помечены как чистые (`/*#__PURE__*/`, `sideEffects: false`), верхний уровень `src/index.ts` — только объявления (правило для авторов, проверяется защитой от `node:*` в браузерных файлах). `defineAnswerElement` как публичное API заменяется на `defineAnswerView` (описание без регистрации); регистрация — в обвязке.
- **Типы id генерируются из JSON.** `as const`-импорт JSON не сохраняет литеральные типы, поэтому нужен генератор объявлений; это дешевле, чем AST-анализ кода, и работает для любого автора на TypeScript.
- **Чистый переход.** Автоопределения старой раскладки нет: сообщение об ошибке называет шаги переноса. Пакеты авторов ещё не опубликованы (ADR 0005, первый выпуск не сделан); публичный API сейчас переформируется до первого выпуска.
- **Контракт `engine-contract` не меняется.** Меняется публичная поверхность опубликованных пакетов (`extension-sdk`, `extension-tools`, `create-extension`, `extension-api`): поэтому спека и ADR 0009.

## Surprises & Discoveries

Разведка до начала работ: сборка уже идёт по одному вызову bundler на выходной файл без общих чанков, поэтому единый вход — это замена источника на виртуальную обвязку, а не переделка раскладки; единственный побочный эффект при импорте SDK — `defineAnswerElement` (регистрирует элемент сразу); браузерная сборка не имеет `external`, поэтому `node:*` в общем файле ломает её; ext-sql держит воркер отдельным входом через `dolphy-ext.config.json`; рендерер, панель и язык могут делить один файл и должны диспетчеризоваться по id.

4a (сборка). Что вскрылось при реализации:

- Пометка чистых вызовов — `/*#__NO_SIDE_EFFECTS__*/` на объявлениях `define…` в SDK (работает через границы модулей в rolldown и сохраняется в опубликованной сборке tsdown); `/*#__PURE__*/` на вызовах автора не нужен. Поля объектов rolldown не отсекает, поэтому сборка сама урезает литералы `views`/`panels`/`markdown` до ключей текущего файла (преобразование по статическому разбору `src/index.ts`): иначе панель тянула бы код видов и рендереров.
- Защита от `node:*` проверяет итоговый код браузерного файла, а не разрешение импортов: импорт в `src/index.ts` (код хоста) остаётся в графе и после отсечения кода хоста. Бандлер оставляет от отсечённого кода голые `import "node:…"` (метаданные чанка `imports` тоже врут) — сборка убирает такие импорты без привязок из браузерного файла и падает на импорте с привязками. Верхний уровень библиотеки с вызовами без пометки (`createRequire` в `engine-sql-runner`) считается кодом с эффектами и попадал в `view.mjs`: пакет получил `sideEffects` (только `worker.ts`). Правило для авторов — в `docs/design/extensions.md`.
- Ключи записей читаются статически (литерал, локальная константа, `as const`/`satisfies`, относительный реэкспорт); спред, вычисляемый ключ и импорт из пакета — ошибка с причиной, а не молчаливый пропуск.
- Сбой первой сборки не оставляет вотчеру файлов для слежения: плагин сам добавляет `src/index.ts` и разобранные файлы в список слежения. Правка `extension.json` в `--watch` перезапускает все вотчеры, сохраняя выход.
- Вотчеры по числу файлов шлют события одной правки порознь: отчёт собирается, пока какой-либо вотчер занят (`START`…`END`), и уходит после тишины в 150 мс; одинаковые ошибки сводятся в одну запись.
- Тесты в happy-dom: `loadView` создаёт элемент с тестовым тегом, а не с тегом манифеста.

4b (типы id):

- Расширение интерфейса из `export *` и именованного реэкспорта работает и в TS 6, и в TS 7. `include` с каталогом `.dolphy` не берёт файлы скрытого каталога: в `tsconfig` нужен путь к файлу `.dolphy/ids.d.ts`. ESLint без игнора `**/.dolphy/**` линтит сгенерированный файл.
- Если проект компилирует исходники SDK (ссылка `link:`), присваивание `ExtensionDefinition` внутренней форме падает при сужении; `defineExtension` приводит определение к свободной форме.
- Проверка типов в `docs-contributions.test.ts` сразу нашла два примера (события и серия дней), где `activate` регистрирует объявленные id: им понадобился `inActivate`.

## Decision Log

- 2026-10-02. Манифест не генерируется из кода, типы строятся из манифеста. Причина: исполнение кода автора недопустимо при проверке каталога и обнаружении; манифест должен читаться без кода.
- 2026-10-02. Регистрация элемента — подпуть `@dolphy-app/extension-sdk/runtime` (`registerAnswerView`, `dispatchPanels`, `dispatchMarkdown`), который импортирует только сгенерированная обвязка; разрешается из проекта автора, чтобы описания и регистрация были из одной копии SDK. Причина: `index.ts` SDK обязан оставаться без DOM.
- 2026-10-02. Типы описаний видов переименованы вместе с функцией: `AnswerView`, `AnswerViewApi`, `AnswerViewInstance`, `MountAnswerView`. Причина: чистый переход, без алиасов.
- 2026-10-02. Чистый переход без автоопределения старой раскладки. Причина: пакеты авторов не опубликованы, правило репозитория — без совместимых прослоек.
- 2026-10-02. Записи `defineExtension` (`exerciseTypes`, `gradePolicies`, `events`, `commands`) исчерпывающие: при сгенерированных типах запись обязательна, если манифест объявляет id этого вида, содержит ровно объявленные ключи и недопустима, если id нет. Id, который регистрируется в `activate` через `ctx.*.register`, получает в записи значение `inActivate` из SDK. Причина: компилятор не видит тело `activate`, а без явной пометки пропущенный ключ нельзя отличить от id, зарегистрированного вручную; `Partial` потерял бы проверку «пропущенный ключ». Предупреждение хоста о незарегистрированном id остаётся. Без `.dolphy/ids.d.ts` записи необязательны и открыты, все id — `string`.
- 2026-10-02. `ExtensionIds` объявлен в SDK и расширяется через `declare module '@dolphy-app/extension-sdk'`; файл подключается в `tsconfig` по имени (`.dolphy/ids.d.ts`), потому что `include` пропускает скрытый каталог целиком. `views`, `panels`, `markdown` проверяются через `satisfies ExtensionViews|ExtensionPanels|ExtensionMarkdown`, а не обёрткой, чтобы сборка по-прежнему читала ключи статически. `ExtensionContext` и `PanelContext` SDK шадоуят обобщённые типы `extension-api` (у них умолчания — строки, движок и хост не меняются).

## Outcomes

Сделано всё из `Требований` R1–R8: единый вход `src/index.ts` с экспортами `host`, `views`, `panels`, `markdown`; сборка по виртуальным обвязкам с диспетчеризацией общих файлов, отсечением кода по контекстам и защитой от `node:*` в браузерных файлах; сверка с манифестом при сборке и предупреждение хоста о незарегистрированном; `defineAnswerView` без побочных эффектов при импорте (регистрация в обвязке через `@dolphy-app/extension-sdk/runtime`); типы id из манифеста (`dolphy-ext types`, `.dolphy/ids.d.ts`, исчерпывающие записи с `inActivate`); `loadView` и `loadPanel`; `--watch` с одним отчётом на правку; миграция `ext-choice`, `ext-sql`, `ext-math`, шаблона `create-dolphy-extension` и примеров документации.

Долговечное перенесено: `docs/design/extensions.md` (раздел «Как сборка раскладывает `src/index.ts`», «Типизированные id», «Как написать расширение»), README `extension-sdk`, `extension-tools`, карта `packages/README.md`. Решение — [ADR 0009](../../../docs/adr/0009-single-entry-extension-authoring.md).

Отличия от плана: пометка чистоты — `/*#__NO_SIDE_EFFECTS__*/` на объявлениях SDK, а не `/*#__PURE__*/` на вызовах автора; литералы `views`/`panels`/`markdown` сборка урезает сама; записи `defineExtension` исчерпывающие (`inActivate`), а не частичные; `engine-sql-runner` получил `sideEffects`. При закрытии весь публичный текст пакетов `extension-api`, `extension-sdk`, `extension-tools`, `create-extension`, README корня, приложения и пакетов и поля `package.json` переведены на английский (правило `AGENTS.md`, «Язык документов»).

Осталось (вне спеки): сообщения CLI `engine-cli` в `packages/engine` ещё на русском; публичные README ссылаются на русские заголовки внутренней документации.
