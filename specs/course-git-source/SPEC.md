# Подгрузка курсов из git-репозитория

Живой документ, пока `status` — `draft` или `active`: `Progress`, `Surprises & Discoveries`, `Decision Log` обновляются вместе с кодом. По завершении фичи переносится в `specs/archive/` и не меняется. Правила — скилл `spec-workflow`.

## Цель

Ученик добавляет курс по URL git-репозитория: курсы из него появляются в каталоге «Курсы» без перезапуска и без ручного копирования файлов в `<userData>/library`. Репозиторий можно обновить (подтянуть новый коммит) и удалить; прогресс в журнале при этом не теряется. Аналог `repository add <url>` в Trane (`managed_courses`), закрывает строку «Vault и „Добавить контент“» этапа 5 в `apps/desktop/README.md`.

## Не цели

- Приватные репозитории и хранение учётных данных (токены, SSH-ключи). Только публичные `http(s)`-URL без логина и пароля в адресе.
- Автоматическое обновление (по таймеру, при запуске) и любая сетевая активность без действия ученика.
- Произвольный коммит как `ref`, подмодули, git LFS, sparse checkout, подкаталог репозитория как корень курса.
- Правка курса внутри приложения и отправка изменений в репозиторий (снимок read-only).
- Синхронизация списка репозиториев между устройствами (как и настройки: устройства не синхронизируют их друг с другом).
- Системный прокси и свои CA [ИНФЕРЕНЦИЯ: `utilityProcess` не использует сетевой стек Chromium; отдельная фича, если понадобится].
- Подписи коммитов, allow-list доменов, проверка доверия к автору курса (содержимое курса, включая SQL упражнений, выполняется так же, как у локальной библиотеки).

## Требования

Наблюдаемое поведение, не реализация. У каждого требования есть проверка.

- R1. `repositories.add({url, ref?})` для репозитория с курсами возвращает `RepositoryDto` со статусом `ready`, 40-символьным `commit` и `courseIds`; курсы сразу видны в `library.listCourses`, событие `library-reloaded` отправлено, перезапуск не нужен. Без `ref` берётся ветка по умолчанию удалённого репозитория; `ref` — имя ветки или тега. Проверка: тест сервиса на локальном git-сервере из `@lms/testkit`; e2e «Добавить из Git» → курс в сетке.
- R2. Добавление атомарно: если в репозитории нет ни одного манифеста курса, либо `reload` отклонён (ошибки сканера, например `E_ID_DUPLICATE` с уже загруженным курсом), `add` падает `REPOSITORY_REJECTED` с диагностиками в `details`; граф, строка в БД и файлы в библиотеке остаются как были. Проверка: тесты сервиса (пустой репозиторий, дубликат id, битый манифест).
- R3. Неверный вход отвергается до обращения к сети: схема не `http`/`https`, логин или пароль в URL, пустой или некорректный URL, `ref` с пробелами или `..` — `INVALID_ARGUMENT` (`details.field`). Повторный `add` того же URL (после нормализации: регистр хоста, хвостовые `/` и `.git`) — `REPOSITORY_EXISTS`. Проверка: тесты схемы RPC и сервиса.
- R4. Сбои сети различимы: `GIT_FETCH_FAILED` с `details.reason` ∈ `not-found` (404/не репозиторий), `auth-required` (401/403), `ref-not-found`, `timeout`, `network`, `too-large`. При любом сбое состояние не меняется (R2). Проверка: тесты адаптера на сервере, отвечающем кодами; таймаут бездействия — на подвешенном соединении.
- R5. `repositories.update(id)` спрашивает у удалённого репозитория только коммит ветки/тега. Совпал с сохранённым — `{changed: false}`, объекты не скачиваются, файлы не трогаются. Отличается — скачивается новый снимок, граф подменяется атомарно, `commit` и `fetchedAt` обновляются, возвращается `{changed: true}`. Отклонённый `reload` оставляет прежний снимок и прежний граф, записывает `lastError` в `RepositoryDto`, вызов падает `REPOSITORY_REJECTED`. Проверка: тесты сервиса (тот же коммит, новый коммит, новый коммит с ошибкой в манифесте).
- R6. `repositories.remove(id)` удаляет снимок и запись; курсы исчезают из `library.listCourses`, выбранный курс из этого репозитория сбрасывается существующей логикой `course-scope`. Журнал попыток не меняется: события пропавших курсов дают `W_ORPHAN_EVENTS`, а повторное добавление того же репозитория возвращает прогресс (`getProgress` совпадает с прежним). Проверка: тест сервиса с `recordAttempt` до `remove` и после повторного `add`.
- R7. Снимок безопасен: в библиотеку попадают только обычные файлы и каталоги. Символические ссылки, пути с `..`, абсолютные пути, сегмент `.git` в любой части пути, совпадающие без учёта регистра пути и превышение лимитов (число файлов, суммарный размер) — `REPOSITORY_REJECTED` (или `GIT_FETCH_FAILED/too-large` для лимита скачивания), ничего не записано. Хуки git не запускаются, записи вне `<libraryRoot>/repositories/<id>` не происходит. Проверка: тесты адаптера на фикстурных репозиториях с каждым случаем.
- R8. Долгая операция видна и отменяема: во время `add`/`update` приходят события `repository-progress` `{id, phase, loaded?, total?}` (`phase` ∈ `resolve`, `fetch`, `export`, `validate`, `reload`); `repositories.cancel(id)` прерывает операцию, состояние как до неё (R2). Пока идёт сеть, остальные методы движка (`plan`, `practice`) отвечают без задержки, вызванной загрузкой. Проверка: тест сервиса с медленным сервером; замер `plan.getDay` во время загрузки.
- R9. Реестр переживает перезапуск: `repositories.list()` после рестарта возвращает те же записи, сеть при запуске не используется. Завершение хоста посреди `add`/`update` не оставляет частичного снимка: после старта в `<libraryRoot>/repositories/` нет каталогов без записи в БД, нет промежуточных каталогов, библиотека загружается. Запись, у которой пропал каталог, получает статус `error` и обновляется повторным `update`. Проверка: тест с убитым процессом (по образцу SIGKILL-теста `engine-sqlite`), тест восстановления при старте.
- R10. Операции над репозиториями выполняются строго по очереди, вместе с `library.reload`. Две одновременные `update` одного `id`: вторая стартует после первой, видит уже загруженный коммит и возвращает `{changed: false}`; снимок цел. Проверка: тест параллельных вызовов.
- R11. Интерфейс: на экране «Курсы» действие «Добавить из Git» открывает диалог (URL, необязательный `ref`, индикатор по `repository-progress`, отмена, ошибка с причиной по `reason` и диагностиками сканера); в «Настройки → Библиотека» список репозиториев (URL, ветка/тег, короткий коммит, дата, статус, число курсов) с «Обновить» и «Удалить» (подтверждение). Все строки — через `vue-i18n` (`ru`/`en`), дата — `d`. Проверка: `pnpm -F @lms/desktop typecheck` (типы ключей), e2e: добавить, увидеть курс, обновить без изменений («уже актуально»), удалить.
- R12. Схема БД, RPC и контракт согласованы: `RPC_METHODS` ↔ `LearningEngine` (тип-тест), zod-схемы `repositories.*`, миграция `engine.db` `user_version` +1, общий набор `describeRepositoryStoreContract` проходят оба адаптера (SQLite и память). Проверка: `pnpm typecheck`, `pnpm test`.

## Решения

**Модель.** Репозиторий — запись `RepositoryDto {id, url, ref, commit, fetchedAt, status: 'ready'|'updating'|'error', courseIds, lastError?}`. `id` — стабильный slug нормализованного URL (`github.com-acme-sql-course`, при коллизии суффикс из 8 hex от SHA-1 URL); ключ уникальности — нормализованный URL. Смена ветки — `remove` + `add` (прогресс сохраняется, R6).

**Снимок вместо клона.** На диске нет `.git`: `<libraryRoot>/repositories/<id>/` — полный снимок дерева коммита, read-only по смыслу. Следствия: сканер видит курсы штатно (`ignored_paths` работает по префиксу `repositories/<id>`), нет локальных правок и конфликтов слияния, нет хуков и подмодулей, нет состояния объектного хранилища, которое можно повредить. Цена: при новом коммите скачивается снимок целиком (`depth: 1`); курсы — текст и небольшие ассеты, для больших репозиториев пересмотреть (Decision Log). Имя каталога `repositories` не занято курсами из `dev-library`; ручной курс с таким именем в корне библиотеки — конфликт, который сервис проверяет при `add` (`REPOSITORY_REJECTED`, если `repositories/<id>` существует без записи).

**Поток `add`/`update`.** `resolve` (запрос refs, без скачивания; совпавший коммит — выход, R5) → `fetch` (shallow, single-branch во временный `gitdir` `<dataDir>/git-tmp/<opId>`) → `export` (обход дерева коммита своим кодом с проверками R7, запись в `<libraryRoot>/.staging/<opId>/`) → `validate` (сканирование staging как отдельной библиотеки: есть манифесты курса, нет ошибок сканера) → подмена: `rename(repositories/<id> → .trash/<opId>)`, `rename(.staging/<opId> → repositories/<id>)` → `reload` (ошибки → обратная подмена и отказ R2/R5) → запись в БД → удаление `.trash/<opId>` и временных каталогов. `.staging` и `.trash` лежат в корне библиотеки, поэтому `rename` остаётся в одной файловой системе, а сканер пропускает каталоги с точкой (`scan.ts:583`). Запись в БД — последний шаг: она фиксирует, какой коммит загружен. Старт (`boot`): удалить `git-tmp`, `.staging`, `.trash`; каталоги `repositories/*` без записи в БД удалить; записи без каталога пометить `error`.

**Git-клиент.** Пакет `@lms/engine-git` (новый): порт `GitSnapshotFetcher {resolve(url, ref, signal), fetch(url, ref, dest, limits, signal, onProgress)}` объявлен в `@lms/engine/ports`, адаптер — на `isomorphic-git` 1.42 (MIT, чистый JS, без бинарника `git`; `listServerRefs`/`getRemoteInfo2` для `resolve`, `clone` с `depth: 1, singleBranch: true, noCheckout: true` для `fetch`, обход дерева через `walk`/`readBlob`). Системный `git` отвергнут: его нет у части пользователей Windows и macOS, а приложение ставится неподписанным установщиком без зависимостей; запуск внешнего процесса с пользовательским URL расширил бы поверхность атаки (`ext::`, `file://`, хуки). Цена isomorphic-git: нет SSH, LFS, partial clone, медленнее на больших репозиториях — все вне целей.

**Лимиты** (константы пакета, [ПРЕДЛОЖЕНИЕ], уточнить на реальных курсах): 20 000 файлов, 256 МиБ суммарно, 32 МиБ на файл, 60 с без прогресса в сети. Сканер и так справляется с 40 тыс. файлов (`fs-course-source.ts`), лимит берётся с запасом.

**Реестр.** Порт `RepositoryStore` (`@lms/engine/ports`), адаптер SQLite — таблица `repository (id TEXT PRIMARY KEY, body TEXT NOT NULL) STRICT` новой миграцией в `engine-sqlite/src/migrations.ts` (по образцу `saved_filter`), адаптер памяти для тестов. Реестр лежит в `engine.db`, а не в файле библиотеки: `AGENTS.md` — пользовательское состояние хранится в БД, а каталог библиотеки — только содержимое курсов.

**Контракт.** Новый сервис `repositories` в `LearningEngine` (`list`, `add`, `update`, `remove`, `cancel`), коды ошибок `REPOSITORY_EXISTS`, `REPOSITORY_REJECTED`, `GIT_FETCH_FAILED`, событие `repository-progress`; `CONTRACT_VERSION` +1; `RPC_METHODS`, zod в `engine-rpc/src/host/schemas.ts`, клиент. `EngineConfig` не меняется: корень `repositories/` выводится из `libraryRoot`, временные каталоги — из `dataDir`.

**Сервис** (`packages/engine/src/app/services/repositories.ts`): очередь операций (один исполнитель, R10), `AbortController` на операцию (R8), вызов `library.reload` через тот же `ctx`; подмена каталогов — порт `SnapshotInstaller` (fs-адаптер в `@lms/engine/node`, память в тестах), чтобы сервис не знал про `node:fs`.

**UI.** `pages/courses` — кнопка и диалог `AddRepositoryDialog` (модель диалога в `model/`, без строк в `lib/`); `pages/settings` — секция «Репозитории» в «Библиотеке»; клиент — `shared/api/engine`. Строки — `pages/courses/i18n`, `pages/settings/i18n`; `RepositoryDto.url`, названия курсов и диагностики движка не переводятся.

**Тестовая инфраструктура.** `@lms/testkit`: `serveGitRepo(files | dir)` — локальный HTTP-сервер поверх `git http-backend` (CGI из установленного `git`, нужен только разработке и CI), создаёт репозитории с заданными коммитами, симлинками и т. п. [ИНФЕРЕНЦИЯ: `git http-backend` есть в образе `ubuntu-latest` и в Apple Git; проверить на первом же тесте].

## Surprises & Discoveries

- `origin/develop` не содержит `specs/` и `docs/adr/`: ветка `feature/extension-isolation` (спека `extension-isolation`, ADR 0001–0002) ещё не влита. Она трогает те же `engine-contract`, `engine-rpc`, `engine-sqlite`, `testkit`, `desktop`; конфликты в `rpc.ts`/`schemas.ts`/`migrations.ts` ожидаемы — подтягивать `develop` в ветку по мере слияния. Номер следующего ADR зависит от того, что влито первым.
- Сканер уже пропускает каталоги с `.` (включая `.git`) и при отклонённом `reload` сохраняет прежний граф (`library.ts`) — на этом держатся откаты R2/R5.

## Decision Log

- 2026-09-30. Git-клиент — `isomorphic-git`, а не системный `git`. Причина: нет внешних зависимостей у пользователя, нет запуска процессов с недоверенным URL. Отмена — если на реальных курсах упрёмся в скорость или понадобится SSH.
- 2026-09-30. На диске снимок без `.git`, а не рабочая копия клона. Причина: нет локальных правок и состояния для порчи, атомарная подмена каталога. Отмена — большие репозитории, для которых нужно инкрементальное получение.
- 2026-09-30. Только публичные `http(s)`-репозитории, без учётных данных. Причина: безопасное хранение секретов (Electron `safeStorage` живёт в main, а git работает в `utilityProcess`) — отдельная фича со своим решением.
- 2026-09-30. Реестр репозиториев в `engine.db`, не синхронизируется. Причина: правило `AGENTS.md` о пользовательском состоянии; устройства не делят настройки.
- 2026-09-30. Обновление только по действию ученика. Причина: приложение не ходит в сеть без просьбы; периодическая проверка — отдельная спека.
- 2026-09-30. Уникальность по нормализованному URL; смена ветки — `remove` + `add`. Причина: детерминированное имя каталога и простая модель, прогресс сохраняется по `unitId`.
